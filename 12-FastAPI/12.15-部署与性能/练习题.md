# 12.15 部署与性能练习题

## 一、概念题

1. `fastapi dev` 和 `fastapi run` 在监听地址、自动重载、多进程支持上有什么区别？为什么容器中必须监听 `0.0.0.0`？
2. 一个 Uvicorn 进程为什么只能用满一个 CPU 核？`--workers` 是如何利用多核的？多个 worker 之间能共享哪些东西、不能共享哪些东西？
3. 用 Gunicorn 管理 Uvicorn worker 时，`worker_class` 应该写什么？老教程中的 `uvicorn.workers.UvicornWorker` 现在有什么问题？
4. 在 Kubernetes 中部署时，为什么通常建议"每个容器一个进程"，而不是在容器里开 `--workers`？
5. liveness 探针和 readiness 探针分别在失败时会触发什么动作？为什么不应在 liveness 探针中检查数据库？
6. Dockerfile 中"先复制依赖清单安装依赖，再复制源码"的目的是什么？多阶段构建解决了什么问题？
7. exec 形式的 `CMD ["fastapi", "run", ...]` 与 shell 形式的 `CMD fastapi run ...` 在接收停止信号时有什么区别？对 lifespan 的清理逻辑有什么影响？
8. `--proxy-headers` 和 `--forwarded-allow-ips` 分别起什么作用？如果把 `--forwarded-allow-ips` 设为 `*`，什么情况下是安全的，什么情况下是危险的？
9. 什么是 `root_path`？Nginx 的 `proxy_pass http://app/;`（结尾带 `/`）与 `proxy_pass http://app;`（不带 `/`）对应用的路由和 `root_path` 设置分别有什么影响？
10. 为什么在 `async def` 端点里调用 `time.sleep(1)` 会让整个服务"卡住"，而在 `def` 端点里调用就不会？`def` 端点的并发上限由什么决定？

```python

@app.get("/a")

    requests.get("https://httpbin.org/delay/1", timeout=5)   # 外部接口耗时约 1 秒

@app.get("/b")
def b():
    requests.get("https://httpbin.org/delay/1", timeout=5)

    time.sleep(0.1)
```

## 三、编程题

### 1. 健康检查（基础）

为一个使用 SQLAlchemy 和 Redis 的应用实现：

- `GET /healthz`：只返回 `{"status": "alive"}`；
- `GET /readyz`：并发检查数据库（`SELECT 1`）和 Redis（`PING`），每项检查设置 2 秒超时；全部成功返回 200，任一失败返回 503，并在响应体中给出每项检查的结果和耗时；
- 两个端点都不出现在 `/docs` 中；
- 用 `TestClient` + `dependency_overrides`（或 `fakeredis`）编写测试，覆盖成功和失败两种情况。

### 2. 结构化日志与请求 ID（基础）

- 实现一个纯 ASGI 中间件或 `@app.middleware("http")`，为每个请求生成或透传 `X-Request-ID`；
- 用 `contextvars.ContextVar` 保存请求 ID，并编写一个 `logging.Filter`，让业务代码中任意位置的 `logger.info()` 都自动带上 `request_id` 字段；
- 日志以 JSON 格式输出到 stdout；
- 未捕获的异常要被记录为 `ERROR` 级别日志，包含堆栈和请求 ID，同时客户端收到的 500 响应体中也包含请求 ID。

### 3. 阻塞检测（进阶）

编写一个开发环境使用的工具，帮助发现"在 `async def` 中调用了阻塞代码"的问题：

- 在 lifespan 中启动一个后台协程，每 100ms `await asyncio.sleep(0.1)` 一次，测量实际经过的时间；
- 如果实际间隔超过 300ms，说明事件循环被阻塞了，打印警告日志；
- 进阶：同时开启 `asyncio` 的调试模式（`loop.set_debug(True)` 与 `loop.slow_callback_duration`），对比两种方式的输出；
- 编写一个故意阻塞的端点，验证你的工具能检测到它。

### 4. 容器化一个完整项目（进阶）

把 12.12 节的项目（或 12.16 综合实战项目）容器化：

- 使用 uv 管理依赖，编写多阶段构建的 Dockerfile，最终镜像以非 root 用户运行；
- 编写 `.dockerignore`，确认 `.env`、`.venv`、`.git` 不会进入构建上下文；
- 编写 `compose.yaml`，包含 app、PostgreSQL、Redis，数据库健康后才启动 app；
- 增加一个一次性的 `migrate` 服务，在 app 启动前执行 `alembic upgrade head`；
- 用 `docker image ls` 对比单阶段和多阶段构建的镜像体积。

### 5. Nginx 反向代理（进阶）

在第 4 题的 Compose 中加入 Nginx：

- 应用挂在 `/api` 子路径下，`/api/docs` 能正常打开并调试接口；
- 支持 WebSocket（用 12.14 节的聊天室验证）和 SSE（验证数据能逐条到达，没有被缓冲）；
- 应用中通过 `request.client.host` 能拿到真实客户端 IP；
- 用 `docker compose up --scale app=3` 启动 3 个应用实例，验证 Nginx 能把请求分发到不同实例（让接口返回 `socket.gethostname()`）。

### 6. 缓存与限流（挑战）

为一个"商品详情"接口实现：

- 基于 `redis.asyncio` 的缓存装饰器 `@cached(ttl=60, key="product:{product_id}")`，能根据端点参数生成缓存键；
- 商品更新接口调用后自动删除对应缓存；
- 防缓存击穿：同一个键缓存失效时，只允许一个请求去查数据库，其他请求等待结果（提示：Redis `SET NX` 分布式锁，或进程内 `asyncio.Lock` + 字典）；
- 使用 `slowapi` 对该接口按用户 ID（从 JWT 中解析，未登录则按 IP）限流 100 次/分钟，限流数据存储在 Redis 中；
- 用 locust 压测，对比加缓存前后的 QPS 和 P99 延迟。

## 四、综合实践：上线一个 FastAPI 服务

以 12.16 综合实战项目为对象，完成一次完整的"上线演练"，并撰写一份部署文档：

1. **配置**：所有环境相关的配置（数据库、Redis、密钥、CORS 白名单、是否开放文档）通过环境变量注入，提供 `.env.example`。
2. **镜像**：多阶段构建，镜像体积控制在 200MB 以内；镜像中不包含测试代码和密钥。
3. **编排**：Compose 编排 Nginx + app（3 个副本）+ PostgreSQL + Redis；所有服务配置 `restart` 策略和健康检查。
4. **代理**：Nginx 提供 HTTPS（可以用 `mkcert` 或 `openssl` 生成本地自签名证书）、HTTP 跳转 HTTPS、WebSocket、SSE、上传大小限制。
5. **可观测性**：JSON 日志带请求 ID；提供 `/metrics` 端点输出 Prometheus 指标（可使用 `prometheus-fastapi-instrumentator`）。
6. **优雅停机**：在 lifespan 中释放数据库和 Redis 连接；验证 `docker compose stop app` 时，正在处理的慢请求（10 秒）能正常完成。
7. **压测**：用 locust 编写包含登录、列表查询、详情查询、创建的混合场景，记录 50 / 200 并发下的 QPS、P95、P99 和错误率；找出一个瓶颈并优化，记录优化前后的对比数据。
8. **检查清单**：对照本节第 11 节的生产检查清单逐项自查，在文档中记录每一项的落实方式。
