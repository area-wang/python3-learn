# 12.15 部署与性能

到目前为止，我们一直用 `fastapi dev` 在本机跑应用。真正上线时要考虑的事情多得多：用什么命令启动、开几个进程、怎么打成 Docker 镜像、前面要不要挡一层 Nginx、HTTPS 怎么配、日志怎么收集、负载均衡怎么知道实例是否健康、为什么压测时 QPS 上不去……本节把这些"最后一公里"的问题串起来，并重点讲解 FastAPI 中最常见的性能陷阱——**在 `async def` 里调用阻塞代码**。

> 本节命令和代码基于 FastAPI 0.143 / Uvicorn 0.54 / Gunicorn 26 实际运行验证；Nginx 配置在 nginx 1.25 上做过端到端测试；Compose 文件通过 `docker compose config` 校验。

## 1. 开发模式 vs 生产模式

FastAPI 自带的命令行工具（`fastapi-cli`，`pip install "fastapi[standard]"` 已包含）提供了两个子命令：

```bash
fastapi dev main.py     # 开发：自动重载，只监听 127.0.0.1
fastapi run main.py     # 生产：不重载，监听 0.0.0.0
```

| | `fastapi dev` | `fastapi run` |
|---|---|---|
| 自动重载 `--reload` | 默认开启 | 默认关闭 |
| 默认监听地址 | `127.0.0.1`（只有本机能访问） | `0.0.0.0`（所有网卡，容器中必须如此） |
| 默认端口 | 8000 | 8000（可用环境变量 `PORT` 覆盖） |
| 多进程 `--workers` | 不支持（与 reload 互斥） | 支持 |
| 代理头 `--proxy-headers` | 默认开启 | 默认开启 |
| 用途 | 本地开发调试 | 容器 / 服务器部署 |

`fastapi run` 底层就是 Uvicorn，等价于：

```bash
uvicorn main:app --host 0.0.0.0 --port 8000
```

### 1.1 在 pyproject.toml 中声明入口

项目结构复杂时，可以在 `pyproject.toml` 中声明应用入口，之后直接运行 `fastapi dev` / `fastapi run`，不必每次写路径：

```toml
[tool.fastapi]
entrypoint = "app.main:app"
```

```text
$ fastapi run --port 8000
 🐍 Using import string: app.main:app
 ...
```

> ⚠️ **生产环境绝对不要开 `--reload`**：它会监控文件变化，占用额外 CPU，而且重载期间请求会失败。

## 2. Uvicorn 常用参数

`fastapi run` 支持最常用的几个参数；需要更精细的控制时直接使用 `uvicorn` 命令：

| 参数 | 说明 | 建议 |
|---|---|---|
| `--host` | 监听地址 | 容器中用 `0.0.0.0` |
| `--port` | 监听端口 | 默认 8000 |
| `--workers N` | 启动 N 个工作进程 | 见第 3 节 |
| `--proxy-headers` / `--no-proxy-headers` | 是否信任 `X-Forwarded-For` / `X-Forwarded-Proto` | 在代理后面时开启（默认开启） |
| `--forwarded-allow-ips` | 只信任来自这些 IP 的代理头，默认 `127.0.0.1,::1` | 设为 Nginx / 负载均衡的 IP 或网段；`*` 表示全部信任 |
| `--root-path` | 应用挂在代理的子路径下时使用，见第 7 节 | 如 `/api` |
| `--log-level` | `critical/error/warning/info/debug/trace` | 生产用 `info` 或 `warning` |
| `--access-log` / `--no-access-log` | 是否输出访问日志 | 自己实现了访问日志中间件时可关闭 |
| `--log-config` | 日志配置文件（`.json` / `.yaml` / `.ini`） | 见第 9 节 |
| `--timeout-keep-alive` | Keep-Alive 空闲超时秒数，默认 5 | 在负载均衡后面时，应**大于**负载均衡的空闲超时 |
| `--timeout-graceful-shutdown` | 优雅停机最多等待秒数 | 配合 K8s 的 `terminationGracePeriodSeconds` |
| `--limit-concurrency` | 最大并发连接数，超出返回 503 | 保护服务不被打垮 |
| `--limit-max-requests` | 处理这么多请求后重启 worker | 缓解内存泄漏 |
| `--ws-ping-interval` / `--ws-ping-timeout` | WebSocket 协议层心跳 | 默认 20 秒 |
| `--ssl-keyfile` / `--ssl-certfile` | 直接由 Uvicorn 提供 HTTPS | 一般交给 Nginx 处理，见第 8 节 |

## 3. 多进程：workers 与 Gunicorn

一个 Uvicorn 进程只有一个事件循环，受 GIL 限制**只能用满一个 CPU 核**。要利用多核，需要启动多个进程，由一个主进程（master）管理多个工作进程（worker），它们共享同一个监听端口。

### 3.1 `--workers`

```python
# main.py
import os

from fastapi import FastAPI

app = FastAPI()


@app.get("/pid")
def pid():
    return {"pid": os.getpid()}
```

```bash
fastapi run main.py --workers 3
# 或：uvicorn main:app --host 0.0.0.0 --workers 3
```

```text
INFO:     Started parent process [37229]
INFO:     Started server process [37239]
INFO:     Started server process [37237]
INFO:     Started server process [37238]
```

多次请求 `/pid`，会看到响应来自不同的进程 ID。Uvicorn 的主进程会监控 worker，worker 崩溃时自动拉起新的。

### 3.2 Gunicorn + uvicorn-worker

Gunicorn 是老牌的 Python 进程管理器，提供更丰富的进程管理能力（超时自动杀死卡死的 worker、平滑重载、`max_requests` 等）。它本身只支持 WSGI，需要搭配 **Uvicorn worker** 来运行 ASGI 应用：

```bash
pip install gunicorn uvicorn-worker
```

> ⚠️ 很多老教程写的是 `-k uvicorn.workers.UvicornWorker`。这个模块在新版 Uvicorn 中**已弃用**（导入时会发出 `DeprecationWarning`），官方要求改用独立的 `uvicorn-worker` 包，类路径为 **`uvicorn_worker.UvicornWorker`**。

用配置文件管理参数更清晰：

```python
# gunicorn.conf.py
import multiprocessing

bind = "0.0.0.0:8000"
workers = multiprocessing.cpu_count() * 2 + 1   # 经验公式，按压测结果调整
worker_class = "uvicorn_worker.UvicornWorker"     # 注意：不是已弃用的 uvicorn.workers.UvicornWorker
timeout = 60                 # worker 超过 60s 无响应就被杀掉重启
graceful_timeout = 30        # 收到停止信号后最多等 30s 处理完在途请求
keepalive = 5
max_requests = 10000         # 每个 worker 处理 1 万请求后重启，缓解内存泄漏
max_requests_jitter = 1000   # 加随机抖动，避免所有 worker 同时重启
accesslog = "-"
errorlog = "-"
loglevel = "info"
```

```bash
gunicorn main:app -c gunicorn.conf.py
```

```text
[INFO] Starting gunicorn 26.2.0
[INFO] Listening at: http://0.0.0.0:8000 (37261)
[INFO] Using worker: uvicorn_worker.UvicornWorker
[INFO] Booting worker with pid: 37263
[INFO] Booting worker with pid: 37264
...
```

### 3.3 开几个 worker？

| 部署方式 | 建议 |
|---|---|
| 单台虚拟机 / 物理机 | `workers ≈ CPU 核数`（纯 async 应用）到 `2 × 核数 + 1`（有较多同步代码），以压测结果为准 |
| Kubernetes / 多容器 | **每个容器 1 个进程**（`fastapi run`，不加 `--workers`），通过增加 Pod 副本数扩容。进程管理、重启、负载均衡交给 K8s |
| Docker Compose 单机 | 可以 `--workers N`，也可以 `docker compose up --scale app=N` + Nginx 负载均衡 |

> ⚠️ 多进程之间**不共享内存**：进程内的全局字典缓存、`ConnectionManager`（12.14 节）、内存限流计数器都只在单个进程内有效，并且每个进程都会执行一次 lifespan。需要共享的状态要放到 Redis / 数据库。

## 4. 健康检查端点

负载均衡、Docker、K8s 都需要定期探测应用是否正常。通常提供两类端点：

- **存活探针（liveness）**：进程活着、能响应就行。失败时编排系统会**重启**容器。不要在这里检查数据库——数据库一抖动，所有实例都被重启，反而雪上加霜。
- **就绪探针（readiness）**：能否正常对外服务（数据库、缓存等关键依赖可用、启动预热完成）。失败时只是**暂时不分配流量**。

```python
# health.py
from contextlib import asynccontextmanager

from fastapi import FastAPI, Response, status
from sqlalchemy import create_engine, text

engine = create_engine("sqlite:///./app.db")


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.ready = True          # 启动完成（加载模型、预热缓存……）后才算就绪
    yield
    app.state.ready = False         # 收到停机信号后先摘流量
    engine.dispose()


app = FastAPI(lifespan=lifespan)


@app.get("/healthz", include_in_schema=False)
def liveness():
    """存活探针：进程还活着、能响应即可，不要检查外部依赖。"""
    return {"status": "alive"}


@app.get("/readyz", include_in_schema=False)
def readiness(response: Response):
    """就绪探针：检查关键依赖，失败返回 503，让负载均衡暂时别把流量打过来。"""
    checks: dict[str, str] = {}
    try:
        with engine.connect() as conn:
            conn.execute(text("SELECT 1"))
        checks["database"] = "ok"
    except Exception as e:
        checks["database"] = f"error: {e.__class__.__name__}"

    ok = app.state.ready and all(v == "ok" for v in checks.values())
    if not ok:
        response.status_code = status.HTTP_503_SERVICE_UNAVAILABLE
    return {"status": "ready" if ok else "not_ready", "checks": checks}
```

```python
from fastapi.testclient import TestClient

from health import app

with TestClient(app) as c:
    print(c.get("/healthz").json())
    r = c.get("/readyz"); print(r.status_code, r.json())
    app.state.ready = False
    r = c.get("/readyz"); print(r.status_code, r.json())
```

```text
{'status': 'alive'}
200 {'status': 'ready', 'checks': {'database': 'ok'}}
503 {'status': 'not_ready', 'checks': {'database': 'ok'}}
```

`include_in_schema=False` 让健康检查端点不出现在 `/docs` 中。

## 5. Docker 镜像

### 5.1 最简版（pip + requirements.txt）

这是 FastAPI 官方文档的基本写法，项目结构为 `requirements.txt` + `app/main.py`：

```dockerfile
FROM python:3.14-slim

WORKDIR /code

# 先只复制依赖清单并安装：代码改动时，这一层可以命中缓存，不用重装依赖
COPY ./requirements.txt /code/requirements.txt
RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

COPY ./app /code/app

# exec 形式（JSON 数组）：进程是 PID 1，能直接收到 SIGTERM 实现优雅停机
CMD ["fastapi", "run", "app/main.py", "--port", "8000"]
```

### 5.2 推荐版（uv + 多阶段构建 + 非 root 用户）

项目使用 uv 管理依赖（`pyproject.toml` + `uv.lock`，见第 11 章）时：

```dockerfile
# ---------- 构建阶段：安装依赖 ----------
FROM python:3.14-slim AS builder

# 从官方镜像拷贝 uv 可执行文件（建议固定版本号）
COPY --from=ghcr.io/astral-sh/uv:0.12 /uv /uvx /bin/

ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_PYTHON_DOWNLOADS=0

WORKDIR /app

# 1) 只用锁文件安装第三方依赖（不含项目本身），这一层只在依赖变化时重建
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project --no-dev

# 2) 再复制源码并安装项目
COPY . /app
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-dev

# ---------- 运行阶段：只带运行所需的文件 ----------
FROM python:3.14-slim

RUN groupadd --system app && useradd --system --gid app --no-create-home app

WORKDIR /app
COPY --from=builder --chown=app:app /app /app

ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1

USER app
EXPOSE 8000

CMD ["fastapi", "run", "app/main.py", "--port", "8000", "--forwarded-allow-ips", "*"]
```

要点：

| 做法 | 原因 |
|---|---|
| 先复制依赖清单、安装依赖，再复制代码 | 利用 Docker 层缓存，改代码不必重装依赖，构建快很多 |
| 多阶段构建 | 最终镜像不包含 uv、编译工具和缓存，体积更小、攻击面更小 |
| `--mount=type=cache` | 依赖下载缓存跨构建复用（需要 BuildKit，新版 Docker 默认启用） |
| `--no-dev` | 不安装 pytest、ruff 等开发依赖 |
| 非 root 用户运行 | 即使应用被攻破，权限也受限 |
| `PYTHONUNBUFFERED=1` | 日志立即输出，不被缓冲 |
| **exec 形式的 CMD** | `CMD ["fastapi", "run", ...]` 让应用成为 PID 1，`docker stop` 发出的 SIGTERM 能直达应用触发优雅停机；shell 形式 `CMD fastapi run ...` 会被 `/bin/sh -c` 包一层，信号可能传不到，最后被 SIGKILL 强杀 |
| `--forwarded-allow-ips "*"` | 容器内应用前面的代理 IP 不固定；**只有当容器端口不直接暴露到公网时**才能这样信任全部来源 |

## 6. Docker Compose：应用 + PostgreSQL + Redis

```yaml
# compose.yaml
services:
  app:
    build: .
    image: myapp:latest
    ports:
      - "8000:8000"
    env_file: .env                        # SECRET_KEY 等敏感配置
    environment:
      DATABASE_URL: postgresql+psycopg://app:app_pwd@db:5432/app   # 主机名 = 服务名
      REDIS_URL: redis://redis:6379/0
    depends_on:
      db:
        condition: service_healthy        # 等数据库真正可用再启动
      redis:
        condition: service_started
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz')"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 10s
    restart: unless-stopped

  db:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app_pwd
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data   # 数据持久化，删容器不丢数据
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped

  redis:
    image: redis:8-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redisdata:/data
    restart: unless-stopped

volumes:
  pgdata:
  redisdata:
```

```bash
docker compose up -d --build     # 构建并后台启动
docker compose ps                # 查看状态（含健康检查结果）
docker compose logs -f app       # 跟踪应用日志
docker compose exec app alembic upgrade head   # 在容器里执行数据库迁移
docker compose down              # 停止并删除容器（数据卷保留）
```

> 💡 slim 镜像里没有 `curl`，所以健康检查用 Python 标准库 `urllib` 发请求。容器之间用**服务名**互相访问（`db`、`redis`），不要写 `localhost`——在容器里 `localhost` 指的是容器自己。

## 7. Nginx 反向代理与 root_path

生产环境通常在应用前面放一个反向代理（Nginx、Caddy、Traefik 或云厂商的负载均衡），负责：HTTPS 终止、静态文件、负载均衡、限制请求体大小、缓冲慢客户端等。

```nginx
# /etc/nginx/conf.d/fastapi.conf
upstream fastapi_app {
    server app:8000;               # docker compose 中的服务名；多实例可写多行 server
    keepalive 32;                  # 与后端保持长连接，减少握手开销
}

# WebSocket：有 Upgrade 头时 Connection 设为 upgrade，否则置空（以便复用 keepalive）
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      '';
}

server {
    listen 80;
    server_name api.example.com;
    return 301 https://$host$request_uri;          # HTTP 一律跳转 HTTPS
}

server {
    listen 443 ssl;
    http2 on;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    client_max_body_size 20m;                      # 上传文件大小上限，默认只有 1m

    # 应用挂在 /api 前缀下：/api/users -> 后端收到 /users
    location /api/ {
        proxy_pass http://fastapi_app/;            # 结尾的 / 会去掉匹配到的 /api/ 前缀
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket 升级
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        proxy_read_timeout 300s;                   # 长连接 / SSE 需要更长的读超时
    }

    # SSE / 流式接口单独关闭缓冲（EventSourceResponse 也会发 X-Accel-Buffering: no）
    location /api/sse/ {
        proxy_pass http://fastapi_app/sse/;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection        '';
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
    }
}
```

### 7.1 代理头：拿到真实的客户端 IP 和协议

经过代理后，应用看到的 TCP 对端是 Nginx，`request.client.host` 是 Nginx 的 IP，`request.url.scheme` 是 `http`。Nginx 通过 `X-Forwarded-For` / `X-Forwarded-Proto` 告诉应用真实信息，Uvicorn 的 `--proxy-headers` 负责解析它们——但**只信任 `--forwarded-allow-ips` 列表中的来源**，否则任何人都能伪造 `X-Forwarded-For`。

```python
# proxy_app.py
from fastapi import FastAPI, Request

app = FastAPI()


@app.get("/whoami", name="whoami")
def whoami(request: Request):
    return {
        "client_ip": request.client.host,             # 开启 proxy-headers 后取自 X-Forwarded-For
        "scheme": request.url.scheme,                 # 取自 X-Forwarded-Proto
        "root_path": request.scope.get("root_path"),
        "self_url": str(request.url_for("whoami")),   # 生成的链接会带上 root_path 前缀
    }
```

模拟代理发来的请求头：

```bash
# 不信任代理头
uvicorn proxy_app:app --root-path /api --no-proxy-headers
curl localhost:8000/whoami -H "X-Forwarded-For: 203.0.113.9" -H "X-Forwarded-Proto: https"
```

```text
{"client_ip":"127.0.0.1","scheme":"http","root_path":"/api","self_url":"http://localhost:8000/api/whoami"}
```

```bash
# 信任来自 127.0.0.1 的代理头
uvicorn proxy_app:app --root-path /api --proxy-headers --forwarded-allow-ips 127.0.0.1
curl localhost:8000/whoami -H "X-Forwarded-For: 203.0.113.9" -H "X-Forwarded-Proto: https"
```

```text
{"client_ip":"203.0.113.9","scheme":"https","root_path":"/api","self_url":"https://localhost:8000/api/whoami"}
```

如果 `scheme` 没有被正确识别为 `https`，`url_for` 生成的链接、重定向地址都会是 `http://`，在 HTTPS 页面中引发"混合内容"错误——这就是 `/docs` 在代理后面"打不开"的常见原因之一。

### 7.2 root_path：应用挂在子路径下

上面的 Nginx 配置把 `https://api.example.com/api/xxx` 转发为后端的 `/xxx`（前缀被去掉了）。应用自身的路由不需要改，但它需要知道"外部访问我时有个 `/api` 前缀"，否则 `/docs` 页面会去请求 `/openapi.json`（而外部正确的地址是 `/api/openapi.json`），结果 404。

解决办法是启动时传入 `--root-path /api`（或 `FastAPI(root_path="/api")`）：

```text
$ curl -s https://api.example.com/api/docs | grep -o "url: '[^']*'"
url: '/api/openapi.json'
$ curl -s https://api.example.com/api/openapi.json | jq .servers
[{"url": "/api"}]
```

| 场景 | 做法 |
|---|---|
| 代理**去掉**前缀再转发（`proxy_pass http://app/;` 结尾带 `/`） | 应用路由不变，启动加 `--root-path /api` |
| 代理**保留**前缀转发（`proxy_pass http://app;` 结尾不带 `/`） | 应用自己处理前缀：`app.include_router(router, prefix="/api")`，不要再设 `root_path` |
| 直接暴露在根路径 | 什么都不用做 |

## 8. HTTPS

HTTPS 几乎总是在**代理层**终止，应用本身跑 HTTP：

| 方案 | 说明 |
|---|---|
| Nginx + Certbot | `certbot --nginx -d api.example.com` 自动申请 Let's Encrypt 免费证书并配置续期 |
| Caddy | 配置里写上域名就**自动**申请和续期证书，配置最简单 |
| Traefik | 适合 Docker / K8s，按容器标签自动发现服务和申请证书 |
| 云负载均衡（ALB、SLB、CLB） | 在云控制台上传/申请证书，应用只需处理 HTTP |
| Uvicorn 直接提供 | `uvicorn main:app --ssl-keyfile key.pem --ssl-certfile cert.pem`，仅适合内网或测试 |

Caddy 的完整配置只有几行：

```text

}
```

## 9. 日志配置

生产环境的日志要能被日志平台（ELK、Loki、云日志服务）采集和检索，推荐**输出到标准输出、每行一条 JSON**。

### 9.1 应用日志：JSON 格式 + 请求 ID

```python
# logging_setup.py
import json
import logging
import logging.config
from datetime import datetime, timezone


class JsonFormatter(logging.Formatter):
    """把每条日志输出成一行 JSON，方便 ELK / Loki / 云日志平台检索。"""

    def format(self, record: logging.LogRecord) -> str:
        log = {
            "time": datetime.fromtimestamp(record.created, timezone.utc).isoformat(),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
        }
        # 通过 logger.info("...", extra={...}) 传入的自定义字段
        for key in ("request_id", "method", "path", "status", "duration_ms"):
            if hasattr(record, key):
                log[key] = getattr(record, key)
        if record.exc_info:
            log["exc_info"] = self.formatException(record.exc_info)
        return json.dumps(log, ensure_ascii=False)


LOGGING_CONFIG = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {"json": {"()": JsonFormatter}},
    "handlers": {
        "stdout": {"class": "logging.StreamHandler", "formatter": "json", "stream": "ext://sys.stdout"},
    },
    "loggers": {
        "app": {"handlers": ["stdout"], "level": "INFO", "propagate": False},
        "uvicorn": {"handlers": ["stdout"], "level": "INFO", "propagate": False},
        "uvicorn.error": {"level": "INFO"},
        "uvicorn.access": {"handlers": [], "level": "WARNING", "propagate": False},  # 用自己的访问日志替代
    },
}


def setup_logging() -> None:
    logging.config.dictConfig(LOGGING_CONFIG)
```

```python
# log_app.py
import logging
import time
import uuid

from fastapi import FastAPI, Request

from logging_setup import setup_logging

setup_logging()
logger = logging.getLogger("app")

app = FastAPI()


@app.middleware("http")
async def access_log(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:12]
    start = time.perf_counter()
    response = await call_next(request)
    duration_ms = round((time.perf_counter() - start) * 1000, 2)
    response.headers["X-Request-ID"] = request_id
    logger.info(
        "request finished",
        extra={
            "request_id": request_id,
            "method": request.method,
            "path": request.url.path,
            "status": response.status_code,
            "duration_ms": duration_ms,
        },
    )
    return response


@app.get("/orders/{order_id}")
async def get_order(order_id: int):
    logger.info("查询订单 %s", order_id)
    return {"order_id": order_id}
```

## 10. 性能优化

### 10.1 头号杀手：在 `async def` 里调用阻塞代码

回顾 12.1 节的规则：`async def` 端点直接运行在事件循环上，`def` 端点会被放进线程池执行。**事件循环是单线程的**，只要有一个 `async def` 端点执行了阻塞操作，整个进程的所有请求都会停下来等它。

```python
# blocking.py
import asyncio
import time

from fastapi import FastAPI

app = FastAPI()


@app.get("/bad")
async def bad():
    time.sleep(1)            # ❌ 同步阻塞调用写在 async def 里：卡住整个事件循环
    return {"endpoint": "bad"}


@app.get("/good-async")
async def good_async():
    await asyncio.sleep(1)   # ✅ 异步等待，事件循环可以去处理别的请求
    return {"endpoint": "good-async"}


@app.get("/good-sync")
def good_sync():
    time.sleep(1)            # ✅ 普通 def：FastAPI 放进线程池执行，不阻塞事件循环
    return {"endpoint": "good-sync"}


@app.get("/fixed")
async def fixed():
    await asyncio.to_thread(time.sleep, 1)   # ✅ 必须在 async 里调同步库时，丢到线程里
    return {"endpoint": "fixed"}
```

用一个小脚本并发打 10 个请求：

```python
# bench.py
import asyncio
import sys
import time

import httpx


async def main(path: str, n: int = 10) -> None:
    async with httpx.AsyncClient(base_url="http://127.0.0.1:8000", timeout=30) as client:
        start = time.perf_counter()
        await asyncio.gather(*(client.get(path) for _ in range(n)))
        print(f"{path:<12} 并发 {n} 个请求，总耗时 {time.perf_counter() - start:.2f}s")


for p in sys.argv[1:]:
    asyncio.run(main(p))
```

```bash
uvicorn blocking:app          # 终端 1
python bench.py /bad /good-async /good-sync /fixed   # 终端 2
```

```text
/bad         并发 10 个请求，总耗时 10.07s
/good-async  并发 10 个请求，总耗时 1.03s
/good-sync   并发 10 个请求，总耗时 1.04s
/fixed       并发 10 个请求，总耗时 1.03s
```

`/bad` 的 10 个请求被**串行**处理，耗时 10 秒；而且在这 10 秒里，其他任何接口（包括健康检查）也都无法响应。常见的"隐形"阻塞调用：

| 阻塞调用 | 异步替代 |
|---|---|
| `time.sleep()` | `await asyncio.sleep()` |
| `requests.get()` | `httpx.AsyncClient` / `aiohttp` |
| 同步数据库驱动（`psycopg2`、`pymysql`、同步 SQLAlchemy Session） | `asyncpg`、`psycopg` 异步模式、`aiomysql`、SQLAlchemy `AsyncSession`；或者端点改成 `def` |
| 同步 Redis 客户端 `redis.Redis` | `redis.asyncio.Redis` |
| 读写大文件 `open().read()` | `anyio` / `aiofiles`，或 `asyncio.to_thread` |
| CPU 密集计算（图像处理、加密、大 JSON 解析） | `asyncio.to_thread`（释放 GIL 的库）或进程池 / 任务队列（Celery、arq） |

**选择规则**：函数里用到的库全是异步的 → `async def`；只要有一个同步阻塞库 → 直接写 `def`，或者把阻塞部分 `await asyncio.to_thread(...)`。

### 10.2 `def` 端点与线程池大小

`def` 端点运行在 AnyIO 的线程池里，默认**最多 40 个线程**。同时进来 80 个慢请求时，后 40 个只能排队：

```python
# threadpool.py
import time
from contextlib import asynccontextmanager

import anyio.to_thread
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    limiter = anyio.to_thread.current_default_thread_limiter()
    print("默认线程池大小：", limiter.total_tokens)
    limiter.total_tokens = 100       # 按需调大（必须在事件循环内设置，lifespan 是合适的位置）
    print("调整后线程池大小：", limiter.total_tokens)
    yield


app = FastAPI(lifespan=lifespan)


@app.get("/sync")
def sync_endpoint():
    time.sleep(1)
    return {"ok": True}
```

```text
默认线程池大小： 40
调整后线程池大小： 100
```

并发 80 个请求打到一个耗时 1 秒的 `def` 端点：

| 线程池大小 | 总耗时 |
|---|---|
| 40（默认） | 约 2.2s（分两批执行） |
| 100 | 约 1.3s |

> ⚠️ 线程池不是越大越好：线程多了，内存和上下文切换开销增加，而且下游（数据库连接池）也要能承受同样多的并发。线程池大小应与数据库连接池大小一起规划。

### 10.3 响应序列化：声明返回类型

新版 FastAPI 在端点**声明了返回类型或 `response_model`** 时，会直接用 Pydantic（Rust 实现）把数据序列化成 JSON 字节；没有声明时，则走较慢的 `jsonable_encoder` + `json.dumps` 路径。

```python
# serialize.py
import time

from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    id: int
    name: str
    price: float
    tags: list[str]


ITEMS = [Item(id=i, name=f"item-{i}", price=i * 1.5, tags=["a", "b"]) for i in range(2000)]


@app.get("/items/no-type")
def items_no_type():                 # 没有返回类型：走 jsonable_encoder + json.dumps
    return ITEMS


@app.get("/items/typed")
def items_typed() -> list[Item]:     # 声明返回类型：Pydantic(Rust) 直接序列化成 JSON 字节
    return ITEMS


client = TestClient(app)
for url in ["/items/no-type", "/items/typed"]:
    client.get(url)                  # 预热
    start = time.perf_counter()
    for _ in range(50):
        client.get(url)
    print(f"{url:<16} 50 次请求耗时 {time.perf_counter() - start:.2f}s")
```

```text
/items/no-type   50 次请求耗时 0.80s
/items/typed     50 次请求耗时 0.07s
```

同样的数据，仅仅加了一个返回类型注解，序列化快了 10 倍以上。

> ⚠️ 老教程常推荐 `default_response_class=ORJSONResponse` 来加速 JSON 序列化。在新版 FastAPI 中 `ORJSONResponse` 和 `UJSONResponse` **已被标记为弃用**——声明返回类型后走的 Pydantic 序列化路径已经足够快，也不需要额外安装 orjson。

### 10.4 数据库连接池

每次请求都新建数据库连接（TCP 握手 + 认证）非常昂贵。SQLAlchemy 的 `Engine` 自带连接池，**全局只创建一次**，在 lifespan 结束时 `dispose()`：

```python
# pool.py
from sqlalchemy import create_engine
from sqlalchemy.ext.asyncio import create_async_engine

# 同步引擎（配合 def 端点）
engine = create_engine(
    "sqlite:///./pool_demo.db",   # 生产中换成 postgresql+psycopg://user:pwd@db:5432/app
    pool_size=10,           # 常驻连接数
    max_overflow=20,        # 高峰期最多再临时创建 20 个
    pool_timeout=30,        # 拿不到连接时最多等 30 秒，然后报错
    pool_recycle=1800,      # 连接用了 30 分钟就回收，避免被数据库/防火墙静默断开
    pool_pre_ping=True,     # 取连接前先 ping 一下，自动剔除坏连接
)

# 异步引擎（配合 async def 端点），参数含义相同
async_engine = create_async_engine(
    "sqlite+aiosqlite:///./pool_demo.db",  # 生产中换成 postgresql+asyncpg://...
    pool_size=10,
    max_overflow=20,
    pool_pre_ping=True,
)

print(engine.pool.status())
```

```text
Pool size: 10  Connections in pool: 0 Current Overflow: -10 Current Checked out connections: 0
```

容量估算：**每个进程**最多占用 `pool_size + max_overflow` 个连接。4 个 worker × 3 个容器 × 30 = 360 个连接，而 PostgreSQL 默认 `max_connections=100`！实例多时要么调小单进程连接池，要么在数据库前加 PgBouncer 连接池代理。

### 10.5 缓存：Redis

对读多写少、计算昂贵的数据，加一层缓存是性价比最高的优化。多进程/多实例部署时缓存必须放在 Redis 这样的共享存储里：

```python
# cache_app.py
import asyncio
import json
import os
from contextlib import asynccontextmanager
from typing import Annotated

import redis.asyncio as redis
from fastapi import Depends, FastAPI, Request

REDIS_URL = os.getenv("REDIS_URL", "redis://localhost:6379/0")


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.redis = redis.from_url(REDIS_URL, decode_responses=True)  # 自带连接池，全局复用
    yield
    await app.state.redis.aclose()


app = FastAPI(lifespan=lifespan)


def get_redis(request: Request) -> redis.Redis:
    return request.app.state.redis


RedisDep = Annotated[redis.Redis, Depends(get_redis)]


async def query_product_from_db(product_id: int) -> dict:
    await asyncio.sleep(0.5)                  # 模拟慢查询
    return {"id": product_id, "name": f"商品{product_id}", "price": 99.0}


@app.get("/products/{product_id}")
async def get_product(product_id: int, r: RedisDep):
    key = f"product:{product_id}"
    if (cached := await r.get(key)) is not None:
        return {"source": "cache", "data": json.loads(cached)}

    data = await query_product_from_db(product_id)
    await r.set(key, json.dumps(data, ensure_ascii=False), ex=60)   # 60 秒过期
    return {"source": "db", "data": data}
```

没有 Redis 也能跑通：用 `fakeredis` 通过依赖覆盖（12.13 节）替换掉真实连接：

> 💡 缓存的难点不在"存"，而在**失效**：数据更新时要删除对应的缓存键；对热点键要防止"缓存击穿"（大量请求同时穿透到数据库），可以用分布式锁或"逻辑过期 + 后台刷新"。

### 10.6 限流：slowapi

限流用来防止接口被刷（短信验证码、登录、昂贵的搜索接口）。`slowapi` 是 FastAPI 生态中常用的限流库（`pip install slowapi`）：

```python
# ratelimit_app.py
from fastapi import FastAPI, Request
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.errors import RateLimitExceeded
from slowapi.util import get_remote_address

# key_func 决定"按什么维度限流"：这里按客户端 IP；也可以按用户 ID / API Key
limiter = Limiter(key_func=get_remote_address)   # 多实例部署时加 storage_uri="redis://..."

app = FastAPI()
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)


@app.get("/sms/send")
@limiter.limit("3/minute")          # 装饰器顺序：limiter 在路由装饰器下面
async def send_sms(request: Request, phone: str):   # 必须显式声明 request 参数
    return {"sent_to": phone}
```

- 关注 **P95 / P99 延迟**和错误率，而不仅仅是平均值和 QPS。
- 压测机和被测服务不要在同一台机器上，否则互相抢 CPU。
- 压测时关闭访问日志（`--no-access-log`），或者至少别输出到终端。
- 用 `py-spy top --pid <PID>` 查看线上进程的热点函数，用 10.8 节的 `cProfile` 分析单个请求。

## 11. 生产环境检查清单

| 类别 | 检查项 |
|---|---|
| 启动 | 使用 `fastapi run` / `uvicorn` / `gunicorn`，**没有** `--reload`；CMD 使用 exec 形式 |
| 进程 | 虚拟机按 CPU 核数设置 workers；K8s 每容器单进程、通过副本扩容 |
| 配置 | 密钥、数据库地址通过环境变量注入（12.12 节 `pydantic-settings`），不进代码和镜像 |
| 安全 | `debug=False`；按需关闭文档 `FastAPI(docs_url=None, redoc_url=None, openapi_url=None)`；CORS 白名单不用 `*`；非 root 用户运行容器 |
| 代理 | 配置 `--forwarded-allow-ips`；子路径部署设置 `root_path`；Nginx 限制 `client_max_body_size` |
| HTTPS | 证书自动续期；HTTP 跳转 HTTPS |
| 健康检查 | 提供 liveness / readiness 端点，接入编排系统 |
| 优雅停机 | lifespan 中释放连接池；`--timeout-graceful-shutdown` / `graceful_timeout` 与编排系统的停止宽限期匹配 |
| 日志 | 输出到 stdout、JSON 格式、带请求 ID；不记录敏感信息 |
| 监控 | 错误追踪（Sentry）；指标（Prometheus：QPS、延迟、错误率）；链路追踪（OpenTelemetry） |
| 性能 | `async def` 中无阻塞调用；声明返回类型；数据库连接池容量规划；热点数据缓存；关键接口限流 |
| 数据库 | 迁移（Alembic）在发版流程中执行，而不是在应用启动时自动执行 |
| 依赖 | 锁定版本（`uv.lock` / `requirements.txt` 带版本号）；定期升级并扫描漏洞 |

## 常见坑

1. **生产环境开了 `--reload`**：浪费 CPU，代码变化时请求失败；`--reload` 与 `--workers` 也不能同时使用。
2. **容器里监听 `127.0.0.1`**：容器外无法访问。容器中必须监听 `0.0.0.0`（`fastapi run` 默认如此）。
3. **使用已弃用的 `uvicorn.workers.UvicornWorker`**：改用 `uvicorn-worker` 包的 `uvicorn_worker.UvicornWorker`。
4. **shell 形式的 CMD**：`CMD fastapi run main.py` 导致 SIGTERM 传不到应用，`docker stop` 要等 10 秒后强杀，lifespan 的清理代码不执行。
5. **`async def` 里调用 `requests`、`time.sleep`、同步数据库驱动**：整个进程的并发能力退化为 1。
6. **多进程下使用进程内状态**：内存缓存、计数器、WebSocket 连接表在每个 worker 中各有一份，行为"时好时坏"。
7. **代理后面拿不到真实 IP / 协议**：没有配置 `X-Forwarded-*` 头或 `--forwarded-allow-ips`，导致限流失效、`url_for` 生成 `http://` 链接。反过来，把 `--forwarded-allow-ips` 设为 `*` 同时又把端口直接暴露到公网，任何人都能伪造 IP。
8. **子路径部署 `/docs` 404**：忘了设置 `root_path`，文档页去请求了错误的 `/openapi.json`。
9. **数据库连接数爆掉**：没有按"进程数 × 实例数 × (pool_size + max_overflow)"估算连接总数。
10. **Nginx 缓冲导致 SSE / 流式输出"卡住后一次性出现"**：流式接口需要 `proxy_buffering off` 或 `X-Accel-Buffering: no`。
11. **健康检查里检查外部依赖导致连锁重启**：liveness 只检查进程本身，依赖检查放到 readiness。
12. **还在用 `ORJSONResponse` 提速**：新版 FastAPI 中已弃用，声明返回类型即可获得更快的序列化。

## 小结

- **启动方式**：开发用 `fastapi dev`，生产用 `fastapi run`（底层为 Uvicorn）；需要更强的进程管理时用 Gunicorn + `uvicorn_worker.UvicornWorker`；K8s 中每容器单进程。
- **容器化**：多阶段构建 + uv 锁定依赖 + 非 root 用户 + exec 形式 CMD + `.dockerignore`；用 Compose 编排应用、PostgreSQL 和 Redis，并配置健康检查与依赖顺序。
- **反向代理**：Nginx 负责 HTTPS、WebSocket 升级、SSE 关闭缓冲；应用通过 `--proxy-headers` + `--forwarded-allow-ips` 获取真实客户端信息，通过 `root_path` 适配子路径部署。
- **可观测性**：liveness / readiness 健康检查；JSON 结构化日志 + 请求 ID；统一 Uvicorn 日志格式。
- **性能**：首先消灭 `async def` 中的阻塞调用；按需调整线程池；声明返回类型加速序列化；规划数据库连接池；Redis 缓存热点数据；slowapi 限流；用 ab / hey / wrk / locust 测量，关注 P99。
