# 12.16 综合实战练习题

本节练习以 [`blog-api/`](./blog-api/) 为基础，**在现有代码上扩展**。每道扩展任务都有验收标准，统一要求：

- 完成后 `pytest` 全部通过（包括原有的 39 个测试）；
- 新功能必须配套新测试，至少覆盖「正常路径 + 一个错误路径 + 一个权限路径（如适用）」；
- 错误响应沿用项目的统一格式（`{"error": {...}, "request_id": ...}`），不要直接 `raise HTTPException`；
- `/docs` 中能看到新接口，且请求/响应模型正确。

建议先 `git` 提交一次原始代码，每完成一题提交一次，方便对比和回退。

## 一、代码阅读理解题

1. 在 `app/deps.py` 中，`get_current_user` 和 `get_post_or_404` 都依赖 `SessionDep`。在一次 `PATCH /posts/1` 请求中，`get_db` 会执行几次？如果执行了两次（两个不同的 Session），`create_post` 里的 `Post(author=current_user, ...)` 会出现什么问题？
2. 把 `get_own_post(user: CurrentUser, post: PostDep)` 的两个参数顺序对调，`test_update_order_401_before_404` 会怎样？为什么说「先 401 再 404」在安全上更合理？
3. `app/routers/posts.py` 的 `list_posts` 中，如果去掉两个 `selectinload`，接口返回结果会变吗？性能会怎样变化？请开启 `BLOG_DEBUG=true`（`echo=True`）后实际观察 SQL 日志，数一数请求 10 篇文章时分别执行了多少条 SQL。
4. `total` 是用 `select(func.count()).select_from(stmt.subquery())` 算出来的。为什么不直接写 `len(session.scalars(stmt).all())`？为什么必须在加 `offset`/`limit` **之前**计算？
5. `app/exceptions.py` 的 `http_exception_handler` 注册在 `starlette.exceptions.HTTPException` 上。如果改成注册在 `fastapi.HTTPException` 上，`GET /no-such-route` 的响应会变成什么样？哪个测试会失败？
6. `UserOut` 继承自 `UserPublic`。如果某天有人给 `UserPublic` 加了 `email` 字段，会造成什么后果？有什么手段（测试、代码审查约定）可以提前发现这类问题？
7. `PostUpdate` 的 `model_dump(exclude_unset=True, exclude_none=True)` 中，如果去掉 `exclude_none=True`，客户端发送 `{"title": null}` 会发生什么？最终返回给客户端的是什么状态码和响应体？
8. `tests/conftest.py` 为什么必须在 `from app.main import app` **之前**设置环境变量？如果把这两行挪到 import 之后，会发生什么？
9. 中间件 `request_context_middleware` 在 CORS 中间件的外层还是内层？如果对调两者顺序，浏览器端读取 `X-Request-ID` 会受影响吗？`expose_headers` 的作用是什么？
10. 注册和登录接口耗时约 50ms，其他接口只有几毫秒。原因是什么？在高并发登录场景下，这会对同步路由所在的线程池造成什么压力？

## 二、功能扩展任务

### ⭐ 基础

#### 1. 文章浏览量

- `Post` 增加 `view_count: int` 字段，默认 0；
- 每次 `GET /posts/{post_id}` 浏览量 +1，并在 `PostOut` 中返回；
- 用 `UPDATE posts SET view_count = view_count + 1` 的方式原子更新，而不是「读出来 +1 再写回」。

**验收标准**：连续请求同一篇文章 3 次，第 3 次返回 `view_count == 3`；思考并在代码注释中说明「读出来 +1 再写回」在并发下会丢失计数的原因。

#### 2. 列表排序参数

- `PostFilter` 增加 `sort` 参数，取值限定为枚举：`newest`（默认）、`oldest`、`most_viewed`、`most_commented`；
- 非法取值返回 422；
- `most_commented` 需要按评论数排序，用子查询或 `group_by` 实现，不能在 Python 里排序。

**验收标准**：每种排序各有一个测试；`?sort=foo` 返回 `VALIDATION_ERROR`。

#### 3. 用户文章列表

- 新增 `GET /users/{user_id}/posts`，返回该用户的文章，分页格式与 `/posts` 相同；
- 用户不存在返回 404；
- 复用现有的分页逻辑，**不要**复制粘贴 `list_posts` 的代码（提示：把查询构建抽成函数，或在 service 层实现）。

**验收标准**：用户不存在 → 404；有文章 → 正确分页；`/posts?author_id=` 与新接口返回的数据一致。

#### 4. 标签列表与热门标签

- `GET /tags`：返回所有标签及每个标签下的文章数，按文章数降序；
- 支持 `?limit=10` 只返回前 N 个；
- 没有任何文章的「孤儿标签」不返回。

**验收标准**：用一条 SQL 完成统计（`func.count` + `group_by`），在测试中构造 3 个标签、不同文章数验证顺序。

### ⭐⭐ 进阶

#### 5. 点赞

- 新建 `likes` 表（`user_id`、`post_id`、`created_at`），联合唯一约束保证同一用户对同一文章只能点赞一次；
- `POST /posts/{post_id}/like` 点赞，`DELETE /posts/{post_id}/like` 取消；重复点赞返回 409（或设计成幂等的 200，二选一并在文档中说明理由）；
- `PostOut` 增加 `like_count`；登录用户访问详情时额外返回 `liked_by_me: bool`，未登录时为 `false`。

**验收标准**：
- 未登录点赞 → 401；
- 点赞后 `like_count == 1`，取消后回到 0；
- 列表接口返回 `like_count` 时**不能产生 N+1**（提示：用子查询或 `column_property`）；
- `liked_by_me` 需要「可选登录」——没有 token 不报错。提示：`OAuth2PasswordBearer(tokenUrl=..., auto_error=False)`。

#### 6. 文章草稿与发布状态

- `Post` 增加 `status` 字段（枚举：`draft` / `published`），新建默认 `draft`；增加 `published_at`；
- `POST /posts/{post_id}/publish` 发布（仅作者），已发布再发布返回 409；
- `/posts` 列表只显示已发布文章；作者本人可以通过 `GET /users/me/posts?status=draft` 看到自己的草稿；
- 他人访问草稿详情返回 404（而不是 403，思考为什么）。

**验收标准**：覆盖「作者看草稿 / 他人看草稿 / 匿名看草稿 / 发布后公开可见」四种情况。

#### 7. 软删除

- `Post` 增加 `deleted_at: datetime | None`；`DELETE /posts/{id}` 改为设置 `deleted_at`，不真正删除；
- 所有查询自动排除已删除文章（列表、详情、评论列表、发评论）；
- 新增 `POST /posts/{id}/restore`，作者可在 7 天内恢复，超过 7 天返回 410 Gone（新增 `GoneError` 异常类）。

**验收标准**：
- 删除后列表和详情都查不到，但数据库里还有这一行；
- 恢复后重新可见；
- 「7 天」通过修改 `deleted_at` 来测试，不要真的等待；
- 思考：如何避免每个查询都手写 `.where(Post.deleted_at.is_(None))`？（提示：封装查询函数，或研究 SQLAlchemy 的 `with_loader_criteria`）

#### 8. 管理员角色

- `User` 增加 `role` 字段（`user` / `admin`）；
- 新增依赖 `require_admin`，非管理员返回 403；
- 管理员可以：删除任何文章和评论、`PATCH /admin/users/{id}` 禁用/启用用户；
- 被禁用的用户：已签发的 token 立刻失效（现有 `get_current_user` 已检查 `is_active`，请写测试确认），也不能登录；
- 不提供「注册成为管理员」的接口，写一个命令行脚本 `python -m app.scripts.create_admin` 创建管理员。

**验收标准**：普通用户访问 `/admin/*` → 403；管理员删除他人文章 → 204；被禁用用户用旧 token 访问 `/users/me` → 401。

#### 9. 刷新令牌

- 登录同时返回 `access_token`（15 分钟）和 `refresh_token`（7 天）；
- 两种 token 在 payload 中用 `type` 字段区分，`get_current_user` 必须拒绝 refresh token；
- `POST /auth/refresh` 用 refresh token 换取新的 access token；
- 进阶：实现 **refresh token 轮换**——每次刷新都返回新的 refresh token，旧的立即作废（需要在数据库中记录 refresh token 的 `jti`）。

**验收标准**：
- 用 refresh token 访问 `/users/me` → 401；
- 用 access token 调用 `/auth/refresh` → 401；
- 轮换模式下，同一个 refresh token 第二次使用 → 401。

#### 10. 头像上传

- `POST /users/me/avatar` 上传图片（`UploadFile`），只接受 `image/png`、`image/jpeg`，最大 2MB；
- 文件保存到配置项 `BLOG_UPLOAD_DIR` 指定的目录，文件名用 `uuid` 生成，**不要**使用客户端提供的文件名；
- 用 `StaticFiles` 挂载到 `/media`，`UserPublic` 增加 `avatar_url`；
- 测试中用 pytest 的 `tmp_path` fixture 作为上传目录。

**验收标准**：上传 PNG 成功并能通过 `/media/...` 访问；上传 3MB 文件 → 413 或 422；上传 `.txt` → 422；思考：为什么只检查 `content_type` 不够安全？

### ⭐⭐⭐ 挑战

#### 11. Alembic 数据库迁移

- 引入 Alembic，`env.py` 从 `app.core.config` 读取数据库地址、从 `app.db.Base.metadata` 读取模型；
- 生成初始迁移，删除 lifespan 中的 `create_all`；
- 为第 1 题的 `view_count` 字段单独生成一个迁移，验证 `alembic upgrade head` / `alembic downgrade -1` 都能正常工作；
- 测试仍然使用 `create_all`（为什么测试里这样做是可以接受的？）。

**验收标准**：在一个有数据的旧版数据库上执行 `alembic upgrade head` 后，旧数据完好、新字段有默认值。

#### 12. 异步化改造

- 把数据库层改为 `create_async_engine` + `AsyncSession`（SQLite 用 `aiosqlite`，PostgreSQL 用 `asyncpg`）；
- 所有路由和依赖改为 `async def`，查询改为 `await session.execute(...)` / `await session.scalars(...)`；
- 注意异步模式下**不能懒加载**：所有用到的关系都要显式 `selectinload`，或者设置 `lazy="raise"` 让遗漏的懒加载立即报错；
- 测试改用 `httpx.AsyncClient` + `ASGITransport` + `pytest-anyio`（或 `pytest-asyncio`）。

**验收标准**：
- 原有所有测试的断言不变，全部通过；
- 在模型上设置 `lazy="raise"` 后测试依然通过（证明没有遗漏的懒加载）；
- 写一段对比说明：本项目改成异步后，什么场景下性能会提升，什么场景下不会。

#### 13. Redis 缓存

- 缓存 `GET /posts/{id}` 的响应，TTL 60 秒，key 设计为 `post:{id}`；
- 修改、删除文章，新增、删除评论时**主动失效**对应缓存；
- Redis 客户端在 lifespan 中创建和关闭，通过依赖注入到路由；
- 测试中用 `fakeredis` 或 `dependency_overrides` 替换为内存实现。

**验收标准**：第二次请求不再查数据库（通过 SQL 计数或 mock 验证）；修改文章后立即请求能拿到新数据；Redis 不可用时接口降级为直接查库而不是 500。

#### 14. 评论实时推送

- 新增 `WebSocket /ws/posts/{post_id}`，客户端连接后，有人对该文章发表新评论时实时推送评论 JSON；
- 维护「文章 id → 连接集合」的连接管理器，连接断开时正确清理；
- 发表评论的 HTTP 接口在提交成功后触发广播。

**验收标准**：用 `TestClient.websocket_connect` 写测试：连接 → 另一个用户发表评论 → WebSocket 收到消息；思考：多进程部署（多个 worker）时这个方案为什么会失效？如何用 Redis Pub/Sub 解决？

#### 15. Docker 化部署

- 编写多阶段 `Dockerfile`：构建阶段用 uv 安装依赖，运行阶段使用 slim 镜像、非 root 用户，启动命令 `fastapi run app/main.py --port 8000`；
- 编写 `docker-compose.yml`：`api` + `postgres` + （可选）`redis`，`api` 通过环境变量 `BLOG_DATABASE_URL` 连接 PostgreSQL；
- 为 `api` 配置 `healthcheck`，使用 `/health` 接口；
- 镜像中不能包含 `.env`、`tests/`、`.venv/`（使用 `.dockerignore`）。

**验收标准**：`docker compose up` 后，按 用法.md 第 10 节的 curl 流程全部走通；`docker compose down && docker compose up` 后数据仍在（PostgreSQL 数据卷）。

## 三、综合实践：从博客到社区

在完成上面若干扩展的基础上，把项目升级为一个小型「技术社区」后端。要求：

1. **功能**：至少包含 草稿/发布（第 6 题）、点赞（第 5 题）、软删除（第 7 题）、管理员（第 8 题）、刷新令牌（第 9 题）；
2. **新增「关注」功能**：用户可以关注/取关其他用户（自关联多对多），`GET /feed` 返回我关注的人发布的文章，按时间倒序、游标分页（用 `?cursor=` 代替 `?page=`，思考游标分页相比偏移分页的优势）；
3. **通知**：被评论、被点赞、被关注时生成通知记录，使用 `BackgroundTasks` 异步写入，`GET /notifications` 查看、`POST /notifications/read` 标记已读；
4. **工程化**：
   - 引入 service 层，路由函数不直接写查询；
   - Alembic 管理所有表结构变更；
   - `ruff check`、`mypy app` 零报错；
   - 配置 GitHub Actions：push 时运行 lint、类型检查和测试；
5. **文档**：更新 `blog-api/README.md` 的接口一览表；为每个路由写好 `summary` 和 `description`，使 `/docs` 可以直接交给前端同事使用；
6. **测试**：整体测试覆盖率 ≥ 90%（`pytest --cov=app`）。

完成后回答：

- 你的 service 层是如何划分的？哪些逻辑留在了依赖里，哪些放进了 service，为什么？
- 如果访问量增长 100 倍，你会首先优化哪里？依据是什么（请用实际的测量数据说话，参考 12.15 节）？

## 四、参考检查点

- 能否说清楚一个请求从进入中间件、经过依赖链、到达路由、抛出异常、被处理器转换为统一错误格式的完整流程；
- 能否解释 `deps.py` 中依赖缓存、路径参数穿透、求值顺序三个机制，并据此设计新的「资源加载 + 权限」依赖；
- 能否正确区分 `XxxCreate` / `XxxUpdate` / `XxxOut` / `XxxPublic`，保证敏感字段永不泄露；
- 能否在新增列表接口时自觉使用 `selectinload` / 子查询避免 N+1，并用 SQL 日志验证；
- 能否正确实现 PATCH 语义（`exclude_unset`），并处理显式 `null` 的边界情况；
- 能否用 `dependency_overrides` + 内存数据库 + fixture 工厂为新功能快速写出隔离的测试；
- 能否根据实际负载在同步/异步数据库方案之间做出有依据的选择，且不在 `async def` 中调用阻塞代码；
- 能否把配置、密钥、数据库地址全部外置到环境变量，让同一份代码在开发、测试、生产环境中运行；
