# 12.3 请求体与 Pydantic 模型练习题

## 一、概念题

1. 当函数参数声明为 Pydantic 模型时，FastAPI 在调用函数之前依次完成了哪些工作？校验失败时客户端收到什么？
2. 请求体为空、请求体不是合法 JSON、请求体缺少某个必填字段、嵌套列表中某个元素的字段出错——这四种情况下 422 响应中的 `type` 和 `loc` 分别是什么样的？
3. Pydantic v2 中 `model_dump()`、`model_dump_json()`、`model_validate()`、`model_validate_json()`、`model_copy()` 分别做什么？它们在 v1 中对应的旧方法名是什么？
4. 金额字段为什么推荐用 `Decimal` 而不是 `float`？Pydantic v2 默认如何把 `Decimal` 序列化成 JSON？这会给前端带来什么影响？
5. `field_validator` 的 `mode="before"` 和 `mode="after"` 有什么区别？各举一个适合的场景。为什么校验器里应该抛 `ValueError` 而不是 `HTTPException`？
6. `model_validator(mode="after")` 产生的错误，`loc` 为什么只有 `["body"]`？如果某个字段本身就校验失败了，模型校验器还会运行吗？
7. `ConfigDict` 中 `extra` 的三个取值分别是什么效果？为什么对外接口推荐 `extra="forbid"`？
8. 函数有一个模型参数、两个模型参数、一个模型参数加 `Body(embed=True)` 时，客户端需要发送的 JSON 结构分别是什么样的？为什么说「从一个模型参数增加到两个」是破坏性变更？
9. 为什么要把「创建用的输入模型」「存储模型」「返回给客户端的模型」分开定义？用继承组织它们有什么好处？
10. 实现 PATCH 部分更新时，`model_dump()`、`model_dump(exclude_none=True)`、`model_dump(exclude_unset=True)` 三者的差别是什么？为什么 `exclude_unset` 是最合适的？

## 二、判断代码输出 / 找错

### 1. 必填与可选

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    name: str
    price: float
    description: str | None
    tags: list[str] = []


@app.post("/items")
async def create_item(item: Item):
    return item
```

请求体为 `{"name": "笔", "price": "3"}` 时，响应是什么？哪个字段的声明可能并不是作者的本意？

### 2. 校验器的 bug

```python
from pydantic import BaseModel, field_validator


class User(BaseModel):
    username: str
    age: int

    @field_validator("username")
    def strip_name(cls, v):
        v.strip()

    @field_validator("age")
    @classmethod
    def check_age(cls, v):
        if v < 0:
            raise HTTPException(status_code=400, detail="年龄不能为负数")
        return v
```

找出上面代码中的所有问题并改正。

### 3. 请求体到底长什么样

```python
from typing import Annotated

from fastapi import Body, FastAPI
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    name: str


@app.post("/a")
async def a(item: Item):
    return item


@app.post("/b")
async def b(item: Item, count: int):
    return {"item": item, "count": count}


@app.post("/c")
async def c(item: Item, count: Annotated[int, Body()]):
    return {"item": item, "count": count}


@app.post("/d")
async def d(item: Annotated[Item, Body(embed=True)]):
    return item
```

分别写出调用 `/a`、`/b`、`/c`、`/d` 时，客户端应该怎样传 `item` 和 `count`（路径、查询字符串、JSON 体分别是什么）。

### 4. 静默丢失的字段

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Settings(BaseModel):
    theme: str = "light"
    font_size: int = 14


@app.put("/settings")
async def save_settings(settings: Settings):
    return settings
```

前端发送 `{"theme": "dark", "fontSize": 18}`，返回 200，但字号没有生效。请解释原因，并给出两种改进方案（一种让问题能被及早发现，一种让接口兼容驼峰命名）。

### 5. PATCH 的错误实现

```python
@app.patch("/items/{item_id}")
async def patch_item(item_id: int, item_update: ItemUpdate) -> Item:
    stored = items[item_id]
    updated = stored.model_copy(update=item_update.model_dump())
    items[item_id] = updated
    return updated
```

`ItemUpdate` 所有字段都是 `X | None = None`。当客户端只发送 `{"price": 10}` 时会发生什么？如何修复？进一步思考：如果客户端发送 `{"name": null}`，而 `Item.name` 是必填的 `str`，修复后的代码会出现什么问题？如何让这种请求得到 422？

### 6. 时间范围校验

```python
from datetime import date

from pydantic import BaseModel, model_validator


class Range(BaseModel):
    start: date
    end: date

    @model_validator(mode="after")
    def check(self):
        if self.start > self.end:
            raise ValueError("start 不能晚于 end")
```

这段代码有什么问题？以下三种输入分别会得到什么结果（修复后）？

- `{"start": "2025-01-01", "end": "2025-02-01"}`
- `{"start": "2025-03-01", "end": "2025-02-01"}`
- `{"start": "2025-13-01", "end": "2025-02-01"}`

## 三、编程题

### 1. 图书录入

定义 `Book` 模型并实现 `POST /books`：

| 字段 | 规则 |
|---|---|
| `title` | 必填，1~100 字符，自动去除首尾空白 |
| `isbn` | 必填，匹配 `^\d{13}$` |
| `price` | `Decimal`，大于 0，最多 2 位小数 |
| `authors` | 至少 1 个作者的列表 |
| `published` | `date`，不能晚于今天（用 `field_validator` 实现） |
| `tags` | 可选，自动去重 |

为模型提供 `json_schema_extra` 示例，确保 `/docs` 中 “Try it out” 直接点击即可成功。

### 2. 嵌套订单

定义 `Address`、`OrderItem`、`Order` 三个模型：

- `Address`：省、市、详细地址、邮编（6 位数字）；
- `OrderItem`：商品 ID（正整数）、数量（1~99）、单价（`Decimal`）；
- `Order`：收货地址、商品列表（1~20 项）、备注（可选，最多 200 字）、`coupon_code`（可选）。

实现 `POST /orders`，返回订单总金额。构造一个让第 2 个商品数量为 0 的请求，确认 `loc` 为 `["body", "items", 1, "quantity"]`。

### 3. 用户注册

实现 `POST /register`：

- 字段：`username`（3~20 位，只允许字母数字下划线，统一转小写）、`email`（`EmailStr`）、`password`、`confirm_password`；
- 密码规则：至少 8 位，必须同时包含字母和数字（`field_validator`）；
- 两次密码一致（`model_validator`）；
- 开启 `extra="forbid"`；
- 返回的数据中不能包含任何密码字段——定义 `UserCreate`、`UserInDB`、`UserPublic` 三个模型，用继承减少重复。

### 4. 兼容多种输入格式

实现 `POST /events`，模型 `Event` 包含：

- `name: str`；
- `tags: list[str]`：客户端既可能传列表 `["a", "b"]`，也可能传逗号分隔的字符串 `"a,b"`，都要支持（`mode="before"`）；
- `happened_at: datetime`：支持 ISO 字符串和 Unix 时间戳，并在 `field_validator` 中统一转换为 UTC 时区；
- JSON 中字段名使用驼峰（`happenedAt`），Python 中使用下划线，同时也接受下划线写法。

### 5. 完整的 CRUD 与 PATCH

基于内存字典，为「联系人」资源实现：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/contacts` | 创建，返回 201 |
| GET | `/contacts/{id}` | 查询 |
| PUT | `/contacts/{id}` | 整体替换，所有字段必填 |
| PATCH | `/contacts/{id}` | 部分更新，只修改传入的字段，显式传 `null` 的可选字段要被清空 |

要求 PATCH 更新后的数据**重新经过完整模型校验**：例如必填字段 `name` 被设为 `null` 时返回 422。

## 四、综合实践：问卷提交接口

设计一个问卷系统的「提交答卷」接口 `POST /surveys/{survey_id}/responses`：

1. `survey_id` 为路径参数（UUID）；查询参数 `draft: bool = False` 表示是否为草稿；
2. 请求体包含两个模型：`respondent`（答题人：昵称、可选邮箱、年龄 1~120）和 `answers`（答案列表）；
3. 每个答案包含 `question_id`（正整数）、`type`（`Literal["single", "multiple", "text"]`）、`value`：
   - `single` 时 `value` 必须是单个字符串；
   - `multiple` 时 `value` 必须是 1~5 个不重复字符串的列表；
   - `text` 时 `value` 是 1~500 字的字符串；
   - 用 `model_validator` 实现上述「根据 type 校验 value」的规则；
4. 同一份答卷中 `question_id` 不能重复（在外层模型中校验）；
5. 非草稿提交时，答案数量不能少于 3 条；草稿不限制（提示：这条规则依赖查询参数，应该放在模型里还是接口函数里？想一想，并说明理由）；
6. 为请求体提供 `openapi_examples`，至少包含「完整提交」「草稿」「会触发 422 的错误示例」三个示例；
7. 列出至少 6 种错误请求，预测 422 响应的 `loc` 和 `type`，并逐一实际验证。

## 五、参考检查点

- 能否用 `BaseModel` + `Field` 准确描述请求数据，包括嵌套模型、容器类型和 `EmailStr`、`HttpUrl`、`UUID`、`datetime`、`Decimal` 等特殊类型；
- 能否熟练使用 Pydantic v2 的 `model_*` 系列方法，不再混用 v1 写法；
- 能否正确编写 `field_validator`（区分 before / after）和 `model_validator`，并理解它们的执行顺序与错误位置；
- 能否用 `ConfigDict` 控制多余字段、空白处理、别名等行为；
- 能否准确预测多个请求体参数、`Body()` 单值参数、`Body(embed=True)` 时的请求体结构；
- 能否把输入、存储、输出模型分开设计，避免敏感字段泄露；
- 能否用 `model_dump(exclude_unset=True)` 正确实现 PATCH，并在合并后重新校验；
- 能否为接口提供高质量的示例数据，让 `/docs` 开箱即用。
