# 12.10 中间件与CORS

12.7 的依赖注入可以给「某些路由」加上公共逻辑，12.6 的异常处理器可以统一错误格式。但还有一类需求是**和具体路由无关、每个请求都要经过**的：记录访问日志、统计耗时、生成请求 ID、压缩响应、限制来源域名、给前端开放跨域访问……这些就是**中间件（Middleware）**的工作。本节先讲清中间件的执行模型和三种写法，再重点讲前后端分离项目一定会遇到的 **CORS 跨域**，最后介绍几个内置中间件，并总结中间件、依赖、异常处理器三者如何选择。

> 本节示例在 FastAPI 0.143 / Starlette 1.8 下实测通过。

## 1. 中间件原理：洋葱模型

FastAPI 基于 ASGI 协议。一个 ASGI 应用本质上是一个 `async def app(scope, receive, send)` 的可调用对象，**中间件就是「包住另一个 ASGI 应用」的 ASGI 应用**。多个中间件层层包裹，形成洋葱结构：

```text
             请求 ──────────────────────────────▶
  ┌─────────────────────────────────────────────────┐
  │ ServerErrorMiddleware（最外层，兜底 500）          │
  │  ┌───────────────────────────────────────────┐  │
  │  │ 你的中间件 D（最后添加的）                    │  │
  │  │  ┌─────────────────────────────────────┐  │  │
  │  │  │ 你的中间件 C                           │  │  │
  │  │  │  ┌───────────────────────────────┐  │  │  │
  │  │  │  │ ExceptionMiddleware（处理       │  │  │  │
  │  │  │  │ HTTPException 等已注册异常）    │  │  │  │
  │  │  │  │  ┌─────────────────────────┐  │  │  │  │
  │  │  │  │  │ Router → 依赖 → 路由函数 │  │  │  │  │
  │  │  │  │  └─────────────────────────┘  │  │  │  │
  │  │  │  └───────────────────────────────┘  │  │  │
  │  │  └─────────────────────────────────────┘  │  │
  │  └───────────────────────────────────────────┘  │
  └─────────────────────────────────────────────────┘
             ◀────────────────────────────── 响应
```

每个中间件都可以：

1. 在请求**进入**内层之前做事（检查请求头、记录开始时间）；
2. 决定是否继续调用内层（例如鉴权失败直接返回，不再往里走）；
3. 在响应**返回**之后做事（加响应头、记录状态码和耗时）。

> 💡 注意框架自带的两层：`ServerErrorMiddleware` 在最外层，负责把未处理异常变成 500；`ExceptionMiddleware` 在**所有用户中间件的内层**，负责调用你用 `@app.exception_handler` 注册的处理器。这个位置关系决定了「中间件里抛的 `HTTPException` 不会被异常处理器接住」（见第 5 节）。

## 2. 最简写法：`@app.middleware("http")`

```python
import time

from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def add_process_time(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)  # 把请求交给内层（其他中间件 / 路由）
    elapsed = (time.perf_counter() - start) * 1000
    response.headers["X-Process-Time"] = f"{elapsed:.2f}ms"
    return response


@app.get("/")
async def index():
    return {"msg": "hello"}
```

- 中间件函数必须是 `async def`，接收 `request` 和 `call_next` 两个参数；
- `await call_next(request)` 之前的代码在请求阶段执行，之后的代码在响应阶段执行；
- 必须返回一个 `Response` 对象；
- 目前只支持 `"http"` 类型，WebSocket 请求不会经过它。

```bash
curl -i localhost:8000/
# HTTP/1.1 200 OK
# content-type: application/json
# x-process-time: 0.46ms
# {"msg":"hello"}
```

## 3. 实用示例：请求 ID + 访问日志

线上排查问题时，需要能把「某一次请求」的所有日志串起来。常见做法是给每个请求分配一个 ID，放进响应头返回给调用方，同时写进日志：

```python
import logging
import time
import uuid

from fastapi import FastAPI, Request

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
logger = logging.getLogger("access")

app = FastAPI()


@app.middleware("http")
async def add_process_time(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    elapsed = (time.perf_counter() - start) * 1000
    response.headers["X-Process-Time"] = f"{elapsed:.2f}ms"
    return response


@app.middleware("http")
async def request_id_and_log(request: Request, call_next):
    # 优先使用上游（网关、前端）传来的请求 ID，没有就生成一个
    request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex
    request.state.request_id = request_id  # 存到 request.state，路由里也能取到

    response = await call_next(request)

    response.headers["X-Request-ID"] = request_id
    logger.info(
        "%s %s %s -> %d",
        request_id[:8],
        request.method,
        request.url.path,
        response.status_code,
    )
    return response


@app.get("/items/{item_id}")
async def read_item(item_id: int, request: Request):
    return {"item_id": item_id, "request_id": request.state.request_id}
```

实测：

```bash
curl -i localhost:8000/items/1 -H 'X-Request-ID: abc12345-from-gateway'
# x-process-time: 0.46ms
# x-request-id: abc12345-from-gateway
# {"item_id":1,"request_id":"abc12345-from-gateway"}

curl -i localhost:8000/items/abc     # 参数校验失败
# HTTP/1.1 422 Unprocessable Content
# x-process-time: 0.21ms
# x-request-id: 0fe8aceb3a984dff9b733733c27c9e61
```

服务端日志：

```text
INFO abc12345 GET /items/1 -> 200
INFO 0fe8aceb GET /items/abc -> 422
INFO eea9a6ba GET /nope -> 404
```

几个要点：

- **`request.state`** 是请求级的「储物格」，中间件写入的值在依赖和路由里都能通过 `request.state.xxx` 读到，是中间件向下游传数据的标准方式。
- 422、404 这类由框架内部产生的响应**同样会经过中间件**，因为它们是在 `ExceptionMiddleware`（内层）中被转换成响应的。
- 生产环境中请求 ID 通常还会放进 `contextvars`，配合 logging 的 `Filter` 让每一行业务日志都自动带上它（参考 10.5 日志）。

## 4. 执行顺序：后添加的在外层

多个中间件的执行顺序是初学者最容易搞错的地方。下面用 2 个装饰器中间件 + 2 个 `add_middleware` 实测：

```python
from fastapi import FastAPI, Request
from starlette.middleware.base import BaseHTTPMiddleware

app = FastAPI()


class LogMiddleware(BaseHTTPMiddleware):
    def __init__(self, app, name: str):
        super().__init__(app)
        self.name = name

    async def dispatch(self, request: Request, call_next):
        print(f"{self.name} 进入")
        response = await call_next(request)
        print(f"{self.name} 离开")
        return response


@app.middleware("http")
async def middleware_a(request: Request, call_next):
    print("A 进入")
    response = await call_next(request)
    print("A 离开")
    return response


@app.middleware("http")
async def middleware_b(request: Request, call_next):
    print("B 进入")
    response = await call_next(request)
    print("B 离开")
    return response


app.add_middleware(LogMiddleware, name="C")
app.add_middleware(LogMiddleware, name="D")


@app.get("/")
async def index():
    print("  >>> 路由函数执行")
    return {"ok": True}
```

请求 `GET /` 的实测输出：

```text
D 进入
C 进入
B 进入
A 进入
  >>> 路由函数执行
A 离开
B 离开
C 离开
D 离开
```

规律：**按注册顺序 A → B → C → D，越晚注册越靠外层**，请求时最先执行，响应时最后执行。源码上，`add_middleware()` 每次都把中间件 `insert(0, ...)` 到列表最前面，而 `@app.middleware("http")` 内部也是调用 `add_middleware(BaseHTTPMiddleware, dispatch=func)`，所以两种写法遵循同一规则。

> ⚠️ 顺序有实际影响。例如 `CORSMiddleware` 应该**最后添加**（处于最外层），这样即使内层某个中间件直接返回了 401，响应也能带上 CORS 头，前端才能读到错误信息；否则浏览器只会报一个含糊的「CORS error」。

## 5. 中间件中的异常处理

### 5.1 不要在中间件里 `raise HTTPException`

```python
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse

app = FastAPI()


@app.middleware("http")
async def check_api_key(request: Request, call_next):
    if request.url.path.startswith("/admin") and request.headers.get("X-API-Key") != "secret":
        raise HTTPException(status_code=401, detail="缺少或错误的 API Key")  # ❌
    return await call_next(request)


@app.get("/admin")
async def admin():
    return {"msg": "welcome"}
```

实测结果：

```text
GET /admin                        → 500 Internal Server Error   （期望是 401！）
GET /admin  X-API-Key: secret     → 200 {"msg":"welcome"}
```

原因见第 1 节的图：处理 `HTTPException` 的 `ExceptionMiddleware` 在用户中间件**内层**，外层抛出的异常它看不到，最终被最外层的 `ServerErrorMiddleware` 当作未知错误变成 500。

正确做法是**直接返回响应**：

```python
@app.middleware("http")
async def check_api_key(request: Request, call_next):
    if request.url.path.startswith("/admin") and request.headers.get("X-API-Key") != "secret":
        return JSONResponse({"detail": "缺少或错误的 API Key"}, status_code=401)  # ✅
    return await call_next(request)
```

```text
GET /admin                        → 401 {"detail":"缺少或错误的 API Key"}
```

> 💡 其实这种「针对部分路由的鉴权」更适合写成**依赖**（12.7 / 12.8），可以利用 `HTTPException`、自动生成 OpenAPI 文档里的安全声明。中间件更适合真正全局、与业务无关的逻辑。

### 5.2 用中间件兜底未处理异常

路由中未捕获的异常会从 `call_next()` 中抛出，可以在中间件里统一捕获、记录日志并返回统一格式：

```python
@app.middleware("http")
async def catch_all(request: Request, call_next):
    try:
        return await call_next(request)
    except Exception as exc:
        print("中间件捕获到异常:", repr(exc))
        return JSONResponse({"detail": "服务器内部错误"}, status_code=500)


@app.get("/boom")
async def boom():
    1 / 0
```

```text
中间件捕获到异常: ZeroDivisionError('division by zero')
GET /boom → 500 {"detail":"服务器内部错误"}
```

> 💡 等价的更规范写法是 12.6 中的 `@app.exception_handler(Exception)`——注册给 `Exception` 或 500 的处理器会被交给最外层的 `ServerErrorMiddleware` 使用。

## 6. 类写法：`BaseHTTPMiddleware`

需要**配置参数**或**复用**时，把中间件写成继承 `BaseHTTPMiddleware` 的类，重写 `dispatch()` 方法，再用 `app.add_middleware()` 注册：

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse
from starlette.middleware.base import BaseHTTPMiddleware


class MaintenanceMiddleware(BaseHTTPMiddleware):
    """维护模式：除白名单路径外，全部返回 503"""

    def __init__(self, app, enabled: bool = False, allow_paths: tuple[str, ...] = ("/health",)):
        super().__init__(app)
        self.enabled = enabled
        self.allow_paths = allow_paths

    async def dispatch(self, request: Request, call_next):
        if self.enabled and request.url.path not in self.allow_paths:
            return JSONResponse({"detail": "系统维护中，请稍后再试"}, status_code=503)
        return await call_next(request)


app = FastAPI()
app.add_middleware(MaintenanceMiddleware, enabled=True)  # 关键字参数会传给 __init__


@app.get("/health")
async def health():
    return {"status": "ok"}


@app.get("/orders")
async def orders():
    return []
```

```text
GET /health → 200 {"status":"ok"}
GET /orders → 503 {"detail":"系统维护中，请稍后再试"}
```

`BaseHTTPMiddleware` 使用简单，但有一些**局限**：

| 局限 | 说明 |
|---|---|
| 额外开销 | 每个请求要额外创建任务和内存流来转发请求/响应，中间件层数多时有可感知的性能损耗 |
| `contextvars` 不向上传播 | 路由里 `ContextVar.set()` 的值，在 `call_next()` 返回后的中间件代码中**看不到**（实测仍是中间件自己设置的旧值）；中间件里设置的值向下传给路由则没问题 |
| 读写响应体麻烦 | `call_next()` 返回的是流式响应，想修改响应体必须自己迭代 `response.body_iterator` 再重新构造响应 |
| 只处理 HTTP | WebSocket 和 lifespan 事件直接透传 |

> 💡 中间件里可以 `await request.body()` 读取请求体，实测之后路由仍能正常读取（Starlette 会缓存已读取的内容）。但读取大请求体会把它整个载入内存，谨慎使用。

## 7. 纯 ASGI 中间件

当你在意性能、需要支持流式响应 / WebSocket、或想避开 `BaseHTTPMiddleware` 的局限时，可以直接按 ASGI 协议写中间件。它就是一个实现了 `__call__(scope, receive, send)` 的类：

```python
import time

from fastapi import FastAPI
from starlette.datastructures import MutableHeaders
from starlette.types import ASGIApp, Message, Receive, Scope, Send


class ProcessTimeMiddleware:
    """纯 ASGI 中间件：不依赖 BaseHTTPMiddleware，开销最小，支持流式响应"""

    def __init__(self, app: ASGIApp, header_name: str = "X-Process-Time") -> None:
        self.app = app
        self.header_name = header_name

    async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None:
        if scope["type"] != "http":  # websocket、lifespan 直接放行
            await self.app(scope, receive, send)
            return

        start = time.perf_counter()

        async def send_wrapper(message: Message) -> None:
            # 响应头随 http.response.start 消息发出，在这里修改
            if message["type"] == "http.response.start":
                elapsed = (time.perf_counter() - start) * 1000
                headers = MutableHeaders(scope=message)
                headers.append(self.header_name, f"{elapsed:.2f}ms")
            await send(message)

        await self.app(scope, receive, send_wrapper)


app = FastAPI()
app.add_middleware(ProcessTimeMiddleware, header_name="X-Elapsed")


@app.get("/")
async def index():
    return {"msg": "hello"}
```

```text
GET / → 200 {"msg":"hello"}   响应头 x-elapsed: 0.27ms
```

理解 ASGI 的三个参数：

| 参数 | 含义 |
|---|---|
| `scope` | 连接信息字典：`type`（http / websocket / lifespan）、`path`、`method`、`headers`…… |
| `receive` | 异步函数，调用它获取客户端发来的消息（如 `http.request` 请求体片段） |
| `send` | 异步函数，调用它向客户端发送消息：先发 `http.response.start`（状态码 + 响应头），再发一个或多个 `http.response.body` |

纯 ASGI 中间件的核心技巧就是**包装 `receive` / `send`**：包装 `send` 可以修改响应头、统计响应大小；包装 `receive` 可以检查或限制请求体。

三种写法对比：

| 写法 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| `@app.middleware("http")` | 最简单 | 无法传参、难复用 | 单个项目里的小逻辑 |
| `BaseHTTPMiddleware` 子类 | 可传参、可复用、API 友好 | 有性能开销和上述局限 | 一般业务中间件 |
| 纯 ASGI 中间件 | 性能最好、支持流式和 WebSocket | 要理解 ASGI 协议，代码更底层 | 通用库、高性能、流式场景 |

## 8. CORS 跨域

### 8.1 同源策略与 CORS

浏览器有一条安全规则——**同源策略**：一个页面的 JavaScript 只能读取**同源**接口的响应。「源」= **协议 + 域名 + 端口**，三者完全相同才算同源：

| 页面地址 | 请求地址 | 是否同源 |
|---|---|---|
| `http://localhost:5173` | `http://localhost:8000` | ❌ 端口不同 |
| `http://example.com` | `https://example.com` | ❌ 协议不同 |
| `https://www.example.com` | `https://api.example.com` | ❌ 域名不同 |
| `https://example.com/a` | `https://example.com/b` | ✅ 只是路径不同 |

前后端分离开发时，前端（Vite 默认 `5173`）请求后端（`8000`）就是跨域。**CORS（跨域资源共享）** 是一套 HTTP 头协议：服务端通过响应头告诉浏览器「我允许哪些源访问我」，浏览器据此决定是否把响应交给页面的 JS。

> ⚠️ 关键认知：**CORS 是浏览器的限制，不是服务端的防护**。用 curl、Postman、后端服务调用接口不受 CORS 影响。而且下面的实测会看到，对于不被允许的源，服务端**照样执行并返回了数据**，只是没带允许头，浏览器拒绝把结果给 JS。所以 CORS **不能替代鉴权**。

### 8.2 简单请求与预检请求

浏览器把跨域请求分为两类：

- **简单请求**：方法是 GET / HEAD / POST，且只带少数「安全」请求头，`Content-Type` 只能是 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded` 三者之一。浏览器直接发送，带上 `Origin` 头，再根据响应里的 `Access-Control-Allow-Origin` 决定是否放行。
- **预检请求（preflight）**：不满足上述条件的——例如 `Content-Type: application/json`、带 `Authorization` 头、使用 PUT/DELETE/PATCH——浏览器会**先**发一个 `OPTIONS` 请求询问服务端，得到允许后才发真正的请求。

```text
浏览器                                          服务端
  │ OPTIONS /items                                │
  │ Origin: http://localhost:5173                 │
  │ Access-Control-Request-Method: POST           │
  │ Access-Control-Request-Headers: content-type  │
  │ ─────────────────────────────────────────────▶│
  │                                               │
  │ 200                                           │
  │ Access-Control-Allow-Origin: http://localhost:5173
  │ Access-Control-Allow-Methods: GET, POST, ...  │
  │ Access-Control-Allow-Headers: ..., Content-Type
  │ Access-Control-Max-Age: 3600                  │
  │ ◀─────────────────────────────────────────────│
  │                                               │
  │ POST /items（真正的请求）                       │
  │ ─────────────────────────────────────────────▶│
```

`fetch(url, {method: "POST", headers: {"Content-Type": "application/json"}})` 就会触发预检——所以几乎所有前后端分离项目都要处理预检。

### 8.3 CORSMiddleware

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173", "https://www.example.com"],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
    expose_headers=["X-Total-Count"],
    max_age=3600,
)


@app.get("/items")
async def list_items():
    return [{"id": 1}]


@app.post("/items")
async def create_item(item: dict):
    return item
```

参数说明：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `allow_origins` | `()` | 允许的源列表，必须是完整的 `协议://域名:端口`，**不要带结尾斜杠**；`["*"]` 表示任意源 |
| `allow_origin_regex` | `None` | 用正则匹配源，如 `r"https://.*\.example\.com"` 允许所有子域名 |
| `allow_methods` | `("GET",)` | 允许的方法；注意默认**只有 GET**，`["*"]` 表示全部 |
| `allow_headers` | `()` | 允许前端携带的请求头；`Accept`、`Accept-Language`、`Content-Language`、`Content-Type` 总是被允许 |
| `allow_credentials` | `False` | 是否允许携带 Cookie / HTTP 认证信息；前端需要同时设置 `credentials: "include"` |
| `expose_headers` | `()` | 允许前端 JS 读取的**响应头**；默认 JS 只能读少数几个标准头，自定义的 `X-Total-Count` 必须在这里声明 |
| `max_age` | `600` | 预检结果的缓存秒数，期间同样的请求不再发预检 |
| `allow_private_network` | `False` | 是否响应「私有网络访问」预检（公网页面访问内网服务时） |

实测（用 TestClient 手动带上浏览器会发的头）：

```text
# ① 允许的源，简单请求
GET /items  Origin: http://localhost:5173
→ 200  access-control-allow-origin: http://localhost:5173
       access-control-allow-credentials: true
       access-control-expose-headers: X-Total-Count
       vary: Origin

# ② 不允许的源，简单请求 —— 注意：仍然 200，而且有响应体！
GET /items  Origin: http://evil.com
→ 200  （没有 access-control-allow-origin 头）  [{"id":1}]
       浏览器会拦截，JS 拿不到数据；但服务端代码已经执行了

# ③ 允许的源，预检
OPTIONS /items  Origin: http://localhost:5173
                Access-Control-Request-Method: POST
                Access-Control-Request-Headers: content-type,authorization
→ 200 "OK"  access-control-allow-origin: http://localhost:5173
            access-control-allow-methods: GET, POST, PUT, DELETE
            access-control-allow-headers: Accept, Accept-Language, Authorization, Content-Language, Content-Type
            access-control-max-age: 3600

# ④ 预检方法不允许
OPTIONS /items  Origin: http://localhost:5173  Access-Control-Request-Method: PATCH
→ 400 Disallowed CORS method

# ⑤ 预检源不允许
OPTIONS /items  Origin: http://evil.com  Access-Control-Request-Method: POST
→ 400 Disallowed CORS origin
```

> 💡 预检请求由 `CORSMiddleware` 直接响应，**不会进入路由**，所以不需要你为每个接口写 `OPTIONS` 方法。没有 `Origin` 头的普通 `OPTIONS` 请求不是预检，会正常进入路由（上例中返回 405）。

### 8.4 `allow_credentials=True` 与 `"*"` 的冲突

CORS 规范规定：**携带凭证（Cookie）的请求，响应的 `Access-Control-Allow-Origin` 不能是 `*`**，必须是具体的源，否则浏览器拒绝。那 `allow_origins=["*"]` + `allow_credentials=True` 时 Starlette 怎么办？实测：

```text
allow_origins=["*"], allow_credentials=False
GET /  Origin: http://evil.com → access-control-allow-origin: *

allow_origins=["*"], allow_credentials=True
GET /  Origin: http://evil.com → access-control-allow-origin: http://evil.com
                                 access-control-allow-credentials: true
```

Starlette 为了「能用」，会**原样回显请求的 Origin**。这意味着**任何网站**都能带着用户的 Cookie 调用你的接口并读取结果——这正是 CORS 想防止的 CSRF 式数据窃取。

> ⚠️ 结论：**生产环境中只要 `allow_credentials=True`，就必须列出明确的源**（或用严格的 `allow_origin_regex`），绝不能用 `"*"`。`["*"]` 只适合完全公开、不依赖 Cookie 的只读 API。

### 8.5 推荐配置

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

# 通常从配置读取（见 12.12），不同环境不同值
ALLOWED_ORIGINS = [
    "http://localhost:5173",   # 本地前端
    "https://www.example.com", # 线上前端
]

# ...其他中间件先添加...

app.add_middleware(  # CORS 最后添加 → 位于最外层
    CORSMiddleware,
    allow_origins=ALLOWED_ORIGINS,
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

> 💡 另一种思路是**根本不跨域**：开发时用 Vite 的 `server.proxy` 把 `/api` 代理到后端，生产环境用 Nginx 把前端和 `/api` 放在同一个域名下。同源之后就不需要 CORS 了。

## 9. 其他内置中间件

```python
from fastapi import FastAPI
from fastapi.middleware.gzip import GZipMiddleware
from fastapi.middleware.httpsredirect import HTTPSRedirectMiddleware
from fastapi.middleware.trustedhost import TrustedHostMiddleware

app = FastAPI()

# 响应体超过 1000 字节且客户端支持 gzip 时才压缩
app.add_middleware(GZipMiddleware, minimum_size=1000, compresslevel=5)
# 只接受这些 Host 头的请求，防御 Host 头攻击
app.add_middleware(TrustedHostMiddleware, allowed_hosts=["example.com", "*.example.com"])


@app.get("/small")
async def small():
    return {"msg": "hi"}


@app.get("/big")
async def big():
    return {"data": "x" * 5000}


redirect_app = FastAPI()
redirect_app.add_middleware(HTTPSRedirectMiddleware)  # http → https，ws → wss


@redirect_app.get("/")
async def index():
    return {"secure": True}
```

实测：

```text
GET http://api.example.com/small → 200，无 content-encoding（12 字节，小于阈值不压缩）
GET http://api.example.com/big   → 200，content-encoding: gzip，content-length: 55（原始 5011 字节）
GET http://evil.com/small        → 400 Invalid host header
GET http://example.com/small     → 200（"*.example.com" 不匹配裸域名，所以要单独列出 example.com）
GET http://testserver/  (redirect_app) → 307，location: https://testserver/
```

| 中间件 | 作用 | 常用参数 |
|---|---|---|
| `GZipMiddleware` | 客户端请求头含 `Accept-Encoding: gzip` 时压缩响应 | `minimum_size`（默认 500 字节）、`compresslevel`（1~9，默认 9）；默认跳过 `text/event-stream` 等不适合压缩的类型 |
| `TrustedHostMiddleware` | 校验 `Host` 头，不在白名单返回 400 | `allowed_hosts`，支持 `*.example.com` 通配子域名 |
| `HTTPSRedirectMiddleware` | 把 http / ws 请求 307 重定向到 https / wss | 无 |

> 💡 实际部署中，压缩、HTTPS 跳转常由 Nginx / 云负载均衡完成，应用层不必重复做（见 12.15）。另外 Starlette 还提供 `SessionMiddleware`（基于签名 Cookie 的会话，需要安装 `itsdangerous`），以及大量第三方中间件（限流、Prometheus 指标、OpenTelemetry 链路追踪等）。

## 10. 中间件、依赖、异常处理器怎么选

| 需求 | 推荐方式 | 理由 |
|---|---|---|
| 所有请求的访问日志、耗时、请求 ID | 中间件 | 与路由无关，所有请求（包括 404、422）都要经过 |
| CORS、GZip、Host 校验 | 内置中间件 | 现成、标准 |
| 鉴权、获取当前用户 | 依赖（12.7 / 12.8） | 需要按路由区分；能 `raise HTTPException`；能出现在 OpenAPI 文档中；测试可 `dependency_overrides` |
| 数据库 Session | 依赖（yield） | 只有需要的路由才创建连接 |
| 参数预处理、分页参数复用 | 依赖 | 能利用 FastAPI 的参数解析和校验 |
| 统一错误响应格式 | 异常处理器（12.6） | 专门为此设计，可以按异常类型分别处理 |
| 未知异常兜底 | 异常处理器 `Exception` / 中间件 try-except | 两者都可以，前者更规范 |
| 修改所有响应头 | 中间件 | 能拿到最终响应 |
| 需要访问路由解析后的参数（如 `item_id`） | 依赖 | 中间件运行在路由匹配之前，拿不到解析好的参数 |

一句话总结：**与业务无关、对所有请求一视同仁的用中间件；与业务相关、按路由区分的用依赖；把异常变成响应的用异常处理器。**

## 常见坑

1. **在中间件里 `raise HTTPException`**：异常处理器在中间件内层接不到，结果变成 500。中间件里要直接 `return JSONResponse(...)`。
2. **搞反中间件顺序**：后添加的在外层。`CORSMiddleware` 不在最外层时，被内层中间件拦截的响应没有 CORS 头，前端只看到「CORS error」而看不到真正的错误。
3. **以为 CORS 能保护接口**：不被允许的源请求照样会执行业务逻辑，CORS 只限制浏览器 JS 读取结果。防护要靠鉴权、CSRF Token 等。
4. **`allow_origins=["*"]` + `allow_credentials=True`**：Starlette 会回显任意 Origin，等于对所有网站开放带 Cookie 的访问。
5. **源写错格式**：`"http://localhost:5173/"`（多了斜杠）、漏写端口、`http` 和 `https` 混淆，都会导致匹配失败。
6. **忘记 `allow_methods` 默认只有 GET**：前端 POST/PUT 的预检返回 400 `Disallowed CORS method`。
7. **自定义响应头前端读不到**：没有在 `expose_headers` 中声明。
8. **中间件里做重活**：中间件对每个请求都执行，在里面查数据库、调用外部服务会拖慢所有接口；需要时用依赖按需执行。
9. **在 `async def` 中间件里调用阻塞函数**：和 `async def` 路由一样会阻塞事件循环。
10. **在中间件里读取请求体**：会把整个请求体读入内存，大文件上传时要特别小心。

## 小结

- 中间件是包裹整个应用的 ASGI 层，按**洋葱模型**执行：请求由外向内，响应由内向外；**后添加的中间件在外层**。
- 三种写法：`@app.middleware("http")` 最简单；`BaseHTTPMiddleware` 子类可传参复用，但有性能开销和 `contextvars` 等局限；纯 ASGI 中间件性能最好、支持流式和 WebSocket。
- 中间件向下游传数据用 `request.state`；中间件中拒绝请求要 `return` 响应而不是 `raise HTTPException`。
- CORS 是浏览器的同源策略放行机制：简单请求直接发，非简单请求先发 `OPTIONS` 预检；`CORSMiddleware` 统一处理，要放在最外层。
- `allow_credentials=True` 时必须列出明确的源；自定义响应头要用 `expose_headers` 暴露。
- `GZipMiddleware`、`TrustedHostMiddleware`、`HTTPSRedirectMiddleware` 开箱即用，但很多时候由网关层承担更合适。
- 全局、与业务无关 → 中间件；按路由、与业务相关 → 依赖；异常转响应 → 异常处理器。
