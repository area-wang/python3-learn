# 12.11 后台任务与生命周期练习题

## 一、概念题

1. `BackgroundTasks` 中的任务在什么时刻开始执行？客户端是否需要等待任务完成才能收到响应？
2. 一个请求中添加了多个后台任务，它们是并发执行还是串行执行？依赖中添加的任务和路由中添加的任务是什么关系？
3. 后台任务函数分别是 `def` 和 `async def` 时，FastAPI 如何执行它们？各自需要注意什么？
4. 后台任务抛出异常时，客户端会收到什么？同一请求中排在它后面的任务还会执行吗？
5. 为什么不应该把 yield 依赖提供的数据库 Session 直接传给后台任务？正确做法是什么？
6. lifespan 函数中 `yield` 之前和之后的代码分别在什么时候执行？启动阶段抛异常会发生什么？
7. `app.state` 与「lifespan yield 字典 → `request.state`」两种共享资源的方式有什么区别？后者是深拷贝还是浅拷贝，会带来什么影响？
8. `@app.on_event("startup")` 在当前版本中是什么状态？它和 `lifespan` 同时使用时会发生什么？
9. 在 `async def` 路由中调用 `time.sleep(1)` 或 `requests.get()` 为什么会拖慢整个服务？`run_in_threadpool`、`anyio.to_thread.run_sync`、`asyncio.to_thread` 有什么区别和联系？
10. 什么样的任务应该从 `BackgroundTasks` 升级到 Celery / ARQ 等任务队列？请至少给出三个判断标准。

## 二、判断代码输出 / 找错

### 1. 执行顺序

```python
from fastapi import BackgroundTasks, Depends, FastAPI

app = FastAPI()


def log(msg: str):
    print(msg)


def dep(background_tasks: BackgroundTasks):
    background_tasks.add_task(log, "依赖中的任务")


@app.get("/", dependencies=[Depends(dep)])
def index(background_tasks: BackgroundTasks):
    background_tasks.add_task(log, "路由中的任务")
    print("路由函数")
    return {"ok": True}
```

## 三、编程题

### 1. 注册通知（基础）

实现 `POST /users`：

- 创建用户后立即返回 201；
- 用后台任务「发送欢迎邮件」（`time.sleep(2)` 模拟）和「写入审计日志」（追加写入 `audit.log` 文件）；
- 邮件任务内部捕获异常并用 `logging` 记录；
- 用 uvicorn 启动，用 httpx 计时验证客户端不需要等待 2 秒。

### 2. 资源生命周期（基础）

用 lifespan 管理以下资源：

- 一个全局的 `httpx.AsyncClient`（启动时创建，关闭时 `aclose()`）；
- 一个从 JSON 文件加载的「敏感词列表」；
- 编写依赖 `get_http_client` 和 `get_sensitive_words`，路由通过依赖获取它们；
- 用 `with TestClient(app)` 编写测试，验证启动和关闭逻辑各执行了一次。

### 3. 两种 state 写法对比（进阶）

把上一题分别用 `app.state` 和「yield 字典 + `TypedDict`」两种方式实现，并编写实验验证：

- yield 字典的值是否出现在 `app.state` 上；
- 在一个请求中给 `request.state` 重新赋值，另一个请求是否能看到；
- 在一个请求中修改 state 中的可变对象（如列表 `append`），另一个请求是否能看到。

### 4. 阻塞代码改造（进阶）

给定一个只有同步 API 的「第三方 SDK」：

```python
def sdk_query(keyword: str) -> list[str]:
    time.sleep(1)
    return [f"{keyword}-{i}" for i in range(3)]
```

- 分别实现 `async def` 直接调用、`def` 路由、`run_in_threadpool`、`asyncio.to_thread` 四个版本的接口；
- 编写并发压测脚本（10 个并发请求），记录各版本总耗时；
- 在 lifespan 中把线程池上限改为 5，重新压测 `def` 路由版本，解释结果变化。

### 5. 带状态的任务（进阶）

不引入任务队列，用 `BackgroundTasks` + 内存字典实现一个「导出任务」：

- `POST /exports` 返回 202 和 `task_id`，后台任务分 5 步执行（每步 1 秒），每步更新进度；
- `GET /exports/{task_id}` 返回 `{"status": "running", "progress": 60}` 或 `{"status": "done", "file": "..."}`；
- 任务失败时状态变为 `failed` 并记录错误信息；
- 思考并写下：这个实现在服务重启、多 worker 部署时分别会出现什么问题？如果换成 Celery，哪些问题可以解决？

### 6. 定时清理（挑战）

使用 APScheduler（3.x）在 lifespan 中启动调度器：

- 每 10 秒清理一次内存中已过期的验证码（验证码 60 秒有效）；
- 提供 `GET /jobs` 查看任务及下次执行时间，`POST /jobs/{job_id}/pause` 和 `/resume` 暂停、恢复任务；
- 关闭时正确 `shutdown()` 调度器；
- 用 `uvicorn --workers 2` 启动，观察清理任务的日志，说明出现了什么问题并提出解决方案。

## 四、综合实践：图片处理服务

实现一个简易图片处理服务，综合运用本节内容：

1. lifespan 中：创建上传目录、初始化 SQLite 数据库引擎（参考 12.9）、加载一个「水印配置」，关闭时 `engine.dispose()`；
2. `POST /images`：接收上传的图片（参考 12.4），保存原图后立即返回 202 和图片 ID；
3. 后台任务生成缩略图（可用 Pillow，或用 `time.sleep` 模拟），任务内部自建数据库 Session，完成后更新状态为 `done`，失败时更新为 `failed` 并记录原因；
4. `GET /images/{id}` 查询处理状态；
5. 图片处理属于 CPU 密集型操作——比较在后台任务中直接处理、`run_in_threadpool`、`ProcessPoolExecutor` 三种方式对其他接口响应时间的影响；
6. 用 APScheduler 每天清理 7 天前的原图；
7. 写一段说明：如果日均处理量从 1000 张增长到 100 万张，这套架构需要做哪些改造。
