# 12.11 后台任务与生命周期

到目前为止，所有代码都发生在「一次请求」之内：请求进来、处理、返回。但真实的服务还有两类请求之外的工作：

- **请求之后**：用户注册成功后要发欢迎邮件，下单后要写审计日志——用户不需要等这些做完才看到结果。
- **请求之前和服务停止时**：服务启动时要加载机器学习模型、创建数据库连接池、初始化 HTTP 客户端；停止时要关闭它们、释放资源。

本节分别用 **BackgroundTasks** 和 **lifespan** 解决这两类问题，并讨论 `async def` 里遇到阻塞代码怎么办、什么时候应该升级到 Celery 这类专业任务队列、定时任务如何实现。

> 本节示例在 FastAPI 0.143 / Starlette 1.8 / APScheduler 3.11 下实测通过。

## 1. BackgroundTasks：响应之后再执行

### 1.1 基本用法

在路由参数中声明一个 `BackgroundTasks` 类型的参数（FastAPI 会自动注入，不需要 `Depends`），然后用 `add_task(函数, *args, **kwargs)` 注册任务：

```python
import time
from datetime import datetime
from typing import Annotated

from fastapi import BackgroundTasks, Depends, FastAPI

app = FastAPI()


def now() -> str:
    return datetime.now().strftime("%H:%M:%S.%f")[:-3]


def send_email(to: str, subject: str) -> None:
    """模拟发送邮件：同步函数，会被放到线程池执行"""
    print(f"[{now()}] 开始给 {to} 发邮件：{subject}")
    time.sleep(2)  # 模拟耗时的 SMTP 调用
    print(f"[{now()}] 邮件发送完成")


async def write_audit_log(message: str) -> None:
    """异步函数也可以作为后台任务"""
    print(f"[{now()}] 审计日志：{message}")


def audit(background_tasks: BackgroundTasks, username: str = "guest"):
    # 依赖里也可以添加后台任务，和路由里拿到的是同一个 BackgroundTasks 对象
    background_tasks.add_task(write_audit_log, f"{username} 访问了注册接口")
    return username


@app.post("/register")
def register(
    email: str,
    background_tasks: BackgroundTasks,
    username: Annotated[str, Depends(audit)],
):
    print(f"[{now()}] 处理注册：{email}")
    background_tasks.add_task(send_email, email, subject="欢迎注册")
    print(f"[{now()}] 返回响应")
    return {"msg": "注册成功，欢迎邮件稍后送达", "user": username}
```

用 `uvicorn main:app` 启动，再用 httpx 请求并计时：

```python
import time
from datetime import datetime

import httpx

start = time.perf_counter()
r = httpx.post("http://127.0.0.1:8000/register", params={"email": "a@b.com", "username": "alice"})
print(f"[{datetime.now():%H:%M:%S.%f}] 客户端收到响应，耗时 {time.perf_counter() - start:.2f}s", r.json())
```

实测输出：

```text
# 客户端
[11:12:29.120] 客户端收到响应，耗时 0.08s {'msg': '注册成功，欢迎邮件稍后送达', 'user': 'alice'}

# 服务端
[11:12:29.117] 处理注册：a@b.com
[11:12:29.117] 返回响应
INFO:     127.0.0.1:58794 - "POST /register?email=a%40b.com&username=alice HTTP/1.1" 200 OK
[11:12:29.118] 审计日志：alice 访问了注册接口
[11:12:29.118] 开始给 a@b.com 发邮件：欢迎注册
[11:12:31.123] 邮件发送完成
```

从时间戳可以看出：

1. 客户端 **0.08 秒**就拿到了响应，不用等 2 秒的邮件发送；
2. 后台任务在**响应发送完成之后**才开始执行（访问日志 `200 OK` 先打印）；
3. 多个任务按 `add_task` 的**添加顺序依次串行执行**——依赖 `audit` 先执行，所以审计日志任务排在前面；
4. 依赖和路由中声明的 `BackgroundTasks` 是**同一个对象**，任务会合并到一起。

### 1.2 同步任务与异步任务

| 任务函数 | 执行方式 | 注意 |
|---|---|---|
| `def` 普通函数 | 放到线程池执行，不阻塞事件循环 | 可以放心调用 `time.sleep`、`requests` 等阻塞代码 |
| `async def` 协程函数 | 直接在事件循环中 `await` | 里面**不能**有阻塞调用，否则会卡住整个服务 |

这与路由函数的规则完全一致（见 12.1）。

### 1.3 后台任务出错会怎样

```python
from fastapi import BackgroundTasks, FastAPI

app = FastAPI()


def task_ok(n: int) -> None:
    print(f"任务 {n} 完成")


def task_fail() -> None:
    raise RuntimeError("后台任务出错")


@app.post("/jobs")
def create_job(background_tasks: BackgroundTasks):
    background_tasks.add_task(task_ok, 1)
    background_tasks.add_task(task_fail)
    background_tasks.add_task(task_ok, 3)  # 前一个任务抛异常后，它还会执行吗？
    return {"msg": "已提交"}
```

实测：

```text
任务 1 完成
POST /jobs → 200 {"msg":"已提交"}      ← 客户端照样收到成功
（服务端日志打印 RuntimeError 的完整堆栈）
                                       ← "任务 3 完成" 没有出现！
```

结论：

- 响应已经发出去了，后台任务的失败**客户端无从得知**；
- 一个任务抛出异常后，**排在后面的任务不再执行**；
- 异常只会出现在服务端日志里，没有重试机制。

所以后台任务内部要**自己捕获并记录异常**：

```python
import logging

logger = logging.getLogger(__name__)


def send_email_safe(to: str, subject: str) -> None:
    try:
        send_email(to, subject)
    except Exception:
        logger.exception("发送邮件失败 to=%s", to)  # 记录堆栈，必要时写入失败表以便补偿
```

### 1.4 使用后台任务的注意事项

- **不要把请求级资源传给后台任务**。例如 12.9 中通过 yield 依赖得到的 `Session`：实测在默认情况下，后台任务在 yield 依赖退出**之前**执行，所以「碰巧能用」；但如果依赖声明了 `scope="function"`（如 12.9 的事务依赖），依赖在响应发送前就已退出，事务已提交、Session 已关闭。让代码的正确性依赖这种执行顺序细节非常脆弱。后台任务应该**自己创建**需要的资源（`with SessionLocal() as session:`），参数只传 id 这类简单值。
- **测试时 TestClient 会等待后台任务结束**才返回（实测上面的注册接口用 TestClient 调用耗时 2.03 秒），这方便断言任务的效果，但不代表线上客户端也要等。
- **后台任务和服务进程同生共死**：进程重启或崩溃时，还没执行完的任务直接丢失。

> 💡 `BackgroundTasks` 适合「**轻量、快速、丢了也能接受**」的工作：发通知、写日志、清理临时文件、刷新缓存。重要且耗时的任务请看第 4 节的任务队列。

## 2. lifespan：应用的启动与关闭

### 2.1 为什么需要 lifespan

有些资源应该**整个应用只创建一次**，并在所有请求之间共享：

- 加载机器学习模型（几百 MB，每个请求加载一次显然不行）；
- 数据库引擎 / 连接池、Redis 连接池；
- `httpx.AsyncClient`（复用 TCP 连接）；
- 读取配置、预热缓存。

如果直接写在模块顶层，导入模块时就会执行——测试时 import 一下就连数据库、命令行工具导入时也加载模型，而且没有地方写「关闭」逻辑。**lifespan** 提供了一个明确的「启动 → 运行 → 关闭」钩子。

### 2.2 基本写法

lifespan 是一个用 `@asynccontextmanager` 装饰的异步生成器函数，传给 `FastAPI(lifespan=...)`：

```python
from contextlib import asynccontextmanager

from fastapi import FastAPI, Request


def load_model():
    """模拟加载一个很大的机器学习模型（耗时、只需加载一次）"""
    print("加载模型...")
    return lambda text: "正面" if "好" in text else "负面"


class FakeRedisPool:
    async def connect(self):
        print("连接池已创建")

    async def close(self):
        print("连接池已关闭")


@asynccontextmanager
async def lifespan(app: FastAPI):
    # ---------- 启动阶段：yield 之前，在接收第一个请求前执行 ----------
    app.state.model = load_model()
    app.state.redis = FakeRedisPool()
    await app.state.redis.connect()
    print("应用启动完成")

    yield  # 应用开始处理请求

    # ---------- 关闭阶段：yield 之后，在服务停止时执行 ----------
    await app.state.redis.close()
    print("应用已关闭")


app = FastAPI(lifespan=lifespan)


@app.get("/predict")
async def predict(text: str, request: Request):
    model = request.app.state.model  # 通过 request.app 拿到应用实例
    return {"text": text, "label": model(text)}
```

```bash
uvicorn main:app
# INFO:     Started server process [39900]
# INFO:     Waiting for application startup.
# 加载模型...
# 连接池已创建
# 应用启动完成
# INFO:     Application startup complete.
# INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)

curl 'localhost:8000/predict?text=很好'   # {"text":"很好","label":"正面"}
curl 'localhost:8000/predict?text=很差'   # {"text":"很差","label":"负面"}

# Ctrl+C 停止服务
# INFO:     Shutting down
# INFO:     Waiting for application shutdown.
# 连接池已关闭
# 应用已关闭
# INFO:     Application shutdown complete.
```

执行时机：

```text
uvicorn 启动 → lifespan 中 yield 之前的代码 → 开始监听、处理请求 …… 收到停止信号 → 处理完进行中的请求 → yield 之后的代码 → 进程退出
```

> ⚠️ 如果启动阶段抛出异常，应用**不会启动**：uvicorn 打印堆栈和 `ERROR:    Application startup failed. Exiting.` 后直接退出。这正是我们想要的——数据库连不上就不应该对外提供服务。

### 2.3 `app.state` 与 `request.app.state`

- `app.state` 是挂在应用上的「全局储物格」，可以随意设置属性；
- 在路由中，通过 `request.app.state.xxx` 访问（在不方便导入 `app` 的模块里尤其有用，如 12.12 拆分后的 router 文件）；
- 也可以封装成依赖，让路由更干净：

```python
from typing import Annotated, Callable

from fastapi import Depends, Request


def get_model(request: Request) -> Callable[[str], str]:
    return request.app.state.model


ModelDep = Annotated[Callable[[str], str], Depends(get_model)]


@app.get("/predict2")
async def predict2(text: str, model: ModelDep):
    return {"label": model(text)}
```

### 2.4 yield 一个字典：lifespan state

lifespan 还可以 `yield` 一个字典，字典的内容会出现在**每个请求的 `request.state`** 上。这种写法不需要修改 `app.state`，类型也更清晰：

```python
from contextlib import asynccontextmanager
from typing import TypedDict

import httpx
from fastapi import FastAPI, Request


class State(TypedDict):
    http_client: httpx.AsyncClient


@asynccontextmanager
async def lifespan(app: FastAPI):
    async with httpx.AsyncClient(base_url="https://httpbin.org", timeout=5) as client:
        yield {"http_client": client}  # yield 一个字典 → 每个请求的 request.state
    # 退出 async with 时客户端自动关闭


app = FastAPI(lifespan=lifespan)


@app.get("/state")
async def show_state(request: Request):
    client: httpx.AsyncClient = request.state.http_client
    return {"base_url": str(client.base_url), "closed": client.is_closed}
```

```text
GET /state → {"base_url":"https://httpbin.org","closed":false}
```

几个细节（均已实测）：

- 这些值**不会**出现在 `app.state` 上，只在 `request.state` 上；
- 每个请求拿到的是 state 字典的**浅拷贝**：在请求里 `request.state.name = "x"` 不会影响其他请求，但修改其中的可变对象（如 `request.state.counter["n"] += 1`）会被所有请求看到；
- 用 `async with` 包住 `yield`，资源的关闭就交给了上下文管理器，不会忘记。

| 方式 | 写入 | 读取 | 特点 |
|---|---|---|---|
| `app.state.xxx = ...` | lifespan 中赋值 | `request.app.state.xxx` | 直观，所有地方都能拿到 `app` 就能访问 |
| `yield {"xxx": ...}` | lifespan 中 yield 字典 | `request.state.xxx` | 不污染 app，和请求级 state 统一入口，配合 `TypedDict` 类型更清晰 |

### 2.5 测试中的 lifespan

TestClient **只有在 `with` 语句中使用时才会触发 lifespan**：

```python
from fastapi.testclient import TestClient

client = TestClient(app)
client.get("/predict", params={"text": "很好"})
# AttributeError: 'State' object has no attribute 'model'   ← lifespan 没执行

with TestClient(app) as client:          # 进入 with：执行启动阶段
    client.get("/predict", params={"text": "很好"})
# 离开 with：执行关闭阶段
```

这是测试中最常见的坑之一，12.13 会进一步讲解。

### 2.6 旧写法 `on_event` 已废弃

老教程中常见这种写法：

```python
@app.on_event("startup")
async def startup():
    ...


@app.on_event("shutdown")
async def shutdown():
    ...
```

在当前版本中它**仍能运行，但会发出 `DeprecationWarning`**（源码中标注了 `on_event is deprecated, use lifespan event handlers instead`）。更要注意的是：**一旦给 `FastAPI()` 传了 `lifespan`，所有 `on_event` 注册的处理器都会被忽略**（实测 startup 处理器没有执行）。新代码统一使用 lifespan——启动和关闭写在同一个函数里，可以共享局部变量，也不会忘记成对释放资源。

## 3. 在异步代码中处理阻塞调用

12.1 讲过：`def` 路由在线程池中执行，`async def` 路由在事件循环中执行。如果在 `async def` 里调用了阻塞函数，会怎样？

```python
import asyncio
import time

import anyio
from fastapi import FastAPI
from fastapi.concurrency import run_in_threadpool

app = FastAPI()


def blocking_io(seconds: float) -> str:
    """模拟阻塞操作：同步的第三方 SDK、requests 调用、读大文件……"""
    time.sleep(seconds)
    return "done"


@app.get("/bad")
async def bad():
    # ❌ async def 里直接调用阻塞函数：整个事件循环被卡住
    return {"result": blocking_io(1)}


@app.get("/sync")
def sync_route():
    # ✅ 普通 def：FastAPI 自动放到线程池执行
    return {"result": blocking_io(1)}


@app.get("/threadpool")
async def threadpool():
    # ✅ async def 中需要调用少量阻塞代码时，手动丢进线程池
    result = await run_in_threadpool(blocking_io, 1)
    return {"result": result}


@app.get("/anyio")
async def with_anyio():
    # ✅ 与 run_in_threadpool 等价，run_in_threadpool 内部就是用的它
    result = await anyio.to_thread.run_sync(blocking_io, 1)
    return {"result": result}


@app.get("/asyncio")
async def with_asyncio():
    # ✅ 标准库写法，效果相同
    result = await asyncio.to_thread(blocking_io, 1)
    return {"result": result}
```

用 uvicorn 启动后，对每个接口同时发 5 个请求：

```python
import asyncio
import time

import httpx


async def main():
    async with httpx.AsyncClient(base_url="http://127.0.0.1:8000", timeout=30) as client:
        for path in ["/bad", "/sync", "/threadpool", "/anyio", "/asyncio"]:
            start = time.perf_counter()
            await asyncio.gather(*(client.get(path) for _ in range(5)))
            print(f"{path:<12} 5 个并发请求总耗时 {time.perf_counter() - start:.2f}s")


asyncio.run(main())
```

实测：

```text
/bad         5 个并发请求总耗时 5.05s     ← 5 个请求被串行化了
/sync        5 个并发请求总耗时 1.04s
/threadpool  5 个并发请求总耗时 1.03s
/anyio       5 个并发请求总耗时 1.04s
/asyncio     5 个并发请求总耗时 1.03s
```

`/bad` 期间，**不只是这个接口，整个服务的所有接口都无法响应**。

三种「丢进线程池」写法的关系：

| 写法 | 来源 | 说明 |
|---|---|---|
| `await run_in_threadpool(func, *args, **kwargs)` | `fastapi.concurrency`（转自 Starlette） | 支持关键字参数，内部调用 `anyio.to_thread.run_sync` |
| `await anyio.to_thread.run_sync(func, *args)` | anyio | 与 FastAPI 共用同一个线程池限制器；不直接支持关键字参数（用 `functools.partial`） |
| `await asyncio.to_thread(func, *args, **kwargs)` | 标准库 | 使用 asyncio 默认线程池，与上面两者是不同的池 |

> 💡 FastAPI 的线程池（`def` 路由、`def` 依赖、`run_in_threadpool` 共用）默认最多 **40** 个线程。大量 `def` 路由同时做慢 IO 时可能排队，可以在 lifespan 中调整：
>
> ```python
> import anyio.to_thread
>
> @asynccontextmanager
> async def lifespan(app: FastAPI):
>     limiter = anyio.to_thread.current_default_thread_limiter()
>     print("默认线程池大小：", limiter.total_tokens)  # 40
>     limiter.total_tokens = 100  # 必须在事件循环内（如 lifespan 中）设置
>     yield
> ```

选择建议：

- 整个路由都是同步代码 → 直接写 `def` 路由；
- `async def` 路由里大部分是异步代码，只夹杂少量阻塞调用 → `run_in_threadpool`；
- **CPU 密集型**计算（图像处理、大量数值计算）→ 线程池受 GIL 限制帮助有限，应该用进程池（`ProcessPoolExecutor`）或交给任务队列（参见 10.7 并发实践）。

## 4. 什么时候该用任务队列

`BackgroundTasks` 和应用跑在同一个进程里，有明显局限：

| 能力 | BackgroundTasks | 任务队列（Celery / ARQ / Dramatiq 等） |
|---|---|---|
| 部署复杂度 | 零，开箱即用 | 需要消息中间件（Redis / RabbitMQ）+ 独立 worker 进程 |
| 进程重启后任务 | **丢失** | 持久化在队列中，不丢 |
| 失败重试 | 无 | 支持自动重试、指数退避 |
| 任务状态查询 | 无 | 可以查询进度、结果 |
| 耗时长的任务 | 占用 Web 进程资源 | 由独立 worker 执行，不影响 API |
| 横向扩展 | 跟着 Web 进程走 | worker 可单独扩容 |
| 定时任务 | 无 | Celery Beat 等支持 |

常见任务队列对比：

| 工具 | 特点 | 适用 |
|---|---|---|
| **Celery** | 功能最全、生态最成熟；同步模型 | 大多数需要可靠后台任务的项目 |
| **ARQ** | 基于 asyncio + Redis，轻量 | 全异步项目、任务本身是异步 IO |
| **Dramatiq** | API 简洁、默认行为合理、可靠性好 | 想要比 Celery 更简单的选择 |
| **RQ** | 基于 Redis，极简 | 小项目、简单任务 |

典型的接入方式（以 Celery 为例，示意）：

```python
# tasks.py —— 由独立的 worker 进程执行：celery -A tasks worker
from celery import Celery

celery_app = Celery("tasks", broker="redis://localhost:6379/0", backend="redis://localhost:6379/1")


@celery_app.task(bind=True, max_retries=3)
def generate_report(self, user_id: int) -> str:
    ...  # 耗时几分钟的报表生成


# main.py —— API 只负责提交任务和查询状态
from fastapi import FastAPI
from tasks import celery_app, generate_report

app = FastAPI()


@app.post("/reports", status_code=202)
def create_report(user_id: int):
    task = generate_report.delay(user_id)  # 投递到队列，立即返回
    return {"task_id": task.id}


@app.get("/reports/{task_id}")
def report_status(task_id: str):
    result = celery_app.AsyncResult(task_id)
    return {"status": result.status, "result": result.result if result.ready() else None}
```

> 💡 判断标准：任务**丢了会不会造成业务问题**？**需不需要重试**？**会不会执行超过几秒**？任何一个答案是「是」，就该用任务队列。注意接口返回 **202 Accepted** 表示「已接受，处理中」，客户端再通过任务 ID 轮询结果（或用 12.14 的 WebSocket/SSE 推送进度）。

## 5. 定时任务

「每 5 分钟清理一次过期 token」「每天凌晨 2 点生成日报」这类定时任务，有以下几种方案：

| 方案 | 说明 |
|---|---|
| 系统 cron / K8s CronJob | 定时执行一个独立脚本或调用某个接口，和 Web 服务解耦，**最稳妥** |
| Celery Beat | 已经使用 Celery 时的自然选择 |
| APScheduler（进程内） | 在 FastAPI 进程里跑调度器，简单，适合小项目 |

APScheduler 与 lifespan 结合的写法（`pip install "apscheduler<4"`，目前稳定版为 3.x）：

```python
from contextlib import asynccontextmanager
from datetime import datetime

from apscheduler.schedulers.asyncio import AsyncIOScheduler
from fastapi import FastAPI

scheduler = AsyncIOScheduler(timezone="Asia/Shanghai")


async def clean_expired_tokens():
    print(f"[{datetime.now():%H:%M:%S}] 清理过期 token")


def daily_report():
    print(f"[{datetime.now():%H:%M:%S}] 生成日报")


@asynccontextmanager
async def lifespan(app: FastAPI):
    scheduler.add_job(clean_expired_tokens, "interval", seconds=2, id="clean_tokens")
    scheduler.add_job(daily_report, "cron", hour=2, minute=0, id="daily_report")  # 每天 02:00
    scheduler.start()
    yield
    scheduler.shutdown()


app = FastAPI(lifespan=lifespan)


@app.get("/jobs")
async def list_jobs():
    return [
        {"id": job.id, "next_run": job.next_run_time.isoformat()}
        for job in scheduler.get_jobs()
    ]
```

```text
GET /jobs → [{"id":"clean_tokens","next_run":"2026-10-18T11:15:43.992316+08:00"},{"id":"daily_report","next_run":"2026-10-19T02:00:00+08:00"}]
[11:13:51] 清理过期 token
[11:13:53] 清理过期 token
...
```

触发器类型：`"interval"`（固定间隔）、`"cron"`（类 crontab 表达式）、`"date"`（指定时间执行一次）。

> ⚠️ **多进程部署的陷阱**：用 `uvicorn --workers 4` 或多个容器副本部署时，**每个进程都会启动一个调度器**，同一个任务会被执行 4 次！解决办法：只在一个专门的进程里运行调度器；或用分布式锁保证只有一个实例执行；或干脆改用系统 cron / K8s CronJob / Celery Beat。

## 6. 方案选择总结

| 需求 | 方案 |
|---|---|
| 响应后顺手做点轻量工作（通知、日志、清理） | `BackgroundTasks` |
| 应用启动时初始化、关闭时释放资源 | `lifespan` |
| 全局共享对象（模型、连接池、HTTP 客户端） | lifespan + `app.state` 或 yield 字典 |
| `async def` 中调用阻塞函数 | `run_in_threadpool` / `anyio.to_thread.run_sync` |
| CPU 密集型计算 | 进程池或任务队列 |
| 重要、耗时、需要重试的任务 | Celery / ARQ / Dramatiq |
| 定时任务 | 系统 cron / K8s CronJob（首选），或 Celery Beat、APScheduler |

## 常见坑

1. **把 yield 依赖得到的 Session 传给后台任务**：是否可用取决于依赖的 `scope` 等执行顺序细节，非常脆弱。后台任务应传 id，在任务内部自建资源。
2. **后台任务不捕获异常**：失败只出现在日志里，而且会导致同一请求中排在后面的任务不再执行。
3. **用 BackgroundTasks 跑重要任务**：进程重启就丢失、没有重试。重要任务用任务队列。
4. **`async def` 后台任务或路由里调用阻塞函数**：卡住事件循环，所有请求一起变慢。
5. **在模块顶层初始化重资源**：import 时就连接数据库、加载模型，测试和工具脚本都受影响，也没有关闭时机。放进 lifespan。
6. **测试时不用 `with TestClient(app)`**：lifespan 不执行，`app.state` 上的属性不存在。
7. **lifespan 和 `on_event` 混用**：传了 `lifespan` 后 `on_event` 处理器被静默忽略。
8. **在 lifespan 外设置线程池大小**：`current_default_thread_limiter()` 必须在事件循环中调用，否则抛 `NoEventLoopError`。
9. **多 worker 下进程内定时任务重复执行**：每个进程都有自己的调度器。
10. **误以为 `asyncio.create_task()` 可以替代后台任务**：没有保存引用的任务可能被垃圾回收，异常也容易被吞掉；在 FastAPI 中优先用 `BackgroundTasks` 或任务队列。

## 小结

- `BackgroundTasks` 让函数在**响应发送之后**执行；任务按添加顺序串行执行，同步函数进线程池、异步函数在事件循环中执行；依赖和路由共享同一个任务列表。
- 后台任务失败客户端无感知、后续任务不再执行、进程退出即丢失——只适合轻量、可丢失的工作，内部要自行捕获异常。
- `lifespan` 用 `@asynccontextmanager` 定义：`yield` 之前是启动逻辑，之后是关闭逻辑；资源可以放在 `app.state`，或 `yield` 字典交给 `request.state`。
- `on_event` 已废弃，且与 `lifespan` 同时存在时会被忽略；测试中必须用 `with TestClient(app)` 才会触发 lifespan。
- `async def` 中遇到阻塞代码用 `run_in_threadpool` / `anyio.to_thread.run_sync` / `asyncio.to_thread`，FastAPI 线程池默认 40 个线程。
- 重要、耗时、需重试的任务交给 Celery / ARQ / Dramatiq 等任务队列；定时任务首选系统级调度，进程内 APScheduler 要注意多 worker 重复执行。
