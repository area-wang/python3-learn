# 12.6 错误处理练习题

## 一、概念题

1. FastAPI 应用中的错误有哪三种来源？它们默认的状态码和响应格式分别是什么？
2. 为什么在路由中要 `raise HTTPException(...)` 而不是 `return HTTPException(...)`？用异常而不是"返回错误码"来表达错误，在多层函数调用中有什么优势？
3. `fastapi.HTTPException` 和 `starlette.exceptions.HTTPException` 是什么关系？覆盖默认 HTTP 异常处理器时应该注册哪一个？为什么？
4. 为什么说服务层不应该直接抛 `HTTPException`？自定义业务异常 + 异常处理器的方案解决了什么问题？
5. 异常处理器是如何匹配异常的？如果同时给 `ValueError` 和 `Exception` 注册了处理器，抛出 `UnicodeDecodeError` 时会调用哪一个？
6. `RequestValidationError.errors()` 返回的每一项包含哪些键？`loc` 的第一个元素代表什么？为什么原样把它放进 `JSONResponse` 可能会失败？
7. 如何在"只记录日志、不改变默认响应格式"的前提下增强异常处理？需要用到哪个模块中的什么函数？
8. 统一错误响应格式中的 `code` 字段有什么作用？为什么不能只依赖 HTTP 状态码或 `message` 文本？
9. 给 `Exception` 注册的处理器和普通处理器有哪些不同？为什么它返回的响应可能没有 CORS 头？测试时需要注意什么？
10. `FastAPI(debug=True)` 有什么作用？为什么生产环境必须关闭？500 响应中返回 `str(exc)` 有什么风险？

## 二、判断代码输出 / 找错

### 1. 返回还是抛出

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()


@app.get("/items/{item_id}")
async def read_item(item_id: int):
    if item_id > 100:
        return HTTPException(status_code=404, detail="not found")
    return {"item_id": item_id}
```

请求 `/items/200` 时状态码是多少？会发生什么？如何修改？

### 2. 接管不了的 404

```python
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse

app = FastAPI()


@app.exception_handler(HTTPException)
async def handler(request: Request, exc: HTTPException):
    return JSONResponse({"error": exc.detail}, status_code=exc.status_code)


@app.get("/items/{item_id}")
async def read_item(item_id: int):
    raise HTTPException(404, "商品不存在")
```

分别请求 `/items/1` 和 `/abc`，写出两个响应体，并解释为什么不一致。

### 3. 处理器的匹配顺序

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()


class AppError(Exception):
    pass


class NotFoundError(AppError):
    pass


@app.exception_handler(AppError)
async def app_error(request: Request, exc: AppError):
    return JSONResponse({"handler": "app_error"}, status_code=400)


@app.exception_handler(NotFoundError)
async def not_found(request: Request, exc: NotFoundError):
    return JSONResponse({"handler": "not_found"}, status_code=404)


@app.get("/a")
async def a():
    raise NotFoundError()


@app.get("/b")
async def b():
    raise AppError()


@app.get("/c")
async def c():
    raise KeyError("x")
```

分别写出 `/a`、`/b`、`/c` 的状态码和响应体。

### 4. 被吞掉的异常

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()
db = {1: "alice"}


@app.get("/users/{user_id}")
async def get_user(user_id: int):
    try:
        if user_id not in db:
            raise HTTPException(404, "用户不存在")
        return {"name": db[user_id].upper()}
    except Exception as e:
        return {"error": str(e)}
```

请求 `/users/2` 时客户端收到什么？状态码是多少？这段代码有哪些问题？如何修改？

### 5. 丢失的响应头

```python
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException

app = FastAPI()


@app.exception_handler(StarletteHTTPException)
async def handler(request: Request, exc: StarletteHTTPException):
    return JSONResponse({"message": exc.detail}, status_code=exc.status_code)


@app.get("/me")
async def me():
    raise HTTPException(401, "未登录", headers={"WWW-Authenticate": "Bearer"})
```

请求 `/me` 时响应中还有 `WWW-Authenticate` 头吗？为什么？如何修复？

## 三、编程题

### 1. 图书查询（基础）

实现 `GET /books/{isbn}`：

- ISBN 不存在时返回 404，`detail` 为 `{"isbn": ..., "message": "图书不存在"}`；
- ISBN 格式不是 13 位数字时（用 `Path(pattern=...)` 校验）由 FastAPI 自动返回 422；
- 图书已下架时返回 410（Gone）；
- 用 curl 演示三种错误。

### 2. 中文化校验错误（基础）

覆盖 `RequestValidationError` 处理器：

- 根据 `type` 字段把常见错误翻译成中文：`missing` → "字段必填"，`int_parsing` → "必须是整数"，`string_too_short` → "长度不能少于 X 个字符"（X 从 `ctx` 中读取）；
- 未翻译的类型保留原始 `msg`；
- 响应格式：`{"message": "参数错误", "errors": {"字段路径": "错误说明"}}`。

### 3. 业务异常体系（进阶）

为一个电商下单服务设计异常体系：

- 基类 `AppError`，带 `status_code`、`code`、`message`、`details`；
- 子类：`ProductNotFound`（404）、`OutOfStock`（409，`details` 包含剩余库存）、`InsufficientBalance`（400）、`OrderAlreadyPaid`（409）；
- 服务层函数 `place_order(user_id, product_id, quantity)` 只抛业务异常，不导入任何 FastAPI 内容；
- Web 层注册一个处理器统一翻译；
- 写一个命令行脚本直接调用 `place_order`，捕获业务异常后打印友好提示，体会"服务层与 HTTP 解耦"的好处。

### 4. 统一错误格式（进阶）

在一个已有 5 个接口的应用中实现统一错误格式 `{"code", "message", "details", "request_id"}`：

- 覆盖业务异常、Starlette `HTTPException`、`RequestValidationError`、`Exception` 四种处理器；
- `request_id` 从请求头 `X-Request-ID` 读取，没有则生成一个 UUID（提示：在处理器中通过 `request.headers` 获取）；
- 500 错误只返回通用信息，完整堆栈用 `logger.exception` 写入日志；
- 用 `TestClient(app, raise_server_exceptions=False)` 为每种错误写一个测试，断言响应结构一致。

### 5. 只加日志，不改格式（进阶）

在不改变任何默认响应格式的前提下：

- 所有 4xx 错误以 `WARNING` 级别记录方法、路径、状态码、`detail`；
- 所有校验错误额外记录出错字段列表；
- 统计每种状态码出现的次数，并提供 `GET /error-stats` 接口返回统计结果；
- 提示：使用 `fastapi.exception_handlers` 中的默认处理器。

### 6. 外部服务错误映射（挑战）

实现 `GET /weather/{city}`，内部用 `httpx.AsyncClient` 调用一个（可以用另一个 FastAPI 应用模拟的）天气服务：

- 外部服务超时 → 返回 504，`code` 为 `UPSTREAM_TIMEOUT`；
- 外部服务返回 5xx → 返回 502，`code` 为 `UPSTREAM_ERROR`；
- 外部服务返回 404 → 返回 404，`code` 为 `CITY_NOT_FOUND`；
- 连接失败 → 返回 503，并带 `Retry-After: 30` 响应头；
- 把 httpx 的异常转换为自定义业务异常的逻辑封装在一个函数中，路由函数本身不出现 `try/except`。

## 四、综合实践：图书馆借阅系统的错误处理

实现一个内存版图书馆借阅 API，重点设计错误处理：

1. 接口：`GET /books`、`GET /books/{id}`、`POST /borrow`（JSON：`user_id`、`book_id`）、`POST /return`、`GET /users/{id}/borrowed`；
2. 业务规则与错误：
   - 图书不存在 → 404 `BOOK_NOT_FOUND`
   - 用户不存在 → 404 `USER_NOT_FOUND`
   - 图书已被借出 → 409 `BOOK_UNAVAILABLE`（`details` 中给出预计归还日期）
   - 用户借阅数量已达上限 3 本 → 400 `BORROW_LIMIT_EXCEEDED`
   - 用户有逾期未还图书 → 403 `OVERDUE_BOOKS`（`details` 列出逾期图书）
   - 归还未借的图书 → 400 `NOT_BORROWED`
3. 所有错误（包括 422、路由 404、405、500）统一为 `{"code", "message", "details"}` 格式；
4. 借阅逻辑放在独立的服务模块中，只抛业务异常；
5. 用 `responses=` 在文档中为每个接口声明可能的错误；
6. 使用 `logging` 记录：4xx 为 `WARNING`，5xx 为 `ERROR` 并附堆栈；
7. 用 pytest + `TestClient` 为每一种错误编写测试。

## 五、参考检查点

- 能否说清 FastAPI 中三种错误来源及其默认响应；
- 能否正确使用 `raise HTTPException`，包括自定义 `detail` 结构和响应头；
- 能否区分 FastAPI 与 Starlette 的 `HTTPException`，并在覆盖处理器时选对类型、保留 `headers`；
- 能否设计业务异常体系，让服务层与 HTTP 解耦，并理解处理器按 MRO 匹配的规则；
- 能否定制 `RequestValidationError` 的响应，并处理 `ctx` 中不可序列化的对象；
- 能否复用 `fastapi.exception_handlers` 中的默认处理器，在不改格式的前提下增加日志；
- 能否实现统一的错误响应格式，用 `Exception` 处理器兜底，且不向客户端泄露内部细节；
- 能否理解 `Exception` 处理器不经过中间件、`TestClient` 默认重抛服务端异常等细节。
