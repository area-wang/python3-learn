# 12.6 错误处理

12.5 讲的是"一切顺利时怎么返回"，本节讲"出错时怎么返回"。一个 API 会遇到各种错误：客户端传错参数、请求的资源不存在、没有权限、业务规则不满足（余额不足、库存不够）、以及服务端自己的 bug。好的错误处理要做到三点：**状态码符合语义**、**响应格式统一**（前端只需一套解析逻辑）、**服务端留下足够的日志**而**不向客户端泄露内部细节**。FastAPI 通过 `HTTPException` 和异常处理器（exception handler）实现这些目标，它与第 06 章学过的 Python 异常机制一脉相承。

> 本节示例基于 FastAPI 0.143 / Pydantic 2.14 / Starlette 1.8 / Python 3.14 实际运行验证。

## 1. FastAPI 中错误的三种来源

| 来源 | 触发场景 | 默认状态码 | 默认响应 |
|---|---|---|---|
| 请求校验失败 `RequestValidationError` | 参数类型不对、缺字段、不满足约束 | 422 | `{"detail": [错误列表]}` |
| HTTP 异常 `HTTPException` | 你主动 `raise`；或框架找不到路由（404）、方法不允许（405） | 你指定 | `{"detail": ...}` |
| 未捕获的其他异常 | 代码 bug、数据库断开等 | 500 | 纯文本 `Internal Server Error` |

前两种由 FastAPI 的默认异常处理器转成 JSON 响应；第三种会被最外层的 `ServerErrorMiddleware` 兜底，并在服务端打印完整堆栈。

## 2. `HTTPException`：主动返回错误

### 2.1 基本用法

```python
from fastapi import FastAPI, HTTPException, status

app = FastAPI()
items = {"foo": "The Foo Wrestlers"}


@app.get("/items/{item_id}")
async def read_item(item_id: str):
    if item_id not in items:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Item not found")
    return {"item": items[item_id]}
```

```bash
curl -i http://127.0.0.1:8000/items/bar
# HTTP/1.1 404 Not Found
# {"detail":"Item not found"}
```

注意是 **`raise`** 而不是 `return`。`raise` 的好处在于：错误可以在**任意深度**的函数调用中抛出（工具函数、依赖、服务层），不需要一层层把错误返回值传上来，这是异常相比"返回错误码"的根本优势。

### 2.2 `detail` 可以是任意可 JSON 序列化的数据

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()


@app.post("/orders")
async def create_order(quantity: int):
    if quantity > 10:
        raise HTTPException(
            status_code=400,
            detail={"code": "QUANTITY_EXCEEDED", "message": "单次最多购买 10 件", "max": 10},
        )
    return {"quantity": quantity}
```

```bash
curl -X POST "http://127.0.0.1:8000/orders?quantity=20"
# {"detail":{"code":"QUANTITY_EXCEEDED","message":"单次最多购买 10 件","max":10}}
```

### 2.3 附带响应头

某些错误按规范需要特定的响应头，例如 401 应携带 `WWW-Authenticate`、429 可以携带 `Retry-After`：

```python
from fastapi import FastAPI, HTTPException, status

app = FastAPI()


@app.get("/private")
async def private():
    raise HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="未登录",
        headers={"WWW-Authenticate": "Bearer"},
    )
```

```bash
curl -i http://127.0.0.1:8000/private
# HTTP/1.1 401 Unauthorized
# www-authenticate: Bearer
# {"detail":"未登录"}
```

### 2.4 FastAPI 的 `HTTPException` 与 Starlette 的 `HTTPException`

FastAPI 的 `HTTPException` 继承自 Starlette 的 `HTTPException`，区别只是 `detail` 可以是任意 JSON 数据（Starlette 版本只接受字符串）。

| | `fastapi.HTTPException` | `starlette.exceptions.HTTPException` |
|---|---|---|
| 关系 | 子类 | 父类 |
| 谁在用 | 你的业务代码 | 框架内部：路由不存在 404、方法不允许 405 等 |
| 写业务代码时 | ✅ 用这个 | — |
| 注册异常处理器时 | ❌ 只能捕获你自己抛的 | ✅ 用这个，才能同时覆盖框架抛出的 404/405 |

这个区别在第 4 节覆盖默认处理器时非常关键。

## 3. 自定义异常 + 异常处理器

### 3.1 为什么不总是用 `HTTPException`

在路由函数里直接抛 `HTTPException` 很方便，但当代码分层后（路由 → 服务层 → 数据访问层），**服务层不应该知道 HTTP 的存在**——同一个服务函数可能被 HTTP 接口、命令行脚本、定时任务调用。服务层应该抛**业务异常**，再由 Web 层统一翻译成 HTTP 响应。

### 3.2 `@app.exception_handler`

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()


class InsufficientBalanceError(Exception):
    def __init__(self, balance: float, required: float):
        self.balance = balance
        self.required = required


@app.exception_handler(InsufficientBalanceError)
async def insufficient_balance_handler(request: Request, exc: InsufficientBalanceError):
    return JSONResponse(
        status_code=400,
        content={
            "message": f"余额不足：当前 {exc.balance}，需要 {exc.required}",
            "path": request.url.path,
        },
    )


def pay(balance: float, amount: float) -> float:
    """服务层函数：只关心业务，不关心 HTTP"""
    if balance < amount:
        raise InsufficientBalanceError(balance, amount)
    return balance - amount


@app.post("/pay")
async def pay_api(amount: float):
    return {"left": pay(100, amount)}
```

```bash
curl -X POST "http://127.0.0.1:8000/pay?amount=150"
# {"message":"余额不足：当前 100，需要 150.0","path":"/pay"}
```

异常处理器的规则：

- 签名固定为 `(request: Request, exc: 异常类型)`，可以是 `async def` 或 `def`；
- 必须**返回**一个 `Response` 对象；
- 匹配时沿异常类的 **MRO** 查找：给 `ValueError` 注册的处理器，也能处理它的子类 `UnicodeDecodeError`；同时注册了父类和子类时，**更具体的子类处理器优先**；
- 也可以用整数状态码注册：`@app.exception_handler(404)`，用于处理所有该状态码的 `HTTPException`。

### 3.3 不用装饰器：构造时传入

```python
from fastapi import FastAPI, Request
from fastapi.responses import PlainTextResponse


async def not_found_handler(request: Request, exc):
    return PlainTextResponse(f"页面 {request.url.path} 不存在", status_code=404)


app = FastAPI(exception_handlers={404: not_found_handler})
```

```bash
curl http://127.0.0.1:8000/whatever
# 页面 /whatever 不存在
```

也可以用 `app.add_exception_handler(异常类, 处理函数)`，这在大型项目中把处理器的注册集中到一个 `register_exception_handlers(app)` 函数里时很常用。

## 4. 覆盖默认的异常处理器

### 4.1 覆盖请求校验错误（422）

默认的 422 响应对前端来说不太友好（`loc` 是数组、`msg` 是英文）。可以覆盖 `RequestValidationError` 的处理器：

```python
from fastapi import FastAPI, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from pydantic import BaseModel

app = FastAPI()


@app.exception_handler(RequestValidationError)
async def validation_handler(request: Request, exc: RequestValidationError):
    errors = [
        {
            "field": ".".join(str(p) for p in err["loc"][1:]),  # 去掉 body/query 前缀
            "location": err["loc"][0],
            "message": err["msg"],
        }
        for err in exc.errors()
    ]
    return JSONResponse(status_code=422, content={"message": "参数校验失败", "errors": errors})


class Item(BaseModel):
    title: str
    size: int


@app.post("/items")
async def create_item(item: Item, page: int = 1):
    return item
```

```bash
curl -X POST "http://127.0.0.1:8000/items?page=abc" \
  -H "Content-Type: application/json" -d '{"size": "XL"}'
```

```json
{
  "message": "参数校验失败",
  "errors": [
    {"field": "page", "location": "query", "message": "Input should be a valid integer, unable to parse string as an integer"},
    {"field": "title", "location": "body", "message": "Field required"},
    {"field": "size", "location": "body", "message": "Input should be a valid integer, unable to parse string as an integer"}
  ]
}
```

`exc.errors()` 返回的每一项包含：

| 键 | 示例 | 说明 |
|---|---|---|
| `type` | `"missing"`、`"int_parsing"` | 错误类型，适合前端做 i18n 映射 |
| `loc` | `("body", "size")` | 错误位置：第一项是来源（body/query/path/header/cookie），后面是字段路径 |
| `msg` | `"Field required"` | 人类可读的说明 |
| `input` | `"XL"` | 导致错误的原始输入 |
| `ctx` | `{"error": ValueError(...)}` | 额外上下文（可选） |

另外 `exc.body` 是收到的原始请求体，调试时很有用。

> ⚠️ 如果要把 `exc.errors()` **原样**放进响应，注意其中 `ctx` 可能包含异常对象（如 `field_validator` 抛出的 `ValueError`），直接 `JSONResponse` 会序列化失败。要么先 `jsonable_encoder(exc.errors())`（异常对象会变成 `{}`），要么像上面一样只挑出需要的字段。

### 4.2 覆盖 HTTP 异常处理器

```python
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException

app = FastAPI()


# ✅ 注册 Starlette 的 HTTPException，才能同时接管框架抛出的 404/405
@app.exception_handler(StarletteHTTPException)
async def http_handler(request: Request, exc: StarletteHTTPException):
    return JSONResponse(
        status_code=exc.status_code,
        content={"error": exc.detail, "status": exc.status_code},
        headers=exc.headers,   # 别丢了 WWW-Authenticate 等响应头
    )


@app.get("/items/{item_id}")
async def read_item(item_id: int):
    raise HTTPException(404, "商品不存在")
```

```bash
curl http://127.0.0.1:8000/items/1
# {"error":"商品不存在","status":404}
curl http://127.0.0.1:8000/no-such-route
# {"error":"Not Found","status":404}
curl -X POST http://127.0.0.1:8000/items/1
# {"error":"Method Not Allowed","status":405}
```

> ⚠️ 如果注册的是 `fastapi.HTTPException`，你自己 `raise` 的异常会被接管，但访问不存在的路由时返回的仍是默认的 `{"detail":"Not Found"}`——因为那是 Starlette 抛出的父类异常，子类处理器匹配不到它。

### 4.3 复用默认处理器：只加逻辑，不改格式

有时只想在出错时"顺便做点事"（记日志、打点统计），响应格式保持默认。FastAPI 把默认处理器暴露在 `fastapi.exception_handlers` 中，可以直接调用：

```python
import logging

from fastapi import FastAPI, HTTPException, Request
from fastapi.exception_handlers import http_exception_handler, request_validation_exception_handler
from fastapi.exceptions import RequestValidationError
from starlette.exceptions import HTTPException as StarletteHTTPException

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger("api")
app = FastAPI()


@app.exception_handler(StarletteHTTPException)
async def log_http_exception(request: Request, exc: StarletteHTTPException):
    logger.warning("HTTP %s %s %s -> %s", exc.status_code, request.method, request.url.path, exc.detail)
    return await http_exception_handler(request, exc)


@app.exception_handler(RequestValidationError)
async def log_validation_exception(request: Request, exc: RequestValidationError):
    logger.warning("校验失败 %s: %s", request.url.path, exc.errors())
    return await request_validation_exception_handler(request, exc)


@app.get("/items/{item_id}")
async def read_item(item_id: int):
    if item_id == 3:
        raise HTTPException(418, "Nope! I don't like 3.")
    return {"item_id": item_id}
```

```bash
curl http://127.0.0.1:8000/items/3
# {"detail":"Nope! I don't like 3."}
# 服务端日志：WARNING:api:HTTP 418 GET /items/3 -> Nope! I don't like 3.
```

## 5. 设计统一的错误响应格式

### 5.1 为什么要统一

不做处理时，一个 FastAPI 应用的错误响应至少有三种形状：

```text
422 → {"detail": [{"type": ..., "loc": [...], "msg": ...}]}
404 → {"detail": "Not Found"}
500 → Internal Server Error   （纯文本！）
```

前端要写三套解析逻辑，非常痛苦。实际项目中一般约定统一格式，例如：

```json
{
  "code": "NOT_FOUND",
  "message": "用户 2 不存在",
  "details": {"user_id": 2}
}
```

| 字段 | 说明 |
|---|---|
| `code` | **机器可读**的错误码，前端据此分支处理、做多语言映射；比 HTTP 状态码更细 |
| `message` | 人类可读的说明，可直接展示 |
| `details` | 可选的附加数据，如校验错误列表、冲突的字段 |

### 5.2 完整实现

```python
# main.py
import logging
from typing import Any

from fastapi import FastAPI, HTTPException, Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from pydantic import BaseModel, field_validator
from starlette.exceptions import HTTPException as StarletteHTTPException

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(name)s: %(message)s")
logger = logging.getLogger("app.errors")


# ---------- 1. 业务异常体系 ----------
class AppError(Exception):
    """所有业务异常的基类，子类只需覆盖类属性"""

    status_code: int = status.HTTP_400_BAD_REQUEST
    code: str = "BAD_REQUEST"
    message: str = "请求错误"

    def __init__(self, message: str | None = None, *, details: Any = None):
        self.message = message or self.message
        self.details = details
        super().__init__(self.message)


class NotFoundError(AppError):
    status_code = status.HTTP_404_NOT_FOUND
    code = "NOT_FOUND"
    message = "资源不存在"


class ConflictError(AppError):
    status_code = status.HTTP_409_CONFLICT
    code = "CONFLICT"
    message = "资源冲突"


class PermissionDeniedError(AppError):
    status_code = status.HTTP_403_FORBIDDEN
    code = "PERMISSION_DENIED"
    message = "没有权限"


# ---------- 2. 统一的响应构造 ----------
def error_response(status_code: int, code: str, message: str, details: Any = None) -> JSONResponse:
    return JSONResponse(
        status_code=status_code,
        content={"code": code, "message": message, "details": details},
    )


HTTP_CODES = {
    401: "UNAUTHORIZED",
    403: "FORBIDDEN",
    404: "NOT_FOUND",
    405: "METHOD_NOT_ALLOWED",
}


# ---------- 3. 注册异常处理器 ----------
def register_exception_handlers(app: FastAPI) -> None:
    @app.exception_handler(AppError)
    async def app_error_handler(request: Request, exc: AppError):
        logger.warning("业务异常 %s %s -> %s: %s", request.method, request.url.path, exc.code, exc.message)
        return error_response(exc.status_code, exc.code, exc.message, exc.details)

    @app.exception_handler(StarletteHTTPException)
    async def http_error_handler(request: Request, exc: StarletteHTTPException):
        code = HTTP_CODES.get(exc.status_code, "HTTP_ERROR")
        response = error_response(exc.status_code, code, str(exc.detail))
        if exc.headers:
            response.headers.update(exc.headers)
        return response

    @app.exception_handler(RequestValidationError)
    async def validation_error_handler(request: Request, exc: RequestValidationError):
        details = [
            {
                "field": ".".join(str(p) for p in err["loc"][1:]),
                "location": err["loc"][0],
                "message": err["msg"],
                "type": err["type"],
            }
            for err in exc.errors()
        ]
        return error_response(status.HTTP_422_UNPROCESSABLE_CONTENT, "VALIDATION_ERROR", "请求参数校验失败", details)

    @app.exception_handler(Exception)
    async def unhandled_error_handler(request: Request, exc: Exception):
        # logger.exception 会自动附带完整堆栈
        logger.exception("未处理异常 %s %s", request.method, request.url.path)
        # 不把异常信息返回给客户端，避免泄露内部实现
        return error_response(status.HTTP_500_INTERNAL_SERVER_ERROR, "INTERNAL_ERROR", "服务器内部错误")


# ---------- 4. 应用与路由 ----------
app = FastAPI()
register_exception_handlers(app)

users = {1: "alice"}


class UserCreate(BaseModel):
    username: str
    age: int

    @field_validator("username")
    @classmethod
    def not_reserved(cls, v: str) -> str:
        if v == "admin":
            raise ValueError("用户名不能是 admin")
        return v


@app.get("/users/{user_id}")
async def get_user(user_id: int):
    if user_id not in users:
        raise NotFoundError(f"用户 {user_id} 不存在", details={"user_id": user_id})
    return {"id": user_id, "name": users[user_id]}


@app.post("/users", status_code=201)
async def create_user(user: UserCreate):
    if user.username in users.values():
        raise ConflictError("用户名已存在", details={"field": "username"})
    users[len(users) + 1] = user.username
    return user


@app.delete("/users/{user_id}")
async def delete_user(user_id: int):
    raise PermissionDeniedError("只有管理员可以删除用户")


@app.get("/login-required")
async def login_required():
    raise HTTPException(401, "请先登录", headers={"WWW-Authenticate": "Bearer"})


@app.get("/boom")
async def boom():
    return 1 / 0
```

依次请求，**所有错误都是同一种结构**：

| 请求 | 状态码 | 响应体 |
|---|---|---|
| `GET /users/2` | 404 | `{"code":"NOT_FOUND","message":"用户 2 不存在","details":{"user_id":2}}` |
| `POST /users` `{"username":"alice","age":1}` | 409 | `{"code":"CONFLICT","message":"用户名已存在","details":{"field":"username"}}` |
| `DELETE /users/1` | 403 | `{"code":"PERMISSION_DENIED","message":"只有管理员可以删除用户","details":null}` |
| `GET /login-required` | 401 | `{"code":"UNAUTHORIZED","message":"请先登录","details":null}`（带 `WWW-Authenticate` 头） |
| `GET /no-such-route` | 404 | `{"code":"NOT_FOUND","message":"Not Found","details":null}` |
| `GET /boom` | 500 | `{"code":"INTERNAL_ERROR","message":"服务器内部错误","details":null}` |

校验失败的请求：

```bash
curl -X POST http://127.0.0.1:8000/users -H "Content-Type: application/json" \
  -d '{"username": "admin", "age": "x"}'
```

```json
{
  "code": "VALIDATION_ERROR",
  "message": "请求参数校验失败",
  "details": [
    {"field": "username", "location": "body", "message": "Value error, 用户名不能是 admin", "type": "value_error"},
    {"field": "age", "location": "body", "message": "Input should be a valid integer, unable to parse string as an integer", "type": "int_parsing"}
  ]
}
```

服务端日志（`/boom` 会附带完整堆栈）：

```text
WARNING app.errors: 业务异常 GET /users/2 -> NOT_FOUND: 用户 2 不存在
WARNING app.errors: 业务异常 POST /users -> CONFLICT: 用户名已存在
ERROR app.errors: 未处理异常 GET /boom
Traceback (most recent call last):
  ...
ZeroDivisionError: division by zero
```

> 💡 这套设计的扩展性很好：新增一种业务错误只需要写一个 3 行的子类，如 `class OutOfStockError(AppError): status_code = 409; code = "OUT_OF_STOCK"; message = "库存不足"`，处理器、响应格式、日志全部自动生效。

## 6. 处理未捕获异常（500）

### 6.1 默认行为

没有注册 `Exception` 处理器时，未捕获异常会：

1. 在服务端（uvicorn 日志）打印完整堆栈；
2. 返回 `500`，响应体是**纯文本** `Internal Server Error`。

### 6.2 `debug=True`：只在开发环境用

```python
from fastapi import FastAPI

app = FastAPI(debug=True)


@app.get("/boom")
async def boom():
    return 1 / 0
```

开启后，500 响应会直接把**完整堆栈**返回给客户端（浏览器访问时是 HTML 页面，其他客户端是纯文本）。方便本地调试，但**生产环境绝对不能开**，否则文件路径、代码片段、甚至配置信息都会泄露。

### 6.3 `Exception` 处理器的特殊之处

给 `Exception`（或状态码 `500`）注册的处理器与其他处理器不同，它由最外层的 `ServerErrorMiddleware` 调用：

1. 处理器返回的响应会发给客户端；
2. 但异常**仍会被继续抛出**，因此 uvicorn 依然会打印堆栈，测试中的 `TestClient` 默认也会把异常重新抛出（需要 `TestClient(app, raise_server_exceptions=False)` 才能拿到 500 响应）；
3. 由于它处在**所有中间件的外层**，这个响应**不会经过你添加的中间件**——例如 `CORSMiddleware` 不会给它加上 CORS 头，浏览器里前端看到的可能是"跨域错误"而不是 500。

> 💡 正因如此，业务中**可预期的**错误都应该定义成 `AppError` 子类，让它们走普通处理器（会经过中间件）。`Exception` 处理器只作为"真正的 bug"的最后防线。中间件会在 12.10 详细讲解。

## 7. 在依赖中抛出异常

依赖注入（12.7 详细讲解）是做鉴权、权限校验的主要手段，在依赖中 `raise` 的异常与在路由中 `raise` 完全一样，会被同一套异常处理器处理：

```python
from typing import Annotated

from fastapi import Depends, FastAPI, Header, HTTPException, status

app = FastAPI()


async def verify_token(x_token: Annotated[str, Header()]) -> str:
    if x_token != "secret":
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Token 无效")
    return x_token


@app.get("/protected")
async def protected(token: Annotated[str, Depends(verify_token)]):
    return {"message": "通过验证"}
```

```bash
curl http://127.0.0.1:8000/protected -H "X-Token: wrong"
# {"detail":"Token 无效"}            401
curl http://127.0.0.1:8000/protected
# {"detail":[{"type":"missing","loc":["header","x-token"],"msg":"Field required","input":null}]}   422
```

注意第二种情况：缺少请求头时，依赖函数**根本没有执行**，FastAPI 在解析依赖参数阶段就返回了 422。

## 8. 状态码选择指南

错误处理的第一步是选对状态码：

| 情况 | 状态码 | 说明 |
|---|---|---|
| 请求格式/类型错误 | 422 | FastAPI 自动处理，一般不需要手动抛 |
| 业务规则不满足（余额不足、参数组合非法） | 400 | 通用客户端错误 |
| 没有登录 / Token 无效或过期 | 401 | 应附带 `WWW-Authenticate` 头 |
| 登录了但没有权限 | 403 | 与 401 区分开 |
| 资源不存在 | 404 | 有时为了不暴露资源存在性，无权限也返回 404 |
| 状态冲突（重复创建、版本冲突） | 409 | |
| 上传文件过大 | 413 | `HTTP_413_CONTENT_TOO_LARGE` |
| 请求过于频繁 | 429 | 可带 `Retry-After` 头 |
| 服务端 bug | 500 | 不要主动抛，让它作为兜底 |
| 依赖的外部服务不可用 | 502 / 503 / 504 | 网关错误 / 服务不可用 / 网关超时 |

## 9. 错误处理最佳实践

1. **分层抛异常**：服务层抛业务异常（`AppError` 子类），只有 Web 层才知道 HTTP；在路由里快速原型时可以直接用 `HTTPException`。
2. **统一响应格式**：所有错误（422、404、业务异常、500）都输出同一种 JSON 结构，前端只写一套解析逻辑。
3. **机器可读的错误码**：`code` 字段比 HTTP 状态码更细，前端靠它分支处理，比解析 `message` 文本可靠。
4. **500 不泄露细节**：响应只说"服务器内部错误"，详细堆栈写日志；生产环境关闭 `debug`。
5. **日志分级**：客户端错误（4xx）用 `WARNING` 或 `INFO`，服务端错误（5xx）用 `ERROR` 并附带堆栈（`logger.exception`）。
6. **带上请求标识**：日志里记录方法、路径，有条件的话记录请求 ID（12.10 中间件中实现），方便把用户反馈与日志对上。
7. **不要吞异常**：`except Exception: pass` 或 `except Exception: return {"ok": False}` 会让 bug 无声无息，宁可让它变成 500 被日志记录。
8. **覆盖 HTTP 处理器时注册 Starlette 的 `HTTPException`**，并保留 `exc.headers`。
9. **在文档中声明错误响应**：结合 12.5 的 `responses=`，让 API 使用者知道每个接口可能返回哪些错误。

## 常见坑

1. **`return HTTPException(...)` 而不是 `raise`**：返回的是一个异常对象，会被当作普通数据序列化，客户端拿到 200。
2. **注册 `fastapi.HTTPException` 处理器想接管 404**：框架的路由 404 抛的是 Starlette 父类，匹配不到。
3. **覆盖 HTTP 处理器时丢失 `headers`**：401 的 `WWW-Authenticate` 等头没了。
4. **原样返回 `exc.errors()`**：`ctx` 中可能有异常对象，直接 `JSONResponse` 序列化失败，需 `jsonable_encoder` 或挑字段。
5. **生产环境开 `debug=True`**：堆栈直接返回给任何人。
6. **500 响应里放 `str(exc)`**：可能包含 SQL 语句、文件路径等敏感信息。
7. **期望 `Exception` 处理器的响应带 CORS 头**：它在中间件之外，可预期错误应定义为业务异常。
8. **测试中 500 接口直接抛异常**：`TestClient` 默认重新抛出服务端异常，测试 500 响应时需要 `raise_server_exceptions=False`。
9. **在 `try/except Exception` 中把 `HTTPException` 也吞掉了**：在宽泛的 `except` 之前先 `except HTTPException: raise`。

## 小结

- FastAPI 中错误有三种来源：校验错误（422）、`HTTPException`（你或框架主动抛）、未捕获异常（500）。
- 用 `raise HTTPException(status_code, detail, headers)` 主动返回错误，`detail` 可为任意 JSON。
- 用自定义异常类 + `@app.exception_handler` 把业务异常翻译成 HTTP 响应，实现服务层与 HTTP 解耦；处理器按 MRO 匹配。
- 覆盖 `RequestValidationError` 和 Starlette 的 `HTTPException` 处理器可以定制默认响应；`fastapi.exception_handlers` 中的默认处理器可复用。
- 设计 `code` / `message` / `details` 统一错误格式，并用 `Exception` 处理器兜底，500 时只记日志、不泄露细节。
- `Exception` 处理器的响应不经过中间件，可预期的错误应定义为业务异常。
