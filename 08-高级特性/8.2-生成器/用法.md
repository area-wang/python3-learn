# 8.2 生成器

`yield` 关键字、生成器函数的基本用法，以及"为什么生成器省内存"已经在 [3.8-生成器函数](../../03-函数/3.8-生成器函数/用法.md) 讲过，这里不再重复。本节站在更高的视角看生成器：生成器表达式与推导式的取舍、`yield from` 委托子生成器时异常与关闭信号如何传播、`send()` 如何把生成器变成一个能双向通信的协程雏形、生成器内部的状态机，以及生成器与后面 8.7 协程一章的历史渊源。

## 1. 生成器表达式 vs 推导式

生成器表达式用 `()` 包裹，语法与列表/集合/字典推导式几乎一致，但求值方式完全不同：推导式立即构造出完整容器，生成器表达式只记录"如何产出"，元素在被消费时才逐个计算。

| 写法 | 语法 | 返回类型 | 求值时机 |
|---|---|---|---|
| 列表推导式 | `[x for x in it]` | `list` | 立即，全部算完 |
| 集合推导式 | `{x for x in it}` | `set` | 立即，全部算完 |
| 字典推导式 | `{k: v for k, v in it}` | `dict` | 立即，全部算完 |
| 生成器表达式 | `(x for x in it)` | `generator` | 惰性，按需一个个算 |

```python
squares_list = [x * x for x in range(5)]      # [0, 1, 4, 9, 16]
squares_set = {x * x for x in range(5)}        # {0, 1, 4, 9, 16}
squares_dict = {x: x * x for x in range(5)}    # {0: 0, 1: 1, 2: 4, 3: 9, 4: 16}
squares_gen = (x * x for x in range(5))        # <generator object ...>
print(list(squares_gen))                        # [0, 1, 4, 9, 16]
```

内存占用差异随数据量增大而放大：

```python
import sys

lst = [x * x for x in range(100_000)]
gen = (x * x for x in range(100_000))

print(sys.getsizeof(lst))   # 800984 —— 随元素数量线性增长
print(sys.getsizeof(gen))   # 112 —— 固定大小，无论 range 多大
```

生成器表达式没有对应的"集合版"或"字典版"——想要 `set`/`dict` 的惰性等价物，只能先写生成器表达式再交给 `set()`/`dict()` 消费一次：

```python
pairs = ((i, i * i) for i in range(5))
print(dict(pairs))   # {0: 0, 1: 1, 2: 4, 3: 9, 4: 16}
```

## 2. 何时用生成器表达式，何时用推导式

| 场景 | 推荐 |
|---|---|
| 结果只用一次，用完即弃（如传给 `sum`/`max`/`any`） | 生成器表达式 |
| 需要多次遍历、索引访问、`len()` | 推导式（列表/集合/字典） |
| 数据量很大甚至无限 | 生成器表达式 |
| 需要立即触发副作用（比如强制求值报错） | 推导式 |

```python
# 只求和，用生成器表达式不产生中间列表
total = sum(x * x for x in range(10_000_000))

# 需要多次使用结果，构造列表更合适
values = [x * x for x in range(100)]
print(values[0], values[-1], len(values))
```

作为函数唯一参数时，生成器表达式外层括号可以省略：`sum(x for x in it)`；但如果还有其他参数，必须显式加括号：`sum((x for x in it), start=100)`。

## 3. 生成器表达式的求值时机陷阱

生成器表达式创建时，**最外层 `for` 子句的可迭代对象会被立即求值**；其余部分（包括嵌套的 `for`/`if`）则延迟到真正迭代时才求值。这一点常常被忽视：

```python
n = 3
g = (x for x in range(n))
n = 100          # 不影响 g，因为 range(n) 在创建 g 时已用 n=3 求值
print(list(g))   # [0, 1, 2]
```

但内层子句每次迭代都会重新求值，会看到外部变量的最新状态：

```python
m = [1, 2, 3]
g2 = (y for x in range(2) for y in range(x, x + len(m)))
m.append(99)      # 消费 g2 之前修改 m，len(m) 变成 4
print(list(g2))    # [0, 1, 2, 3, 1, 2, 3, 4] —— 内层用的是最新的 len(m)
```

写复杂的多层生成器表达式时，如果依赖的外部变量会变化，结果可能和直觉不符，建议改写成显式的生成器函数以提高可读性。

## 4. `yield from`：委托的语义细节

`yield from iterable` 把控制权委托给内层可迭代对象，逐个转发它产出的值；`iterable` 不一定是生成器，任何可迭代对象都可以：

```python
def flatten_shallow():
    yield from [1, 2, 3]
    yield from "ab"
    yield from range(2)

print(list(flatten_shallow()))   # [1, 2, 3, 'a', 'b', 0, 1]
```

当委托对象确实是生成器时，`yield from` 不仅转发 `yield` 产出的值，还会把调用方对外层生成器的 `send()`、`throw()`、`close()` 原样转发给内层生成器，并把内层的返回值（`StopIteration.value`）作为 `yield from` 表达式的结果——这部分在 3.8 已经演示过基本用法，这里重点看异常和关闭信号的传播路径。

## 5. `yield from` 链路中的异常传播

`g.throw(exc)` 抛给外层生成器的异常，会沿着 `yield from` 链条一路转发到当前挂起的最内层生成器；如果内层捕获并继续产出值，这个值就成为 `throw()` 调用的返回值：

```python
def inner():
    try:
        while True:
            x = yield
            print("inner 收到:", x)
    except ValueError:
        print("inner 捕获 ValueError")
        yield "inner 恢复"
    finally:
        print("inner 清理")

def outer():
    yield from inner()

g = outer()
next(g)                       # 预激活，推进到 inner 内部的 yield
g.send("hi")                   # inner 收到: hi
print(g.throw(ValueError("boom")))
# inner 捕获 ValueError
# inner 恢复
g.close()                      # 触发 inner 的 finally 清理
# inner 清理
```

如果内层生成器没有捕获异常，异常会继续向上抛出到调用 `throw()` 的地方，就像普通函数调用栈一样。同理，`g.close()` 会向当前挂起点注入 `GeneratorExit`，这个信号也会顺着 `yield from` 链条传给最内层，触发它的 `finally` 清理逻辑，最终外层生成器才真正关闭。

## 6. `send()`：把生成器用作协程

`send(value)` 把 `value` 送回 `yield` 表达式的位置，从而实现"外部 → 生成器"的数据流；3.8 已经介绍过预激活规则和基础用法，这里演示两个更实用的模式。

### 6.1 用装饰器自动预激活

手工在每次创建生成器后调用一次 `next()` 容易漏掉，可以封装成装饰器：

```python
from functools import wraps

def prime(gen_func):
    """自动预激活生成器，调用方无需再手动 next() 一次"""
    @wraps(gen_func)
    def wrapper(*args, **kwargs):
        g = gen_func(*args, **kwargs)
        next(g)
        return g
    return wrapper

@prime
def running_average():
    total, count = 0, 0
    average = None
    while True:
        value = yield average
        total += value
        count += 1
        average = total / count

avg = running_average()
print(avg.send(10))   # 10.0
print(avg.send(20))   # 15.0
print(avg.send(30))   # 20.0
```

### 6.2 双向通信：既接收又反馈

`yield` 表达式的值来自上一次 `send()`，同时又可以把处理结果 `yield` 回去，形成一来一回的对话式接口，这正是"生成器即协程雏形"的核心：外部代码通过 `send()` 喂数据，生成器通过 `yield` 返回处理结果，中间的状态（`total`、`count`）由生成器自己维护，不需要额外的类或全局变量。

## 7. `throw()` 与 `close()`：异常注入与资源清理

`throw()` 用于在生成器当前挂起的位置注入异常，`close()` 则是注入固定的 `GeneratorExit`，二者的组合常用来实现"取消正在进行的惰性任务并保证清理"。

### 7.1 用 `try/finally` 保证清理一定执行

```python
def managed_resource():
    print("获取资源")
    try:
        yield "resource"
    finally:
        print("释放资源")   # 无论正常耗尽、close() 还是异常，都会执行

g = managed_resource()
next(g)
g.close()   # 获取资源 -> 释放资源
```

### 7.2 `close()` 期间不允许再产出值

`GeneratorExit` 是一种特殊信号：生成器捕获它之后只能选择结束（`return`/自然落出 `try` 块）或重新抛出，**不能再 `yield` 一个新值**，否则 Python 会把它视为"生成器无视了关闭请求"并抛出 `RuntimeError`：

```python
def bad_cleanup():
    try:
        yield 1
    except GeneratorExit:
        print("收到关闭信号")
        yield 2   # 错误：close() 期间不允许再产出值

g = bad_cleanup()
next(g)
try:
    g.close()
except RuntimeError as e:
    print("RuntimeError:", e)   # RuntimeError: generator ignored GeneratorExit
```

这个陷阱在写基于生成器的资源管理器（例如 `contextlib.contextmanager`）时尤其要注意：`finally` 块里只应该做清理动作，不应该再 `yield`。

## 8. 生成器的内部状态机

每个生成器对象在生命周期中处于四种状态之一，可以用 `inspect.getgeneratorstate()` 查看：

| 状态 | 含义 |
|---|---|
| `GEN_CREATED` | 刚创建，尚未开始执行 |
| `GEN_RUNNING` | 正在执行（只有在生成器内部反射式地检查自身时才可能观察到，正常代码几乎看不到这个状态） |
| `GEN_SUSPENDED` | 在某个 `yield` 处挂起，等待下一次 `next()`/`send()` |
| `GEN_CLOSED` | 已执行完毕、`return`、抛出未捕获异常，或被 `close()` 关闭 |

```python
import inspect

def demo():
    x = yield "a"
    y = yield "b"

g = demo()
print(inspect.getgeneratorstate(g))   # GEN_CREATED
next(g)
print(inspect.getgeneratorstate(g))   # GEN_SUSPENDED
print(g.gi_frame is not None, g.gi_running)   # True False
g.close()
print(inspect.getgeneratorstate(g))   # GEN_CLOSED
print(g.gi_frame)                      # None —— 帧已被释放
```

几个常用的内省属性：

| 属性 | 说明 |
|---|---|
| `gi_frame` | 生成器当前挂起处的帧对象；关闭后为 `None` |
| `gi_running` | 生成器是否正处于执行中（防止递归重入） |
| `gi_code` | 生成器函数编译得到的代码对象 |
| `gi_yieldfrom` | 当前正在 `yield from` 委托的子生成器；不涉及委托时为 `None` |

理解这套状态机有助于排查"生成器为什么卡住了""为什么再次 `send` 报错"之类的问题：本质上都是在错误的状态下发起了操作（比如对 `GEN_CLOSED` 的生成器再 `next()` 会直接抛 `StopIteration`）。

## 9. 生成器与协程的渊源

`send()`/`throw()`/`close()` 是 PEP 342（Python 2.5）为生成器新增的能力，其初衷就是让生成器承担"协程"的角色：函数可以被外部驱动、暂停、注入数据和异常。在 `async`/`await` 语法（PEP 492）出现之前，早期的 `asyncio` 正是用 `@asyncio.coroutine` 装饰器加 `yield from` 来编写协程的——`yield from` 委托恰好可以把一层层嵌套的"等待"逐层转发给事件循环。

今天的 `async def`/`await` 本质上是这套机制的语法升级：协程对象在概念上仍然是"可以被挂起和恢复的状态机"，只是不再借用 `yield` 语义，而是有了专属的语法和调度方式。这段历史脉络会在 [8.7-协程](../8.7-协程/) 中展开，本节不涉及 `async`/`await` 本身，只需要记住：生成器的 `send`/`throw`/`close` 三件套，是理解协程语义的重要铺垫。

## 10. 本节小结

1. 生成器表达式 `(x for x in ...)` 与列表/集合/字典推导式语法相似但求值方式不同：推导式立即构造完整容器，生成器表达式惰性按需产出，内存占用恒定；
2. 生成器表达式创建时最外层 `for` 的可迭代对象立即求值，其余子句延迟到迭代时求值，依赖外部可变状态时容易产生反直觉的结果；
3. `yield from` 可以委托任意可迭代对象，若委托对象是生成器，还会转发调用方的 `send()`/`throw()`/`close()`，并把内层的返回值作为 `yield from` 表达式的结果；
4. `throw()` 注入的异常和 `close()` 注入的 `GeneratorExit` 都会沿 `yield from` 链条传给当前挂起的最内层生成器，逐层向外传播或触发清理；
5. `send()` 让生成器变成可以双向通信的协程雏形，第一次必须先用 `next()` 或 `send(None)` 预激活，可用装饰器自动化这一步；
6. 生成器捕获 `GeneratorExit` 后只能结束或重新抛出，不能再 `yield` 新值，否则触发 `RuntimeError`，编写基于生成器的资源管理器时要格外注意；
7. `inspect.getgeneratorstate()` 可以查看生成器所处的四种状态（created/running/suspended/closed），`gi_frame`/`gi_running`/`gi_yieldfrom` 等属性能帮助排查生成器相关的疑难问题；
8. `send`/`throw`/`close` 是 PEP 342 为生成器引入的协程能力，是理解 `async`/`await`（见 8.7-协程）历史渊源和语义的重要基础。
