# 8.2 生成器练习题

## 一、概念题

1. 生成器表达式 `(x for x in ...)` 与列表推导式、集合推导式、字典推导式相比，语法差异是什么？返回类型和求值时机分别有什么不同？
2. 生成器表达式创建时，哪一部分会被立即求值？哪一部分会延迟到迭代时才求值？举一个会因此产生反直觉结果的场景。
3. 什么场景应该优先用生成器表达式，什么场景应该优先用列表/集合/字典推导式？
4. `yield from` 除了转发生成器产出的值之外，还会转发调用方的哪些操作？它委托的对象是否必须是生成器？
5. 当外层生成器被 `throw()` 注入异常时，异常是如何沿着 `yield from` 链条传播到最内层的？如果内层没有捕获，会发生什么？
6. `close()` 会向生成器注入什么信号？生成器在捕获这个信号后可以做什么，不可以做什么？
7. 为什么在 `except GeneratorExit` 块里再 `yield` 一个值会导致 `RuntimeError`？
8. `send()` 第一次调用为什么必须先 `next()` 预激活？如果直接 `send(非 None 值)` 会发生什么？
9. 生成器有哪几种状态？分别通过什么方式可以观察到当前状态？
10. `send`/`throw`/`close` 这套机制最初是为了解决什么问题引入的？它与后面 `async`/`await` 的关系是什么？

### 2. 生成器表达式只能消费一次

print(sum(gen))

### 3. yield from 转发 send

```python
def inner():
    total = 0
    while True:
        x = yield total
        total += x

def outer():
    yield from inner()

g = outer()
print(next(g))
print(g.send(5))
print(g.send(10))
```

写出输出，并说明 `send` 的值是如何"穿过" `outer` 到达 `inner` 的。

### 4. throw 沿 yield from 传播

```python
def inner():
    try:
        yield 1
        yield 2
    except ValueError:
        yield 99

def outer():
    yield from inner()
    yield "outer done"

g = outer()
print(next(g))
print(g.throw(ValueError("x")))
print(next(g))
```

写出三行输出，并解释 `outer` 本身并没有写任何 `try/except`，为什么 `ValueError` 还是被 `inner` 捕获了。

### 5. GeneratorExit 与 RuntimeError

```python
def f():
    try:
        yield 1
    except GeneratorExit:
        yield 2

g = f()
next(g)
try:
    g.close()
    print("closed normally")
except RuntimeError as e:
    print("caught:", e)
```

写出输出，并说明触发这个结果的规则是什么。

### 6. 生成器状态

```python
import inspect

def f():
    yield 1
    yield 2

g = f()
print(inspect.getgeneratorstate(g))
next(g)
print(inspect.getgeneratorstate(g))
list(g)
print(inspect.getgeneratorstate(g))
```

## 三、编程题

### 1. 惰性数据管道

编写 `pipeline(numbers)`，用生成器表达式（可以嵌套多个）依次完成：过滤出偶数、每个数平方、再过滤出大于 10 的结果，要求：

- 全程不产生中间列表，只用生成器表达式串联；
- 返回一个生成器对象，调用方决定何时消费；
- 用 `list(pipeline(range(10)))` 验证结果。

### 2. 委托式文件多路读取器

实现生成器函数 `read_many(paths)`：

- 对 `paths` 中的每个文件路径，用 `yield from` 委托一个内部生成器 `read_one(path)` 逐行产出该文件内容（去掉行尾换行符）；
- `read_one` 内部使用 `try/finally` 确保文件被关闭；
- 如果某个路径不存在，捕获 `FileNotFoundError` 并 `yield` 一条形如 `f"[跳过] {path}"` 的提示，继续处理下一个文件，而不是让整个 `read_many` 中断。

### 3. 可取消的双向累加器

实现一个用 `@prime`（自定义预激活装饰器）包装的生成器 `cancellable_accumulator()`：

- 通过 `send(x)` 累加数值并返回当前累计和；
- 支持 `throw(RuntimeError)` 注入"重置"信号：捕获后把累计和清零，并继续接收后续 `send`；
- 支持 `close()`：在 `finally` 中打印一条"累加器已关闭，最终累计值为 ..."的日志。

### 4. 状态查看装饰器

实现装饰器 `with_state_log(gen_func)`：

- 包裹一个生成器函数，每次调用 `next()`/`send()` 前后，用 `inspect.getgeneratorstate()` 打印生成器的状态变化（例如 `"GEN_SUSPENDED -> GEN_SUSPENDED"`）；
- 生成器执行完毕或被关闭后，状态变化应显示为 `"... -> GEN_CLOSED"`；
- 不改变被包裹生成器本身对外暴露的行为（依然可以正常 `send`/`throw`/`close`）。

## 四、综合实践：基于生成器的简易任务调度器

用生成器实现一个"协作式"任务调度器，模拟多个任务交替执行，不使用 `threading`/`asyncio`：

1. 每个任务是一个生成器函数，内部通过 `yield` 表达"我在这里让出控制权，等下次被调度时继续"；
2. 编写调度器 `run(tasks)`，接收多个任务生成器，轮流对每个任务调用 `next()`，直到全部任务耗尽（捕获 `StopIteration`）；
3. 支持任务之间传递消息：某个任务可以 `yield ("send_to", task_name, value)` 这样的元组，让调度器把 `value` 通过 `send()` 交给名为 `task_name` 的任务；
4. 任一任务在执行中抛出未捕获异常时，调度器应该用 `throw()` 把这个异常告知其余仍在运行的任务（可选：让它们各自决定是否要清理资源并提前 `close()`）；
5. 调度器退出前，对所有还未耗尽的任务调用 `close()`，确保 `finally` 清理逻辑被执行；
6. 用 `inspect.getgeneratorstate()` 在调度日志中打印每个任务当前的状态，验证调度过程中任务确实在 `GEN_SUSPENDED` 与 `GEN_CLOSED` 之间切换；
7. 思考：这个简易调度器和真正的 `asyncio` 事件循环相比缺了什么能力？为什么 `async`/`await` 最终取代了手写的 `yield`-based 协程调度（不需要写代码，用一段话回答）。
