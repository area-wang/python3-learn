# 8.7 协程

协程（coroutine）是一种可以在执行过程中挂起、并在稍后从挂起点恢复执行的函数。本节聚焦协程本身的语言级语义——`async def`/`await` 语法、协程对象的本质、事件循环的最基本概念、协程的生命周期状态——不涉及 `Task`、`Future`、`asyncio.gather`、并发原语等 asyncio 工具箱内容，那些留给 8.8 异步编程详细展开。理解本节内容是看懂 8.8 一切工具的前提。

## 1. 从生成器到原生协程：一段简史

Python 的协程并不是一开始就长现在这个样子，而是经历了三个阶段演化而来：

| 阶段 | 特性 | 引入版本 | 现状 |
|---|---|---|---|
| 基于生成器的协程雏形 | `yield` 表达式可以接收 `send()` 传入的值 | PEP 342（Python 2.5） | 仍是生成器语法基础 |
| 委托生成器 | `yield from` 可以把子生成器的值透明地转发给调用者 | PEP 380（Python 3.3） | 早期 asyncio（`@asyncio.coroutine` + `yield from`）就建立在它之上 |
| 原生协程 | `async def`/`await` 成为独立的语法和类型 | PEP 492（Python 3.5） | 当前标准写法 |

在原生协程出现之前，asyncio 的协程是这样写的：

```python
import asyncio

@asyncio.coroutine
def old_style_coroutine():
    yield from asyncio.sleep(1)
    return "done"
```

这种"生成器伪装成协程"的写法有几个明显问题：

- **语义混乱**：一个函数到底是普通生成器（用来迭代产出值）还是协程（用来表达异步流程），只能靠装饰器和文档区分，解释器和类型系统都无法从语法上判断；
- **误用风险**：忘记 `yield from` 直接调用协程函数、把协程当生成器去 `for` 循环遍历，这类错误在生成器协程时代很常见且难以静态发现；
- **无法与普通生成器区分**：`inspect.isgenerator()` 对两者返回的都是 `True`，工具链无法可靠地识别"这是一个协程"。

PEP 492 引入 `async def`、`await`、`async for`、`async with`，让协程成为独立的类型（`types.CoroutineType`），从语法层面把"协程"和"生成器"彻底分开。`@asyncio.coroutine` 装饰器和生成器版协程从 Python 3.8 起触发 `DeprecationWarning`，并已在 **Python 3.11 中被彻底移除**。现在唯一推荐、唯一支持的写法就是原生协程。

## 2. `async def`：定义一个协程函数

用 `async def` 定义的函数称为**协程函数**（coroutine function）。关键认知：调用协程函数**不会执行函数体**，而是立即返回一个**协程对象**（coroutine object）。

```python
async def greet(name):
    print(f"你好，{name}")
    return f"greet({name}) 完成"

result = greet("小明")
print(type(result))   # <class 'coroutine'>
print(result)          # <coroutine object greet at 0x...>
```

运行上面的代码，你会发现 `"你好，小明"` 根本没有被打印出来——因为函数体一行都没执行。协程对象只是一份"待执行的计划书"，必须被 `await`，或者被提交给事件循环调度，函数体才会真正运行。

```python
import asyncio

async def main():
    text = await greet("小明")   # 只有在这里函数体才真正开始执行
    print(text)

asyncio.run(main())
# 你好，小明
# greet(小明) 完成
```

不 `await` 直接丢弃协程对象，解释器会发出警告：

```python
async def leak():
    await asyncio.sleep(0.1)

leak()   # 没有 await，也没有交给事件循环
# 程序退出前会看到：
# RuntimeWarning: coroutine 'leak' was never awaited
```

这是初学者最常见的坑：**调用协程函数 ≠ 运行协程**，只有 `await` 或调度执行才会真正跑起来。

## 3. `await`：挂起并等待结果

`await` 只能出现在 `async def` 函数体内部（否则是 `SyntaxError`），作用是：

1. 把当前协程挂起，把控制权交还给事件循环；
2. 让事件循环去推进 `await` 后面那个对象的执行；
3. 等它完成后，把结果作为 `await` 表达式的值，恢复当前协程继续往下执行。

`await` 后面并不能接任意对象，只能接**可等待对象**（awaitable）。可等待对象有三类：

| 类型 | 说明 |
|---|---|
| 协程对象（coroutine） | `async def` 函数调用后得到的对象，本节的核心 |
| `Task` | 对协程的进一步包装，让协程可以"独立调度、并发运行"，8.8 详细讲解 |
| `Future` | 表示一个尚未完成的底层结果占位符，比 `Task` 更底层，8.8 详细讲解 |

判断一个对象是否可等待，可以用 `inspect.isawaitable()`：

```python
import inspect

async def foo():
    return 1

coro = foo()
print(inspect.isawaitable(coro))   # True
print(inspect.isawaitable(42))     # False
coro.close()   # 用不到的协程对象要主动关闭，避免警告
```

本节只把 `Task`/`Future` 作为"可等待对象家族的成员"简单提及；如何创建、调度、取消它们，是 8.8 的内容。

## 4. 事件循环：驱动协程的引擎

协程对象自己不会跑，必须有一个**事件循环**（event loop）在背后不断地：

1. 维护一个待执行的协程/回调队列；
2. 依次推进它们执行，直到遇到 `await` 挂起点；
3. 在等待的操作（如 I/O、`sleep`）就绪之前，切换去执行其他协程；
4. 就绪之后，恢复被挂起的协程继续执行。

这就是"协作式多任务"（cooperative multitasking）：协程之间不会被强制打断，而是在每个 `await` 点**主动让出**控制权。同一时刻永远只有一个协程在真正执行代码，其余的都挂起等待。

### 4.1 `asyncio.run()`：标准入口

`asyncio.run(coro)` 是运行顶层协程的标准方式，它负责：

- 创建一个新的事件循环；
- 运行传入的协程直到它完成；
- 关闭并清理这个事件循环。

```python
import asyncio

async def main():
    print("开始")
    await asyncio.sleep(1)
    print("1 秒后")

asyncio.run(main())
```

一个进程中，**同一时刻只应该有一个事件循环在运行**。`asyncio.run()` 内部会检查当前线程是否已经有一个正在运行的循环，如果有则抛出 `RuntimeError`，因此不要在协程内部再次调用 `asyncio.run()`。

### 4.2 事件循环不是并行执行

事件循环本身运行在单个线程里，`await` 点之间的代码是完全独立执行、互不打断的——这一点在第 8 节会详细对比"并发"与"并行"。

## 5. 协程对象的生命周期状态

协程对象在其生命周期中会经历几种状态，可以用 `inspect.getcoroutinestate()` 查看：

| 状态 | 含义 |
|---|---|
| `CORO_CREATED` | 协程对象刚创建，函数体尚未开始执行 |
| `CORO_RUNNING` | 协程正在执行（正处于被 `await`/驱动的那一刻） |
| `CORO_SUSPENDED` | 协程在某个 `await` 点被挂起，等待恢复 |
| `CORO_CLOSED` | 协程已执行完毕，或被 `close()` 关闭 |

```python
import asyncio
import inspect

async def worker():
    print("worker 开始")
    await asyncio.sleep(0.1)
    print("worker 结束")

async def main():
    coro = worker()
    print(inspect.getcoroutinestate(coro))   # CORO_CREATED

    task = asyncio.ensure_future(coro)  # 简单驱动它开始运行（Task 细节见 8.8）
    await asyncio.sleep(0)              # 让出一次控制权，使 worker 得以开始执行
    print(inspect.getcoroutinestate(coro))   # CORO_SUSPENDED（卡在 sleep(0.1) 上）

    await task
    print(inspect.getcoroutinestate(coro))   # CORO_CLOSED

asyncio.run(main())
```

直接调用 `coro.send(None)` 也能手动"推进"一个协程一步，这与生成器的 `send()` 是同一套底层机制——协程本质上仍由生成器式的帧挂起/恢复机制实现，只是语法和类型独立出来了。协程运行结束时会抛出 `StopIteration`，其 `value` 属性携带 `return` 的返回值，这与生成器完全一致。

## 6. 最小示例：协作式并发 vs 阻塞式等待

下面用一个最小例子对比 `time.sleep()`（阻塞）和 `await asyncio.sleep()`（协作式让出）的差别。

### 6.1 阻塞版本：`time.sleep()`

```python
import time

def task(name, seconds):
    print(f"{name} 开始")
    time.sleep(seconds)   # 阻塞整个线程，谁也跑不了
    print(f"{name} 结束，耗时 {seconds}s")

start = time.perf_counter()
task("A", 1)
task("B", 1)
print(f"总耗时：{time.perf_counter() - start:.2f}s")
# A 开始
# A 结束，耗时 1s
# B 开始
# B 结束，耗时 1s
# 总耗时：2.00s   —— 两个任务顺序执行，严格叠加
```

### 6.2 协作版本：`await asyncio.sleep()`

```python
import asyncio
import time

async def task(name, seconds):
    print(f"{name} 开始")
    await asyncio.sleep(seconds)   # 只挂起当前协程，把控制权交还事件循环
    print(f"{name} 结束，耗时 {seconds}s")

async def main():
    start = time.perf_counter()
    await task("A", 1)   # 注意：这里仍是顺序 await，尚未并发
    await task("B", 1)
    print(f"总耗时：{time.perf_counter() - start:.2f}s")

asyncio.run(main())
# 总耗时仍约 2.00s——因为两次 await 是顺序书写的，没有并发调度
```

单看 6.2，你会发现结果和阻塞版本一样慢——这是因为**协程本身只解决了"挂起点上不霸占线程"的问题，真正的并发调度需要事件循环同时驱动多个协程**，这正是 `asyncio.gather()`/`asyncio.create_task()` 要做的事（8.8 详细讲解）。这里只用一句话展示效果对比：

```python
async def main():
    start = time.perf_counter()
    await asyncio.gather(task("A", 1), task("B", 1))
    print(f"总耗时：{time.perf_counter() - start:.2f}s")
    # 总耗时约 1.00s —— 两个 sleep 是并发等待的

asyncio.run(main())
```

本节不深入 `gather` 的用法与陷阱，只需要理解：**协程提供了"可以被挂起和恢复"的语言能力，事件循环 + 调度工具提供了"多个协程交替推进"的并发能力**，两者分工不同。

## 7. 并发（Concurrency）与并行（Parallelism）

这是理解 asyncio 定位最关键的一组概念：

| 维度 | 并发（Concurrency） | 并行（Parallelism） |
|---|---|---|
| 定义 | 多个任务在**同一时间段内交替推进**，宏观上"看起来同时进行" | 多个任务在**同一时刻真正同时执行**，需要多个 CPU 核心 |
| asyncio 属于哪种 | 并发 | 不是并行 |
| 执行线程数 | 单线程 | 多线程/多进程 |
| 任务切换方式 | 协作式：代码主动在 `await` 处让出 | 抢占式或硬件级并行，操作系统/CPU 决定 |
| 适合的场景 | I/O 密集型（网络请求、磁盘、数据库） | CPU 密集型（大量计算） |

asyncio 的事件循环**始终运行在单个线程里**，它带来的是并发而非并行：多个协程通过在 `await` 点相互"礼让"来分时共享同一个线程的执行权，宏观上表现为多个任务同时推进，但任何一个瞬间都只有一段代码在真正运行。

这也意味着：

- asyncio **不能绕开 GIL（全局解释器锁）**，CPU 密集型的纯计算任务不会因为改写成协程而变快，反而可能因为长时间不 `await` 而"饿死"其他协程（因为它一直不让出控制权）；
- asyncio 真正的优势在于 I/O 密集型场景：等待网络响应、等待磁盘、等待数据库时，线程本可以闲置的时间被用来推进其他协程，从而大幅提高吞吐；
- 如果确实需要利用多核做并行计算，应该使用 `multiprocessing`，或者把 CPU 密集型代码丢进 `run_in_executor` 的线程/进程池（这属于 8.8 的调度话题）。

## 8. 本节小结

1. 协程经历了"生成器 + `yield from`"到"`async def`/`await` 原生语法"的演化，`@asyncio.coroutine` 已在 Python 3.11 中被彻底移除，现在只应使用原生协程；
2. 调用 `async def` 函数不会执行函数体，只会返回一个协程对象，必须 `await` 或交由事件循环调度才会真正运行；
3. `await` 只能用在协程函数内部，且只能作用于可等待对象：协程、`Task`、`Future`（后两者的用法留给 8.8）；
4. 事件循环是驱动协程的引擎，`asyncio.run()` 是运行顶层协程的标准入口，同一线程同一时刻只应有一个循环在运行；
5. 协程对象有 `CORO_CREATED`/`CORO_RUNNING`/`CORO_SUSPENDED`/`CORO_CLOSED` 四种状态，可用 `inspect.getcoroutinestate()` 查看，其底层机制仍是生成器式的帧挂起/恢复；
6. `await asyncio.sleep()` 是协作式让出，不会阻塞线程；但顺序 `await` 多个协程并不会自动并发，真正的并发调度依赖事件循环工具（如 `gather`），这是 8.8 的内容；
7. asyncio 提供的是单线程协作式并发，不是并行，无法绕开 GIL；它擅长 I/O 密集型场景，不适合 CPU 密集型计算。
