## 一、概念题

## 二、判断代码输出

### 1. 调用协程函数会立即执行吗

```python
async def step():
    print("A")
    print("B")
    return "C"

x = step()
print("main 先运行到这里")
```

写出输出。`step()` 内部的 `print` 语句会不会执行？为什么？

### 2. 协程状态变化

```python
import asyncio
import inspect

async def slow():
    await asyncio.sleep(0.05)

async def main():
    coro = slow()
    print(1, inspect.getcoroutinestate(coro))
    task = asyncio.ensure_future(coro)
    print(2, inspect.getcoroutinestate(coro))
    await asyncio.sleep(0)
    print(3, inspect.getcoroutinestate(coro))
    await task
    print(4, inspect.getcoroutinestate(coro))

asyncio.run(main())
```

写出四行输出中协程状态各是什么，并解释第 2 行和第 3 行为什么不同。

### 3. 顺序 await 与并发 await

```python
import asyncio
import time

async def job(name, seconds):
    await asyncio.sleep(seconds)
    return name

async def main():
    start = time.perf_counter()
    a = await job("A", 1)
    b = await job("B", 1)
    print(a, b, f"{time.perf_counter() - start:.0f}s")

asyncio.run(main())
```

预测大约耗时多久。如果把最后三行改成 `results = await asyncio.gather(job("A", 1), job("B", 1))`，耗时会怎样变化？为什么（不要求掌握 `gather` 细节，只需说明协程挂起点和调度的关系）？

### 4. `time.sleep()` 混入协程

```python
import asyncio
import time

async def bad_task(name):
    print(f"{name} 开始")
    time.sleep(1)   # 注意：这里用的是 time.sleep 而不是 await asyncio.sleep
    print(f"{name} 结束")

async def main():
    await asyncio.gather(bad_task("A"), bad_task("B"))

start = time.perf_counter()
asyncio.run(main())
print(f"总耗时：{time.perf_counter() - start:.0f}s")
```

这里两个任务是否真的并发执行了？说明 `time.sleep()` 在协程里为什么会破坏协作式调度。

## 三、编程题

### 1. 协程对象探针

编写函数 `inspect_coroutine(coro_func, *args)`：

- 接收一个协程函数和参数，调用得到协程对象但先不 `await`；
- 用 `inspect.iscoroutinefunction()` 确认传入的确实是协程函数；
- 打印协程对象创建后的初始状态；
- 通过 `asyncio.run()` 包装的方式驱动它执行完毕，并打印执行前后的状态变化；
- 要求整个函数本身是同步函数（不是 `async def`），内部自行创建事件循环运行。

### 2. 手动单步驱动协程

编写一个不使用 `asyncio.run()`、只用协程底层接口驱动的小例子：

- 定义一个 `async def counter()`，内部用 `await asyncio.sleep(0)` 分隔打印三次不同的数字；
- 使用 `coro.send(None)` 反复推进这个协程，每次推进后打印一次 `inspect.getcoroutinestate()`；
- 捕获协程结束时抛出的 `StopIteration`，打印其 `.value`（如果 `counter` 有返回值）；
- 说明这个手动驱动过程和 `asyncio.run()` 内部做的事情有何相似之处。

### 3. 阻塞 vs 非阻塞耗时对比器

编写函数 `compare_blocking_vs_async(n, seconds)`：

- 用 `time.sleep(seconds)` 顺序执行 `n` 次模拟任务，记录总耗时；
- 用 `async def` + `await asyncio.sleep(seconds)`，通过 `asyncio.gather` 并发执行 `n` 个任务，记录总耗时；
- 打印两种方式的耗时对比，并断言并发版本明显快于顺序阻塞版本；
- 用一句注释说明：这个对比能不能类比到 CPU 密集型任务？为什么不能。

### 4. 未 `await` 检测器

编写一个上下文管理器 `warn_on_leak()`：

- 进入时清空 Python 的警告过滤记录；
- 退出时检测是否产生过 `RuntimeWarning: coroutine ... was never awaited`；
- 在 `with warn_on_leak():` 代码块中故意调用一个协程函数但不 `await`，验证你的检测器能捕获到这个警告；
- 提示：可以使用 `warnings.catch_warnings(record=True)`。

## 四、综合实践：一个最小"协程状态可视化"工具

编写一个函数 `trace_coroutine(coro, poll_interval=0.01)`，用于观察一个协程对象在其生命周期中的状态迁移轨迹，要求：

1. 接收一个已经创建但还未运行的协程对象（不能是已经关闭的）；
2. 内部创建一个事件循环（或使用 `asyncio.run()` 包装一个内部协程）来驱动它执行；
3. 在驱动过程中，每隔 `poll_interval` 秒记录一次 `inspect.getcoroutinestate(coro)`，直到协程进入 `CORO_CLOSED`；
4. 最终返回一个列表，形如 `["CORO_CREATED", "CORO_SUSPENDED", "CORO_SUSPENDED", "CORO_CLOSED"]`，展示状态迁移的完整轨迹（允许出现连续重复的状态，因为轮询间隔和协程真实挂起时长不一定对齐）；
5. 用一个内部至少包含两次 `await asyncio.sleep(...)` 的协程函数测试你的工具，并打印轨迹；
6. 思考并回答：如果被追踪的协程内部混入了一次 `time.sleep()`（同步阻塞），你的轮询轨迹会出现什么异常现象？这说明了什么？
