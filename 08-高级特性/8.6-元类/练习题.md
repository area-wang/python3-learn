# 8.6 元类练习题

## 一、概念题

1. 为什么说 `type` 既是内置函数又是元类？`type(obj)` 和 `type(name, bases, namespace)` 分别在做什么？
2. `class Foo(Base, metaclass=Meta): ...` 语句执行时，`__prepare__`、`__new__`、`__init__` 分别在什么阶段被调用，各自的职责是什么？
3. 元类的 `__new__` 和 `__init__` 有什么区别？分别应该在什么场景下重写？
4. `__init_subclass__` 能替代元类的哪些常见用途？它和元类相比缺失了哪些能力？
5. `ABC` 与 `metaclass=ABCMeta` 是什么关系？为什么抽象类不能直接实例化？
6. 一个类可以指定多个元类吗？多重继承时如果两个基类的元类不同会发生什么？
7. 为什么通过重写元类的 `__call__` 能实现单例模式？它和重写普通类的 `__new__` 实现单例有什么本质区别？
8. 列举至少三个「不应该使用元类」的场景，并说明各自更合适的替代方案。
9. `type(name, bases, namespace)` 中的 `namespace` 参数对应 `class` 语句里的哪一部分？如果直接修改它会产生什么效果？
10. 为什么说元类是「深层魔法」？如果团队中有人滥用元类，可能给协作带来哪些具体问题？

## 二、判断代码输出

### 1. `type` 的自指关系

```python
class A:
    pass

print(type(A) is type)
print(type(type) is type)
print(isinstance(A, type))
print(isinstance(type, object))
```

写出四行输出，并说明 `type` 为什么被称为「自己的元类」。

### 2. 元类方法的调用顺序

```python
class Meta(type):
    def __new__(mcs, name, bases, namespace):
        print(f"__new__: {name}")
        return super().__new__(mcs, name, bases, namespace)

    def __init__(cls, name, bases, namespace):
        print(f"__init__: {name}")
        super().__init__(name, bases, namespace)

    def __call__(cls, *args, **kwargs):
        print(f"__call__: {cls.__name__}")
        return super().__call__(*args, **kwargs)


class Widget(metaclass=Meta):
    def __init__(self, label):
        print(f"Widget.__init__: {label}")
        self.label = label


w = Widget("button")
```

写出完整的输出顺序，解释为什么 `Meta.__new__`/`Meta.__init__` 只在类定义时触发一次，而 `Meta.__call__` 会在每次实例化 `Widget(...)` 时触发。

### 3. `__init_subclass__` 的隐式调用

```python
class Base:
    subclasses = []

    def __init_subclass__(cls, category=None, **kwargs):
        super().__init_subclass__(**kwargs)
        Base.subclasses.append((cls.__name__, category))


class Cat(Base, category="animal"):
    pass


class Table(Base, category="furniture"):
    pass


class Sofa(Table):
    pass

print(Base.subclasses)
```

写出输出。`Sofa` 的 `category` 应该是什么？说明关键字参数在没有显式传递时如何被继承或丢失。

## 三、编程题

### 1. 手写一个「冻结」元类

实现元类 `FrozenMeta`：

- 用它创建的类，实例在 `__init__` 执行完毕后不允许再新增或修改任何实例属性；
- 尝试修改会抛出 `AttributeError` 并给出清晰提示；
- 通过在元类中包装被修饰类的 `__init__`（或使用 `__setattr__`）实现「初始化期可写、之后只读」。

### 2. 接口强制元类

实现元类 `InterfaceMeta`：

- 允许某个基类通过类属性 `abstract_methods = (...)` 声明必须被子类实现的方法名列表；
- 子类定义时如果没有实现全部列出的方法，在类创建阶段就抛出 `TypeError`，并在异常信息中列出缺失的方法名；
- 基类自身（`abstract_methods` 声明处）不受此检查约束。

### 3. 自动注册 + 工厂函数

实现一套插件体系：

- 元类 `PluginMeta` 维护一个 `registry: dict[str, type]`，子类定义时按类属性 `name` 自动注册；
- 提供工厂函数 `create_plugin(name, *args, **kwargs)`，根据注册表实例化对应插件；
- 若请求了未注册的 `name`，抛出 `KeyError` 并提示当前可用的插件名列表；
- 额外思考：如果同一个 `name` 被两个类重复注册，应该报错还是覆盖？给出你的设计并说明理由。

### 4. 用 `__init_subclass__` 重写单例

- 先实现一版基于元类 `SingletonMeta` 的单例（参考用法.md 第 10 节）；
- 再尝试仅用 `__init_subclass__` 加一个类方法（例如 `get_instance()`）实现类似效果，不重写 `__call__`；
- 对比两种实现：直接 `MyClass()` 调用的行为是否一致？哪种方案更符合「最小惊讶原则」？分别写出优缺点。

## 四、综合实践：声明式配置校验框架

设计一个小型「声明式」配置系统，模拟 ORM 字段校验的思路，要求综合运用元类和描述符：

1. 定义 `Field` 类，支持声明类型（`field_type`）、是否必填（`required`）、默认值（`default`）；
2. 编写元类 `ConfigMeta`，在类创建时收集所有 `Field` 类属性到 `_fields` 字典，并检查：
   - 字段名不能以下划线开头；
   - 若某字段 `required=True` 又设置了 `default`，在类创建阶段直接抛出 `TypeError`（二者语义冲突）；
3. 定义基类 `Config(metaclass=ConfigMeta)`，其 `__init__(self, **kwargs)` 根据 `_fields` 对传入参数做类型校验、必填校验、缺省值填充；
4. 提供 `to_dict()` 方法导出当前配置为普通字典；
5. 用你的框架定义一个 `ServerConfig`（至少包含 `host: str`、`port: int`、`debug: bool` 三个字段，`debug` 有默认值 `False`），演示正常创建、类型错误、缺少必填字段三种场景的报错信息；
6. 思考并写一段简短说明：这里哪些逻辑必须放在元类里（类创建阶段），哪些可以下放到 `__init_subclass__` 或普通 `__init__`（实例创建阶段）？如果整个框架只用 `__init_subclass__` 重写，会在哪一步遇到困难？
