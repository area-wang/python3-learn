# 8.3 装饰器进阶

3.7 节已经介绍了装饰器的基本概念：`@decorator` 语法糖、带参数的装饰器（三层嵌套）、以及用 `functools.wraps` 保留 `__name__`/`__doc__`。这些是理解本节的前提，这里不再重复讲解。本节聚焦更进阶的话题：多个装饰器如何叠加、如何用类实现有状态的装饰器、如何让装饰器不破坏函数签名、以及标准库里几个开箱即用的强力装饰器（`singledispatch`、`lru_cache`）。

## 1. 装饰器链：叠加与展开顺序

多个装饰器叠加时，**应用顺序自下而上，执行顺序自上而下**（洋葱模型），这一点 3.7 节已提到。这里重点是把它**精确展开**成嵌套调用，避免记混。

```python
@decorator_a
@decorator_b
@decorator_c
def handler():
    pass

# 完全等价于：
def handler():
    pass
handler = decorator_a(decorator_b(decorator_c(handler)))
```

应用顺序：`decorator_c` 最先包裹原函数，`decorator_a` 最后包裹，离函数最近的装饰器最先生效。

```python
from functools import wraps

def trace(tag):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            print(f"进入 {tag}")
            result = func(*args, **kwargs)
            print(f"离开 {tag}")
            return result
        return wrapper
    return decorator

@trace("A")
@trace("B")
@trace("C")
def handler():
    print("核心逻辑")

handler()
# 进入 A
# 进入 B
# 进入 C
# 核心逻辑
# 离开 C
# 离开 B
# 离开 A
```

### 1.1 顺序会改变语义

装饰器链不是无关紧要的排列组合，顺序不同结果可能完全不同。典型例子：`lru_cache` 和记录调用日志的装饰器谁在外层。

```python
from functools import lru_cache, wraps

def log_call(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        print(f"调用 {func.__name__}{args}")
        return func(*args, **kwargs)
    return wrapper

@log_call
@lru_cache(maxsize=None)
def slow_square(n):
    return n * n

slow_square(4)
slow_square(4)
# 调用 slow_square(4)
# 调用 slow_square(4)     —— 缓存命中也会打印日志，因为 log_call 在缓存外层
```

```python
@lru_cache(maxsize=None)
@log_call
def slow_square2(n):
    return n * n

slow_square2(4)
slow_square2(4)
# 调用 slow_square2(4)
#                          —— 第二次直接命中缓存，log_call 根本没被执行
```

一般把「缓存/短路类」装饰器放在**更靠内**（离原函数更近），把「日志/监控类」装饰器放在更靠外，才能观察到每一次真实调用。

## 2. 类装饰器：用 `__call__` 维护跨调用状态

函数装饰器每次调用都要借助闭包变量保存状态，写法有点绕；如果状态较多、逻辑复杂，用**类实例**做装饰器更直观：类的 `__init__` 接收被装饰的函数，`__call__` 让实例本身可以像函数一样被调用，实例属性天然充当跨调用状态。

```python
from functools import wraps

class CallCounter:
    """统计并限制某函数的调用次数"""

    def __init__(self, func):
        wraps(func)(self)          # 把 func 的元信息复制到 self 上
        self.func = func
        self.calls = 0

    def __call__(self, *args, **kwargs):
        self.calls += 1
        print(f"{self.func.__name__} 第 {self.calls} 次调用")
        return self.func(*args, **kwargs)

    def reset(self):
        self.calls = 0

@CallCounter
def greet(name):
    return f"hello, {name}"

greet("Ann")
greet("Bob")
print(greet.calls)     # 2
greet.reset()
print(greet.calls)     # 0
```

### 2.1 类装饰器实现结果缓存

```python
class Memoize:
    """手写一个简易缓存，比较关注命中率等自定义指标"""

    def __init__(self, func):
        wraps(func)(self)
        self.func = func
        self.cache = {}
        self.hits = self.misses = 0

    def __call__(self, *args):
        if args in self.cache:
            self.hits += 1
            return self.cache[args]
        self.misses += 1
        result = self.func(*args)
        self.cache[args] = result
        return result

    def stats(self):
        return {"hits": self.hits, "misses": self.misses, "size": len(self.cache)}

@Memoize
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(20))
print(fib.stats())     # {'hits': ..., 'misses': ..., 'size': ...}
```

### 2.2 类实例作装饰器的注意点

| 场景 | 说明 |
|---|---|
| 装饰普通函数 | 直接可用，`self.func` 保存原函数。 |
| 装饰实例方法 | `__call__(self, *args)` 里的 `args[0]` 才是被装饰方法的 `self`，容易混淆两个 `self`（见第 8 节）。 |
| 需要 `hasattr(obj, "__get__")` | 若要让类装饰器实例正确绑定到实例方法，需要额外实现描述符协议（`__get__`），否则装饰实例方法可能拿不到正确的 `self`，建议装饰方法优先用函数装饰器。 |

## 3. 装饰器工厂进阶：三层闭包的非平凡应用

装饰器工厂（带参数的装饰器）本质是三层闭包：外层接收配置参数，中层接收函数，内层才是真正的 `wrapper`。3.7 节已经过一次基础写法，这里给一个更贴近实战的例子——**带指数退避的重试装饰器**。

```python
import time
import random
from functools import wraps

def retry(times=3, base_delay=0.1, exceptions=(Exception,)):
    """
    times       最多尝试次数
    base_delay  初始等待时间，每次失败翻倍（指数退避）
    exceptions  只捕获指定的异常类型，其余异常直接抛出
    """
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            delay = base_delay
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as exc:
                    if attempt == times:
                        raise
                    print(f"第 {attempt} 次失败：{exc!r}，{delay:.2f}s 后重试")
                    time.sleep(delay)
                    delay *= 2
        return wrapper
    return decorator

@retry(times=4, base_delay=0.05, exceptions=(ConnectionError,))
def flaky_request():
    if random.random() < 0.7:
        raise ConnectionError("网络抖动")
    return "ok"

flaky_request()
```

工厂参数（`times`、`base_delay`、`exceptions`）在装饰器创建时就固定下来，被 `decorator` 和 `wrapper` 两层闭包一直捕获，每次真正调用 `flaky_request()` 时都能读到。

## 4. 深入 `functools.wraps`：`WRAPPER_ASSIGNMENTS` 与 `inspect.signature`

`@wraps(func)` 内部其实是调用 `functools.update_wrapper`，它复制两组属性：

```python
from functools import WRAPPER_ASSIGNMENTS, WRAPPER_UPDATES
print(WRAPPER_ASSIGNMENTS)
# ('__module__', '__name__', '__qualname__', '__annotations__', '__doc__')
print(WRAPPER_UPDATES)
# ('__dict__',)
```

| 属性组 | 行为 |
|---|---|
| `WRAPPER_ASSIGNMENTS` | 直接**赋值**覆盖 `wrapper` 对应属性，来自原函数。 |
| `WRAPPER_UPDATES` | 用原函数的 `__dict__` **更新**（`update()`）`wrapper.__dict__`，而不是整体替换。 |
| `__wrapped__` | 额外附加，指向原始函数，`inspect.unwrap()` 靠它层层剥开。 |

`@wraps` **不会**修改 `wrapper` 的真实调用签名——`wrapper(*args, **kwargs)` 依然只有这一种形参形式。但 Python 3.4+ 的 `inspect.signature()` 在解析签名时会自动跟随 `__wrapped__`，从而"看起来"拿到了原函数的签名：

```python
import inspect
from functools import wraps

def deco(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@deco
def greet(name: str, *, loud: bool = False) -> str:
    """打个招呼"""
    return name.upper() if loud else name

print(inspect.signature(greet))
# (name: str, *, loud: bool = False) -> str   —— 借助 __wrapped__ 还原
print(greet.__name__, greet.__doc__)
# greet 打个招呼
```

如果手写 `update_wrapper` 而不用 `@wraps`，或者需要自定义复制哪些属性，可以直接传参：

```python
from functools import update_wrapper

def deco(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return update_wrapper(wrapper, func,
                           assigned=("__name__", "__doc__"),   # 只复制这两项
                           updated=())                          # 不合并 __dict__
```

## 5. `functools.singledispatch`：按参数类型分派

`singledispatch` 把一个函数变成**泛型函数**：根据**第一个参数的类型**分派到不同实现，效果类似其他语言的函数重载。

```python
from functools import singledispatch

@singledispatch
def render(value):
    """默认实现，处理未注册的类型"""
    return f"<{type(value).__name__}: {value}>"

@render.register(int)
def _(value):
    return f"整数({value})"

@render.register(list)
def _(value):
    return "[" + ", ".join(render(v) for v in value) + "]"

@render.register
def _(value: str) -> str:      # 3.7+ 可用类型注解代替 register(str)
    return f'"{value}"'

print(render(10))          # 整数(10)
print(render("hi"))        # "hi"
print(render([1, "a"]))    # [整数(1), "a"]
print(render(3.14))        # <float: 3.14> —— 落回默认实现
```

### 5.1 一个类型注册多个实现：`register` 支持联合类型

```python
@render.register(float)
@render.register(complex)
def _(value):
    return f"数值({value})"
```

### 5.2 查看已注册的分派表

```python
print(render.registry.keys())
# dict_keys([<class 'object'>, <class 'int'>, <class 'list'>, <class 'str'>, ...])
```

`singledispatch` 只看**第一个位置参数**类型；如果需要按 `self` 之后的参数分派实例方法，标准库另提供 `singledispatchmethod`（用法类似，装饰在类方法上）。

## 6. `functools.lru_cache` 与 `cache`：记忆化的完整用法

`lru_cache` 是最常用的内置缓存装饰器，按参数值缓存返回结果（要求参数**可哈希**）。

```python
from functools import lru_cache

@lru_cache(maxsize=128)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

fib(30)
print(fib.cache_info())
# CacheInfo(hits=28, misses=31, maxsize=128, currsize=31)

fib.cache_clear()
print(fib.cache_info())
# CacheInfo(hits=0, misses=0, maxsize=128, currsize=0)
```

| 参数/方法 | 说明 |
|---|---|
| `maxsize` | 最多缓存多少组不同参数的结果，超出后按 LRU（最近最少使用）淘汰；`None` 表示不限制。 |
| `typed` | `True` 时把 `1` 和 `1.0` 当作不同的缓存键（类型也参与哈希）。 |
| `cache_info()` | 返回 `CacheInfo(hits, misses, maxsize, currsize)`，用于观测命中率。 |
| `cache_clear()` | 清空缓存，常用于测试之间的隔离，或数据源更新后手动失效。 |
| `__wrapped__` | 同样指向原始未缓存的函数。 |

Python 3.9 起新增更轻量的 `functools.cache`，等价于 `lru_cache(maxsize=None)`：

```python
from functools import cache

@cache
def expensive(x, y):
    print("计算中...")
    return x ** y

expensive(2, 10)
expensive(2, 10)   # 直接命中，不再打印"计算中..."
```

### 6.1 缓存失效的常见坑

```python
@lru_cache(maxsize=None)
def get_config(path):
    with open(path) as f:
        return f.read()

# 文件内容变了，但缓存不知道 —— 需要手动 get_config.cache_clear()
```

`lru_cache` 不感知外部状态变化，只按参数值判断是否命中；用于「纯函数」最安全，用于依赖外部可变资源的函数要小心。

## 7. 装饰方法与整个类

### 7.1 装饰实例方法

装饰器写法和装饰普通函数一致，`self` 会作为 `*args` 的第一项透传：

```python
def log_call(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        self = args[0]
        print(f"{type(self).__name__}.{func.__name__} 被调用")
        return func(*args, **kwargs)
    return wrapper

class Order:
    @log_call
    def pay(self, amount):
        print(f"支付 {amount}")
```

### 7.2 装饰 `staticmethod`/`classmethod` 要注意顺序

`@staticmethod`/`@classmethod` 必须放在**最外层**（离 `def` 更远），否则普通装饰器拿到的是描述符对象而不是可调用函数：

```python
class Util:
    @staticmethod
    @log_call            # 正确：先转普通函数装饰，最外层再转 staticmethod
    def add(a, b):
        return a + b

# 反例（Python 3.10 以前会直接报错，3.10+ 虽可运行但语义混乱，应避免）：
class BadUtil:
    @log_call
    @staticmethod
    def add(a, b):
        return a + b
```

### 7.3 类装饰器批量处理整个类

不想给每个方法都写一遍 `@log_call`，可以写一个**类装饰器**遍历类属性，批量包装：

```python
import inspect

def log_all_methods(cls):
    for name, member in vars(cls).items():
        if inspect.isfunction(member) and not name.startswith("_"):
            setattr(cls, name, log_call(member))
    return cls

@log_all_methods
class Service:
    def start(self):
        print("started")

    def stop(self):
        print("stopped")

Service().start()
# Service.start 被调用
# started
```

## 8. 常见陷阱

| 陷阱 | 现象 | 解决办法 |
|---|---|---|
| 忘记在多层装饰器里都加 `@wraps` | 链条越长，`__name__`/`inspect.signature` 越容易在中间某一层丢失 | 每一层 `wrapper` 都单独加 `@wraps(func)`，不能只在最外层加 |
| 缓存装饰器放在错误位置 | `lru_cache` 放在日志装饰器外层，导致「日志显示每次都调用」但实际是缓存命中 | 把缓存放在更靠近原函数的位置（见第 1 节） |
| `staticmethod`/`classmethod` 与普通装饰器顺序颠倒 | 装饰器收到的是描述符而非函数，运行时报错或行为异常 | `@staticmethod`/`@classmethod` 放最外层 |
| 类装饰器实例忘记支持描述符协议就用于实例方法 | 方法访问不到正确的 `self`，或直接抛异常 | 优先用函数装饰器装饰方法；类装饰器主要用于装饰独立函数或整个类 |
| 用 `lru_cache` 缓存依赖可变外部状态的函数 | 数据源更新后仍返回旧结果 | 定期或按需调用 `cache_clear()`，或改用带 TTL 的第三方缓存 |
| 用不可哈希参数调用 `lru_cache`/`Memoize` 装饰的函数 | 抛 `TypeError: unhashable type` | 传参前转换为元组等可哈希结构，或在装饰器内部对参数做归一化 |
| 装饰器链顺序写反导致语义错误 | 权限校验放在缓存内层，导致未授权用户也能拿到缓存结果 | 权限、限流类装饰器放在缓存等「短路」装饰器外层 |

## 9. 本节小结

1. 多个装饰器自下而上应用、自上而下执行（洋葱模型），链条顺序会实际影响语义，缓存类装饰器一般放更内层；
2. 类装饰器通过 `__call__` 让实例可调用，实例属性天然维护跨调用状态，适合计数器、自定义缓存等场景；
3. 装饰器工厂是三层闭包（参数 → 装饰器 → wrapper），可以支撑重试、限流等带配置的复杂逻辑；
4. `@wraps` 复制 `WRAPPER_ASSIGNMENTS`/`WRAPPER_UPDATES` 并挂上 `__wrapped__`，使 `inspect.signature()` 能穿透包装层还原原始签名；
5. `functools.singledispatch` 提供按第一参数类型分派的泛型函数机制，`register` 可用装饰、参数、类型注解三种方式注册；
6. `functools.lru_cache`/`cache` 是标准的记忆化方案，`maxsize`/`typed` 控制缓存策略，`cache_info()`/`cache_clear()` 用于观测与失效；
7. 装饰方法时 `self` 只是 `*args` 的第一项；`staticmethod`/`classmethod` 必须放在装饰器链最外层；
8. 类装饰器可以遍历类属性，批量给整个类的方法打上装饰器，避免逐个方法手写。
