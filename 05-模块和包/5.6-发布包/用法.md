# 5.6 发布包

发布包是把 Python 项目构建为标准发行产物，让其他环境可以可靠安装。现代项目通常使用 `pyproject.toml` 声明构建系统和项目元数据，构建 wheel 与源码发行包，再上传到包索引或内部仓库。

## 1. 发布前的核心概念

### 1.1 导入包与发行包

```text
发行项目名：awesome-tools
导入包名：awesome_tools
```

用户可能执行：

```bash
python -m pip install awesome-tools
```

代码中执行：

```python
import awesome_tools
```

发行项目名用于包索引和依赖声明，导入包名必须符合 Python 标识符规则。

### 1.2 构建前端与构建后端

- 构建前端：调用标准构建接口并生成产物，例如 `python -m build`；
- 构建后端：根据项目配置实际完成构建，例如 setuptools、Hatchling、Flit 等；
- 安装前端：解析并安装发行包，例如 pip；
- 包索引：存储和分发发行产物，例如公共或私有索引。

构建标准允许项目选择不同后端。应阅读所选后端文档，不要把某个后端的专用配置当成所有工具通用标准。

## 2. 推荐目录结构

```text
awesome-tools/
├── pyproject.toml
├── README.md
├── LICENSE
├── src/
│   └── awesome_tools/
│       ├── __init__.py
│       ├── core.py
│       └── py.typed
└── tests/
    └── test_core.py
```

`src` 布局的主要优点是开发和测试更不容易意外从仓库根目录导入未安装源码。项目应安装到虚拟环境后再测试。

## 3. 最小 `pyproject.toml`

以下示例使用一种常见后端；具体版本范围应根据项目实际验证和维护策略调整：

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "awesome-tools"
version = "0.1.0"
description = "Small reusable tools for learning Python packaging"
readme = "README.md"
requires-python = ">=3.11"
license = "MIT"
authors = [
  { name = "Example Author", email = "author@example.com" },
]
dependencies = []

[project.urls]
Homepage = "https://example.com/awesome-tools"
Repository = "https://example.com/awesome-tools/repository"
Issues = "https://example.com/awesome-tools/issues"
```

`[build-system]` 告诉构建工具使用哪个后端及构建所需依赖。`[project]` 包含标准化项目元数据。

项目也可以选择其他后端，例如使用 setuptools 时：

```toml
[build-system]
requires = ["setuptools"]
build-backend = "setuptools.build_meta"
```

后端选择不是本节重点，关键是理解标准元数据和构建接口。

## 4. 项目元数据

常见字段：

| 字段 | 作用 |
|---|---|
| `name` | 发行项目名称，必须唯一才能发布到目标索引 |
| `version` | 当前发行版本 |
| `description` | 一行摘要 |
| `readme` | 长描述来源 |
| `requires-python` | 支持的 Python 版本范围 |
| `license` | 许可证表达 |
| `authors` / `maintainers` | 作者和维护者 |
| `dependencies` | 运行依赖 |
| `optional-dependencies` | 可选功能或开发依赖组 |
| `urls` | 文档、源码、问题追踪等地址 |
| `classifiers` | 包索引分类信息 |
| `keywords` | 搜索关键词 |

元数据应真实反映经过测试的兼容范围。声明支持某 Python 版本，就应在自动化测试中验证该版本。

## 5. 静态与动态元数据

静态版本：

```toml
[project]
version = "1.2.0"
```

动态版本：

```toml
[project]
dynamic = ["version"]
```

动态字段由构建后端根据配置获取，例如从源码属性或版本控制标签读取。不同后端的配置方式不同。

版本应尽量只有一个权威来源，避免 `pyproject.toml`、`__init__.py`、文档中分别手工维护而产生不一致。

已安装包中查询版本：

```python
from importlib.metadata import version

print(version("awesome-tools"))
```

## 6. 版本设计

常见版本：

```text
1.4.2       正式版本
2.0.0a1     alpha 预发布
2.0.0b1     beta 预发布
2.0.0rc1    候选版本
1.4.2.post1 后发布版本
```

项目可采用语义化版本思想：

- 主版本：不兼容的公开 API 变化；
- 次版本：向后兼容的新功能；
- 修订版本：向后兼容的问题修复。

但实际版本规则必须由项目明确记录。`0.x` 阶段是否稳定、何为破坏性变化、弃用保留多久，都需要维护策略说明。

## 7. 运行依赖与可选依赖

```toml
[project]
dependencies = [
  "httpx>=0.27,<1",
]

[project.optional-dependencies]
cli = ["rich>=13,<15"]
test = [
  "pytest>=8,<9",
  "coverage>=7,<8",
]
```

原则：

- 只声明项目真正需要的直接依赖；
- 不把标准库写成第三方依赖；
- 不把本地开发工具强制变成所有用户的运行依赖；
- 对可复用库给出经过验证的合理版本范围；
- 使用环境标记表达平台或 Python 版本条件，而不是让用户手工删改配置。

## 8. 命令行入口

如果包提供 CLI，可在项目元数据中声明：

```toml
[project.scripts]
awesome = "awesome_tools.cli:main"
```

其中 `awesome_tools.cli:main` 表示导入模块并调用 `main`。安装后用户可以执行：

```bash
awesome --help
```

入口函数应返回或通过 `sys.exit()` 表达合理退出码，不应在模块导入时立即解析参数。

## 9. 包数据与类型信息

项目可能需要包含：

- 模板；
- 默认配置；
- 静态数据；
- `py.typed` 类型标记；
- 类型存根 `.pyi`。

是否包含这些文件取决于构建后端配置。不能因为文件位于源码目录就假设它一定进入 wheel 和 sdist。

构建后应检查产物内容，并在安装后的干净环境使用 `importlib.resources` 读取资源。

## 10. README、许可证与文档

高质量发布项目至少应说明：

- 项目用途和适用场景；
- 安装命令；
- 最小使用示例；
- 支持的 Python 版本；
- 配置方式；
- 常见错误；
- 许可证；
- 贡献和问题反馈入口；
- 版本变更记录或发布说明。

README 会作为包索引项目页面的重要内容。发布前应检查 Markdown 渲染、相对图片链接和代码示例。

许可证决定用户能否复制、修改和分发项目。不能随意复制代码而忽略其许可证，也不要发布不清楚授权来源的资源文件。

## 11. 构建发行产物

在干净虚拟环境安装构建前端后：

```bash
python -m pip install build
python -m build
```

通常生成：

```text
dist/
├── awesome_tools-0.1.0-py3-none-any.whl
└── awesome_tools-0.1.0.tar.gz
```

构建前应清理旧 `dist/` 和构建缓存，避免误上传旧版本。删除前必须确认当前目录和目标路径。

构建完成后，不要只看“命令成功”，还要检查：

- 文件名和版本是否正确；
- wheel 中是否包含预期模块和资源；
- sdist 中是否包含构建所需文件；
- 元数据和依赖是否正确；
- README 能否正确渲染；
- 是否意外包含密钥、测试数据或大文件。

## 12. 在干净环境测试产物

最有说服力的验证是安装真正构建出的 wheel：

```bash
python -m venv .venv-test
source .venv-test/bin/activate
python -m pip install dist/awesome_tools-0.1.0-py3-none-any.whl
python -c "import awesome_tools; print(awesome_tools)"
awesome --help
```

还应从源码目录之外运行测试，防止当前目录遮蔽已安装包。

至少验证：

- 顶层导入；
- 公开 API；
- CLI 入口；
- 包内资源；
- 运行依赖能否自动安装；
- 最低和最高受支持 Python 版本；
- 目标操作系统。

## 13. 测试索引与正式索引

首次发布或调整发布流程时，应先上传到测试索引，验证项目页面和安装行为，再发布到正式索引。

上传通常使用专用上传工具：

```bash
python -m pip install twine
python -m twine check dist/*
python -m twine upload --repository testpypi dist/*
```

再从测试索引进行安装验证。具体索引地址、依赖来源和认证方式应以目标索引文档为准。

注意：测试索引中的项目依赖不一定都存在。验证时要明确主项目来自哪里、依赖从哪里解析，避免得到错误结论。

## 14. 认证与可信发布

上传凭据具有发布权限，必须安全管理：

- 不把用户名、密码或 API 令牌写入仓库；
- 不在可泄露的日志中输出令牌；
- 使用范围尽可能小的令牌；
- 为发布账号启用强认证措施；
- CI 使用平台密钥存储或索引支持的可信发布机制；
- 限制谁能触发正式发布；
- 发布工作流应从受保护标签或分支触发。

一旦凭据泄露，应立即撤销并轮换，而不是只删除 Git 最新版本中的文件，因为历史记录可能仍然保留秘密。

## 15. 发布不可变性与版本升级

包索引通常不允许用同一版本号反复覆盖不同内容。即使某些私有系统允许，也不应这样做，因为缓存和镜像可能得到不同文件。

发现已发布版本有问题时：

1. 停止推广问题版本；
2. 必要时撤回或标记不推荐；
3. 修复代码；
4. 增加版本号；
5. 重新构建、测试和发布；
6. 写清变更说明。

不要手工修改构建产物后仍使用旧版本号。

## 16. 自动化发布流程

成熟项目可以在 CI 中：

1. 在支持的 Python 和平台矩阵运行测试；
2. 运行静态检查和类型检查；
3. 构建 sdist 和 wheel；
4. 检查产物；
5. 在干净环境安装 wheel 并执行冒烟测试；
6. 验证 sdist 可以重新构建；
7. 从受保护版本标签触发发布；
8. 使用可信发布或安全令牌上传；
9. 生成发布说明；
10. 发布后从索引重新安装验证。

构建一次并推广同一产物，通常比在不同阶段重复构建更可靠。

## 17. 兼容性与弃用

公共包发布后，用户会依赖：

- 导入路径；
- 函数和类名称；
- 参数形式和默认值；
- 返回值；
- 异常类型；
- CLI 参数和退出码；
- 配置文件格式；
- 数据序列化格式。

需要移除旧接口时，可以：

1. 先提供新接口；
2. 在旧接口发出明确弃用警告；
3. 文档说明迁移方式和移除版本；
4. 保留足够迁移周期；
5. 在约定的大版本或明确版本中移除。

## 18. 发布失败排查

### 18.1 构建后缺少模块

检查包发现配置、`src` 布局配置和构建产物内容。不要只测试仓库源码。

### 18.2 缺少资源文件

配置构建后端包含包数据，重新构建并安装 wheel 验证。

### 18.3 项目名已被占用

公共索引项目名称需要唯一。选择新的发行项目名，同时评估导入包名是否也需调整。

### 18.4 README 渲染失败

运行产物检查工具，检查声明的内容类型、Markdown 语法和无法访问的本地链接。

### 18.5 用户安装后 CLI 不存在

检查 `[project.scripts]`、入口模块、函数名和环境的脚本目录是否在 `PATH`。

### 18.6 本地成功、发布产物失败

通常是本地测试导入了源码、依赖未声明、资源未包含或依赖了未提交文件。必须在源码目录外安装 wheel 验证。

## 19. 发布检查清单

### 代码与测试

- 所有自动化测试通过；
- 支持的 Python 版本得到验证；
- 公共 API 变更已评审；
- 没有调试输出、临时代码和秘密。

### 元数据

- 项目名和版本正确；
- Python 版本范围真实；
- 依赖和可选依赖完整；
- README、许可证、链接和作者信息正确。

### 构建产物

- wheel 和 sdist 均成功生成；
- 产物内容完整且无敏感文件；
- 元数据检查通过；
- 干净环境可以安装 wheel；
- CLI、资源和公开导入均验证成功。

### 发布操作

- 使用正确目标索引；
- 凭据来源安全；
- 版本号从未发布过；
- 测试索引验证完成；
- 发布说明准备完毕；
- 发布后重新安装并执行冒烟测试。

## 20. 本节小结

1. 发布是把项目转换为标准发行产物，不只是把源码目录上传。
2. `pyproject.toml` 描述构建系统、项目元数据、依赖和入口等信息。
3. Wheel 与 sdist 服务于不同安装场景，发布前应同时构建并检查。
4. 必须在干净环境、源码目录之外安装真实 wheel，验证导入、CLI 和资源。
5. 版本发布应不可变；已发布版本出错时要增加版本号，而不是覆盖旧产物。
6. 凭据、兼容性、许可证、供应链和自动化测试都是发布质量的一部分。
