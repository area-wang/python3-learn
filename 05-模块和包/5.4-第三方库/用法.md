# 5.4 第三方库

第三方库是 Python 标准库之外、由社区或组织发布的软件。它们可以通过包索引、代码仓库、本地目录或私有仓库安装。正确管理第三方依赖是保证项目可运行、可复现和可维护的重要基础。

## 1. 先区分四个概念

| 概念 | 作用 | 示例 |
|---|---|---|
| 项目（project） | 源代码、配置、测试和文档的整体 | 一个 Git 仓库 |
| 发行包（distribution package） | 可以被构建、安装和管理的发布单元 | PyPI 上的 `requests` |
| 导入包（import package） | Python 代码中可导入的包 | `import requests` |
| 模块（module） | 单个可导入代码单元 | `requests.sessions` |

发行包名称与导入名称不一定一致。不能仅根据 `import` 语句猜测安装命令，应查阅项目官方说明或已安装元数据。

## 2. `pip` 的角色

`pip` 是常用的 Python 包安装工具，负责解析需求、下载发行产物并安装到指定 Python 环境。

建议始终通过解释器调用：

```bash
python -m pip --version
python -m pip install requests
```

相比直接执行 `pip`，`python -m pip` 更明确地表示“使用这个 `python` 对应的 pip”，可以减少机器中多个 Python 环境造成的混淆。

检查解释器和安装位置：

```bash
python -c "import sys; print(sys.executable)"
python -m pip --version
python -m pip show requests
```

## 3. 虚拟环境

虚拟环境为项目提供相对隔离的 Python 解释器入口和 `site-packages`，避免不同项目的依赖版本互相冲突。

创建环境：

```bash
python -m venv .venv
```

激活环境：

```bash
# macOS / Linux
source .venv/bin/activate

# Windows 命令提示符
.venv\Scripts\activate.bat

# Windows PowerShell
.venv\Scripts\Activate.ps1
```

确认环境：

```bash
python -c "import sys; print(sys.executable)"
python -c "import sys; print(sys.prefix != sys.base_prefix)"
```

退出环境：

```bash
deactivate
```

重要原则：

- 每个项目使用独立虚拟环境；
- `.venv/` 不提交到版本库；
- 虚拟环境应视为可删除、可重建的产物；
- 不要复制虚拟环境到另一台机器或另一条路径，应根据依赖声明重新创建；
- 激活只是在当前终端调整 `PATH`，并不是使用环境的唯一方式；
- 未激活时也可直接运行 `.venv/bin/python` 或 Windows 对应路径。

## 4. 安装、升级和卸载

```bash
# 安装最新可用版本
python -m pip install requests

# 安装指定版本
python -m pip install "requests==2.32.0"

# 指定版本范围
python -m pip install "requests>=2.31,<3"

# 兼容版本约束
python -m pip install "requests~=2.31"

# 升级
python -m pip install --upgrade requests

# 卸载
python -m pip uninstall requests
```

在 shell 中应给包含 `<`、`>`、`*` 等特殊字符的需求表达式加引号。

查看环境：

```bash
python -m pip list
python -m pip show requests
python -m pip check
```

- `pip list`：列出已安装发行包；
- `pip show`：查看版本、位置、依赖等元数据；
- `pip check`：检查已安装依赖是否存在缺失或版本冲突。

## 5. 版本说明符

常见形式：

| 写法 | 含义 |
|---|---|
| `package==1.2.3` | 仅允许该精确版本 |
| `package>=1.2` | 至少为 1.2 |
| `package>=1.2,<2` | 大于等于 1.2 且小于 2 |
| `package~=1.4.2` | 兼容版本，通常相当于 `>=1.4.2,==1.4.*` |
| `package!=1.5.0` | 排除特定版本 |

约束策略需要根据项目类型决定：

- 可复用库通常声明合理范围，避免过度锁死下游环境；
- 应用通常需要更强的可复现性，可以使用锁文件或经过验证的精确版本集合；
- 无上限依赖可能在未来遇到不兼容大版本；
- 所有依赖永远固定不升级会积累安全和兼容问题。

## 6. 直接依赖与传递依赖

如果应用直接使用 `requests`，那么 `requests` 是直接依赖；它内部所需的其他发行包是传递依赖。

依赖声明应优先记录项目直接依赖，而不是把当前环境中所有包都当作业务依赖。应用锁定完整环境与可复用库声明最小直接依赖，是两个不同目标。

判断一个依赖是否应该直接声明：

- 项目代码是否直接导入或调用它；
- 项目是否依赖它提供的命令行工具；
- 它是否只是测试、格式化或构建工具；
- 它是否只是另一个依赖的内部实现，项目并未直接依赖其 API。

## 7. `requirements.txt`

需求文件是传给 `pip install -r` 的安装输入：

```text
requests>=2.31,<3
python-dotenv>=1,<2
```

安装：

```bash
python -m pip install -r requirements.txt
```

可以拆分不同环境：

```text
# requirements-dev.txt
-r requirements.txt
pytest>=8,<9
coverage>=7,<8
```

`pip freeze` 会输出当前环境中安装的版本：

```bash
python -m pip freeze > requirements-lock.txt
```

但要理解其局限：

- 它记录的是当前环境快照，不一定表达项目真正的直接依赖；
- 环境中手工安装的无关包也可能被写入；
- 不同平台可能需要不同发行包；
- 对可复用库而言，把所有传递依赖完全固定通常过度严格。

因此，规范项目通常把项目元数据中的依赖声明作为主要来源，并根据工具和部署目标生成锁定结果。

## 8. `pyproject.toml` 中的依赖

现代 Python 项目通常在 `pyproject.toml` 的 `[project]` 中声明运行依赖：

```toml
[project]
name = "weather-cli"
version = "1.0.0"
requires-python = ">=3.11"
dependencies = [
  "requests>=2.31,<3",
]
```

可选依赖：

```toml
[project.optional-dependencies]
dev = [
  "pytest>=8,<9",
  "coverage>=7,<8",
]
docs = [
  "sphinx>=7,<9",
]
```

安装可选依赖组：

```bash
python -m pip install ".[dev]"
```

可选依赖也可表达用户选择的功能：

```toml
[project.optional-dependencies]
postgres = ["psycopg>=3,<4"]
mysql = ["mysqlclient>=2,<3"]
```

是否支持特定依赖组、锁文件和同步命令，取决于采用的项目管理工具；不要假设所有工具语义完全相同。

## 9. 可编辑安装

开发本地项目时：

```bash
python -m pip install -e .
```

可编辑安装使项目以“已安装”的方式出现在环境中，同时源码修改通常可立即生效。它适合本地开发，尤其适合 `src` 布局。

普通安装：

```bash
python -m pip install .
```

发布前不能只验证可编辑安装，还应构建 wheel，并在干净环境安装 wheel 测试，以发现遗漏文件、错误元数据等问题。

## 10. 从不同来源安装

### 10.1 本地目录和构建产物

```bash
python -m pip install .
python -m pip install ./dist/example-1.0.0-py3-none-any.whl
```

### 10.2 版本控制系统

```text
project-name @ git+https://example.com/organization/repository.git@commit-id
```

生产环境应尽量固定到不可变提交，而不是依赖会变化的分支名称。安装私有仓库时不要把访问令牌直接写入会提交的文件或命令历史。

### 10.3 其他索引

企业可能使用私有包索引。配置凭据时应使用安全的凭据管理方式。混用公开索引和私有索引时要警惕依赖混淆风险，确保同名项目不会从非预期来源被解析。

## 11. Wheel 与源码发行包

安装工具常见两种发行产物：

- Wheel（`.whl`）：已构建的安装格式，通常安装更快；
- Source Distribution（sdist，常见 `.tar.gz`）：源码发行包，安装时通常还需在本地构建 wheel。

包含编译扩展的项目可能针对 Python 版本、操作系统和 CPU 架构提供不同 wheel。若没有兼容 wheel，本地构建可能要求编译器和系统开发库。

看到“构建 wheel 失败”时，应检查：

1. 是否存在适配当前 Python 和平台的 wheel；
2. Python 版本是否过新或过旧；
3. 是否缺少系统编译工具和头文件；
4. 包版本是否支持当前平台；
5. 构建日志中第一个真正的错误，而非最后一行汇总。

## 12. 依赖冲突与排查

典型冲突：

```text
project-a requires library-x<2
project-b requires library-x>=2
```

同一环境无法同时满足时，可以：

- 寻找兼容版本组合；
- 升级依赖旧版本的项目；
- 替换产生冲突的库；
- 若是互不相关的应用，放入不同虚拟环境；
- 不要使用强制覆盖等方式制造表面安装成功、运行时失败的环境。

排查步骤：

```bash
python -m pip check
python -m pip show package-name
python -m pip list
```

然后在全新虚拟环境中用最小依赖复现，排除旧环境残留。

## 13. 选择第三方库

安装一个库前应评估：

- 功能是否真的需要，标准库能否满足；
- 项目是否持续维护，最近发布和问题响应是否合理；
- 文档、类型提示和测试是否完善；
- 许可证是否符合项目要求；
- 支持哪些 Python 版本和平台；
- 依赖树是否过重；
- 是否有已知安全问题；
- API 是否稳定，升级成本是否可控；
- 社区规模不是唯一指标，小而专注的库也可能更适合。

不要仅根据下载量决定，也不要随意运行来源不明项目的安装脚本。安装第三方包本质上是在本机运行他人发布的代码和构建流程。

## 14. 依赖安全与维护

- 只从可信索引和可信仓库安装；
- 仔细核对项目名称，防止拼写仿冒；
- 不把索引令牌、仓库令牌写入版本库；
- 定期审查和升级依赖，而不是永不更新；
- 升级后运行自动化测试；
- 生产部署使用可复现的依赖集合；
- 删除不再使用的直接依赖；
- 在 CI 中从干净环境安装，验证声明完整；
- 对高安全要求场景考虑哈希校验、软件物料清单和漏洞扫描。

## 15. 独立命令行工具

如果第三方项目主要提供全局命令行程序，把它装进每个业务项目的虚拟环境并不总是合适。专门的工具可以为每个 CLI 创建隔离环境，同时把命令暴露到用户的 `PATH`。

核心思想是区分：

- 项目运行依赖：安装到项目虚拟环境；
- 项目开发工具：按团队约定安装到开发环境或隔离工具环境；
- 用户级独立 CLI：使用专门隔离方案管理。

## 16. 常见错误

### 16.1 安装成功但无法导入

常见原因是 `pip` 和运行程序的 `python` 不属于同一环境。使用：

```bash
python -m pip show package-name
python -c "import sys; print(sys.executable)"
```

### 16.2 `pip install` 权限错误

不要立刻使用管理员权限安装到系统 Python。优先创建虚拟环境，尤其不要随意修改操作系统管理的 Python 环境。

### 16.3 只有自己机器能运行

说明依赖声明不完整、依赖了未提交文件、隐含系统工具或环境变量。应在干净环境中重建验证。

### 16.4 虚拟环境已提交或复制

删除环境目录，将其加入忽略规则，根据项目声明重新创建。

## 17. 推荐开发流程

```bash
# 1. 创建并激活环境
python -m venv .venv
source .venv/bin/activate

# 2. 确认解释器
python -c "import sys; print(sys.executable)"

# 3. 安装当前项目和开发依赖
python -m pip install -e ".[dev]"

# 4. 运行测试
python -m pytest

# 5. 检查依赖一致性
python -m pip check
```

实际团队还应明确 Python 版本、依赖更新策略、锁定方式、私有索引配置和 CI 安装命令。

## 18. 本节小结

1. `pip` 管理的是发行包，代码导入的是模块或导入包，两者名称不一定相同。
2. 每个项目应使用独立、可重建且不提交版本库的虚拟环境。
3. 使用 `python -m pip` 可以减少多个解释器带来的安装位置混乱。
4. 库和应用的依赖约束目标不同：库强调兼容范围，应用强调部署可复现。
5. `requirements.txt` 是安装输入，`pip freeze` 是环境快照，不应不加判断地替代项目依赖设计。
6. 第三方依赖不仅带来功能，也带来升级、许可证、供应链和安全维护成本。
