# 5.4 第三方库练习题

## 一、概念题

1. 为什么推荐使用 `python -m pip` 而不是直接使用 `pip`？
2. 虚拟环境隔离了什么？它是否等同于操作系统容器？
3. 为什么虚拟环境不应提交到 Git，也不应直接复制给别人？
4. 发行包名称与导入包名称为什么可能不同？
5. 直接依赖和传递依赖有什么区别？
6. `requirements.txt` 与 `pip freeze` 的输出分别代表什么？
7. 为什么可复用库不应随意精确固定所有传递依赖版本？
8. Wheel 与源码发行包有什么区别？
9. 可编辑安装适合什么场景？发布前为什么还要测试普通 wheel 安装？
10. 安装第三方库可能带来哪些供应链风险？

## 二、命令实践

创建一个全新练习目录，完成并记录以下步骤：

1. 使用 `venv` 创建 `.venv`；
2. 激活虚拟环境；
3. 打印 `sys.executable`、`sys.prefix` 和 `sys.base_prefix`；
4. 使用 `python -m pip` 安装一个小型第三方库；
5. 使用 `pip show` 查看它的安装位置和依赖；
6. 使用 `pip list` 查看环境；
7. 在 Python 中打印该库的 `__file__`；
8. 退出并重新激活环境；
9. 删除虚拟环境并根据依赖声明重建；
10. 验证重建后程序仍能运行。

## 三、依赖声明题

### 1. 版本范围

为以下场景设计版本说明符并解释：

- 只能使用精确测试过的 `2.3.1`；
- 支持 `2.3` 以上但不支持 `3.0`；
- 支持 `1.4.2` 开始的 `1.4.x`；
- 排除存在已知缺陷的 `2.5.0`；
- 最低版本为 `8`，暂未确认下一个大版本兼容性。

### 2. 依赖分类

某项目环境中安装了：Web 框架、数据库驱动、测试框架、代码格式化器、框架的传递依赖、交互式调试工具。把它们分为：

- 运行时直接依赖；
- 开发或测试依赖；
- 传递依赖；
- 用户个人工具。

说明哪些内容应进入 `[project.dependencies]`，哪些适合进入可选依赖组。

### 3. 编写配置

为一个天气 CLI 编写 `pyproject.toml` 依赖片段：

- Python 最低版本；
- 一个 HTTP 客户端运行依赖；
- `dev` 组包含测试和覆盖率工具；
- `docs` 组包含文档工具；
- 给每个版本范围写出选择理由。

## 四、故障排查题

### 1. 安装后无法导入

终端中执行 `pip install example` 成功，但 `python app.py` 报 `ModuleNotFoundError`。写出逐步排查命令，重点验证 `pip` 与 `python` 是否对应同一环境。

### 2. 依赖冲突

应用依赖：

```text
framework-a -> common-lib>=2,<3
plugin-b    -> common-lib>=3,<4
```

分析为什么无法直接求解，并列出至少四种合理处理策略。禁止以忽略冲突或强制安装作为最终方案。

### 3. 构建失败

安装某科学计算包时出现“Failed building wheel”。请按优先级检查：

- 当前 Python 版本；
- 操作系统和 CPU 架构；
- 是否存在兼容 wheel；
- 是否缺少编译器和系统库；
- 构建日志中的首个错误。

### 4. 环境不可复现

同事只发送了 `.venv` 压缩包，在你的机器解压后无法运行。解释原因，并设计正确的项目交付清单。

## 五、综合实践：可复现的小应用

创建一个使用至少两个第三方依赖的小型应用：

1. 使用 `.venv` 隔离环境；
2. 在项目配置中声明直接运行依赖；
3. 把测试工具放到开发可选依赖中；
4. 添加忽略规则，不提交环境和缓存；
5. 编写清晰的环境创建和安装命令；
6. 在干净环境执行安装和测试；
7. 运行 `python -m pip check`；
8. 记录直接依赖及选择原因；
9. 记录至少一个传递依赖，但不要把它误当成业务直接依赖；
10. 模拟升级一个依赖，运行测试后决定是否接受升级。

## 六、安全审查清单

选择一个准备引入的第三方库，调查并回答：

- 官方项目页面和源码仓库在哪里；
- 项目名称是否可能与仿冒名称混淆；
- 维护是否持续；
- 支持哪些 Python 版本；
- 使用什么许可证；
- 直接和传递依赖数量如何；
- 是否需要编译扩展；
- 是否会访问网络、文件或执行外部命令；
- 项目停止维护时有什么替代方案；
- 团队将如何测试和更新它。
