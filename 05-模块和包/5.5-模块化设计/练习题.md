## 一、概念题

1. 为什么“文件拆得越多”不等于“模块化越好”？
2. 什么是高内聚？请给出一个高内聚和一个低内聚模块示例。
3. 什么是低耦合？哪些代码现象说明模块之间耦合过高？
4. 公开 API 应包含哪些行为约定？
5. 为什么核心业务模块不应依赖具体 Web 框架或数据库驱动？
6. 依赖注入如何提高可测试性？
7. 什么时候值得使用 `Protocol`，什么时候只是过度抽象？
8. 为什么全局可变状态会造成隐藏依赖？
9. 循环导入可能反映哪些设计问题？
10. 为什么插件系统不应在没有真实扩展需求时过早引入？

## 三、重构题

### 1. 拆分单文件程序

选择一个至少包含 150 行的单文件程序，识别：

- 输入输出；
- 数据结构；
- 业务规则；
- 外部存储；
- 配置；
- 错误处理。

逐步重构为包。每次移动代码后运行原有行为验证，记录每个模块的一句话职责。

### 2. 消除隐藏依赖

重构：

```python
def create_report():
    connection = connect_production_database()
    current_time = datetime.now()
    records = connection.query("...")
    ...
```

要求将数据库和时钟作为依赖传入，使测试能够使用内存数据和固定时间。

### 3. 异常转换

数据库驱动会抛出 `DriverNoRowError`，业务层希望暴露 `OrderNotFoundError`。实现异常转换，并保证：

- 保留原始异常链；
- 不泄漏数据库实现到接口层；
- 其他数据库错误不被错误地伪装成“订单不存在”。

### 4. 移除循环依赖

给出结构：

```text
models.py -> services.py
services.py -> repositories.py
repositories.py -> models.py
```

分析每条依赖是否合理，重新设计数据模型、仓库协议、应用服务和具体仓库实现的位置，使依赖图无环。

## 四、接口设计题

设计一个通知系统，支持邮件、短信和控制台实现：

1. 定义最小通知协议；
2. 业务服务只依赖协议；
3. 实现三个通知器；
4. 入口根据配置选择实现；
5. 测试使用记录消息的假实现；
6. 讨论失败、重试和批量发送应属于哪一层。

## 五、综合实践：可替换存储的任务管理器

设计以下项目：

```text
task_app/
├── domain/
├── application/
├── infrastructure/
└── interfaces/
```

要求：

1. 领域层定义任务实体和业务异常；
2. 应用层实现创建、完成、删除和查询任务；
3. 定义仓库协议；
4. 提供内存仓库和 JSON 文件仓库；
5. CLI 只负责参数解析和结果展示；
6. 配置在入口处读取并校验；
7. 核心逻辑不导入 `json`、`argparse` 或具体文件路径；
8. 单元测试使用内存仓库；
9. 集成测试验证 JSON 仓库；
10. 画出模块依赖图并证明无循环依赖。

## 六、设计取舍题

对以下情况判断“保持现状、拆分、合并或抽象”，并说明理由：

1. 一个 40 行模块包含三个始终一起使用的金额函数；
2. 一个 1000 行模块同时处理 HTTP、业务规则和数据库；
3. 两个模块各只有一个函数，且总是一起修改；
4. 当前只有一个存储实现，但测试很难隔离真实数据库；
5. 团队为了未来插件功能设计了五层工厂，但没有第二个实现；
6. 顶层包重新导出 80 个内部类；
7. `utils.py` 每周都加入不同领域的函数；
8. 为解决循环导入，在十几个函数内部使用局部导入。
