# 5.5 模块化设计

模块化设计不是简单地“把一个大文件拆成很多小文件”，而是根据职责、变化原因和依赖关系建立清晰边界。好的模块具有高内聚、低耦合、公开接口明确、依赖方向稳定等特点。

## 1. 模块化的目标

- **可理解**：只阅读少量模块就能理解某项功能；
- **可修改**：改变一个实现不会引发大量无关改动；
- **可测试**：核心逻辑可以在不启动整个系统时单独验证；
- **可复用**：稳定能力可以在不同入口复用；
- **可替换**：数据库、网络客户端等外部实现可以替换；
- **可协作**：不同成员可以在明确边界内工作；
- **可发布**：公共 API、依赖和资源能够被可靠打包。

## 2. 高内聚与低耦合

### 2.1 高内聚

一个模块中的内容应该围绕同一职责或同一变化原因。

```text
pricing.py
├── calculate_subtotal
├── apply_discount
└── calculate_tax
```

这些函数都围绕价格计算，内聚度较高。

如果一个 `utils.py` 同时包含日期格式化、数据库连接、邮件发送、密码哈希和金额计算，它只是把无关代码放在一起，内聚度很低。

### 2.2 低耦合

模块之间应尽量只依赖少量、稳定的公开接口，而不是了解对方内部数据和执行细节。

高耦合表现：

- 直接修改其他模块的内部全局变量；
- 从 `_internal` 模块导入大量实现细节；
- 调用方必须按隐含顺序调用多个函数；
- 一个模块修改后几十个模块都要同步修改；
- 为测试一个纯计算必须连接真实数据库。

## 3. 按职责拆分，而不是按代码长度拆分

不应仅因为文件超过某个行数就机械拆分。判断模块边界可以问：

1. 这些代码是否描述同一领域概念？
2. 它们是否因同一种业务变化而修改？
3. 使用者是否通常同时需要这些能力？
4. 模块能否用一句话说明职责？
5. 是否存在稳定的公开入口？

示例：订单系统可按领域职责拆分：

```text
order_app/
├── domain/
│   ├── models.py
│   ├── pricing.py
│   └── exceptions.py
├── application/
│   └── checkout.py
├── infrastructure/
│   ├── database.py
│   └── payment_gateway.py
└── interfaces/
    └── cli.py
```

这不是唯一正确结构。小项目不必照搬复杂分层；结构复杂度应与问题规模匹配。

## 4. 关注点分离

把不同类型的工作分开：

```python
# 不理想：输入、业务计算、存储和输出混在一起
def checkout():
    quantity = int(input("数量："))
    price = float(input("单价："))
    total = quantity * price
    open("orders.txt", "a").write(str(total))
    print(f"总价：{total}")
```

拆分后：

```python
# pricing.py
from decimal import Decimal


def calculate_total(price: Decimal, quantity: int) -> Decimal:
    if quantity <= 0:
        raise ValueError("quantity must be positive")
    return price * quantity
```

```python
# service.py
def create_order(price, quantity, repository):
    total = calculate_total(price, quantity)
    order = Order(price=price, quantity=quantity, total=total)
    repository.save(order)
    return order
```

```python
# cli.py
def main():
    # 只负责输入、调用和展示
    ...
```

业务计算不依赖命令行和真实文件后，更容易测试和复用。

## 5. 公开 API 与内部实现

模块应明确调用者可以依赖什么：

```python
# pricing.py
__all__ = ["calculate_total", "PricingError"]


class PricingError(Exception):
    pass


def calculate_total(items):
    normalized = _normalize_items(items)
    return _sum_items(normalized)


def _normalize_items(items):
    ...


def _sum_items(items):
    ...
```

前导下划线表达内部接口约定。调用者依赖内部名称，会增加未来重构成本。

一个稳定 API 应考虑：

- 函数名、参数和返回值；
- 异常类型和错误语义；
- 是否产生副作用；
- 数据是否可变；
- 线程或异步使用要求；
- 兼容性和弃用策略。

## 6. 依赖方向

依赖应尽量从易变化、外层细节指向稳定、内层规则：

```text
CLI / Web API
      ↓
应用服务
      ↓
领域逻辑
```

数据库和外部 API 是实现细节。核心业务规则不应为了复用数据库代码而反向导入 Web 框架或命令行模块。

错误方向：

```text
domain -> web_framework
domain -> concrete_database
```

更合理：

```text
web -> application -> domain
infrastructure -> domain contracts
```

## 7. 依赖注入

不要在业务函数内部固定创建外部依赖：

```python
# 难测试
def register_user(email):
    database = ProductionDatabase()
    mailer = SmtpMailer()
    ...
```

把依赖作为参数传入：

```python
def register_user(email, repository, mailer):
    user = User(email=email)
    repository.save(user)
    mailer.send_welcome(user)
    return user
```

入口负责组装：

```python
def main():
    repository = SqlUserRepository(...)
    mailer = SmtpMailer(...)
    register_user(input("Email: "), repository, mailer)
```

优点：

- 测试可传入内存实现；
- 核心模块不依赖具体基础设施；
- 配置和对象创建集中在组合根；
- 替换实现不修改业务规则。

Python 中依赖注入通常不需要大型框架，函数参数和构造方法已经足够强大。

## 8. 使用协议或抽象定义边界

如果多个实现需要遵循统一接口，可以使用协议：

```python
from typing import Protocol


class UserRepository(Protocol):
    def save(self, user): ...
    def find_by_email(self, email): ...
```

应用服务依赖抽象行为：

```python
def register_user(email: str, repository: UserRepository):
    ...
```

具体实现：

```python
class InMemoryUserRepository:
    ...


class SqlUserRepository:
    ...
```

并非每个函数都需要抽象基类或协议。只有当边界确实存在多个实现、需要静态约束或值得明确表达时再引入。

## 9. 避免全局可变状态

```python
# 不理想
current_user = None
cache = {}
```

全局可变状态会造成：

- 测试之间相互污染；
- 调用顺序影响结果；
- 并发访问复杂；
- 依赖关系隐藏；
- 重新加载和多进程行为难以理解。

优先把状态封装到对象中，并由入口创建和传递：

```python
class UserCache:
    def __init__(self):
        self._items = {}
```

模块级不可变常量和轻量无状态对象通常没有问题，关键在于是否存在隐式共享和可变生命周期。

## 10. 配置与代码分离

不应把环境相关值散落在模块中：

```python
# 不理想
DATABASE_URL = "postgresql://production-host/app"
```

可以定义配置数据结构，在入口读取环境并完成校验：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Settings:
    database_url: str
    debug: bool = False
```

配置对象显式传给需要它的组件。密码和令牌不应写入源码或提交到版本库。

## 11. 错误边界

模块应在合适层级转换异常：

```python
class UserNotFoundError(Exception):
    pass


def get_user(user_id, repository):
    try:
        return repository.get(user_id)
    except DatabaseNoRowError as error:
        raise UserNotFoundError(user_id) from error
```

这样上层依赖领域异常，不必理解具体数据库驱动异常。注意不要无差别捕获 `Exception` 后丢弃上下文，也不要把所有错误都转换成同一种无信息异常。

## 12. 循环依赖是设计信号

大量循环导入往往说明：

- 两个模块职责没有真正分开；
- 公共概念放错位置；
- 依赖方向不稳定；
- 一个模块承担过多角色；
- 包的公开入口反向导入了内部模块。

解决策略：

1. 提取共同的数据类型或协议；
2. 合并实际上不可分割的模块；
3. 把协调逻辑移到更高层模块；
4. 通过依赖注入反转对具体实现的依赖；
5. 类型专用导入使用 `TYPE_CHECKING`；
6. 最后才考虑局部导入作为实现细节。

## 13. 插件式设计

系统需要按配置扩展功能时，可以建立明确插件协议：

```python
class Exporter(Protocol):
    def export(self, records, destination): ...
```

插件注册方式可以是：

- 显式字典注册；
- 配置给出模块路径并动态导入；
- 发行包入口点；
- 框架提供的扩展机制。

简单项目优先使用显式注册：

```python
EXPORTERS = {
    "json": JsonExporter(),
    "csv": CsvExporter(),
}
```

插件系统必须定义版本兼容、错误隔离、加载失败处理和可信边界。不要为了“未来可能扩展”过早构建复杂插件架构。

## 14. 测试与模块边界

好的模块边界会自然产生测试边界：

- 纯领域逻辑：快速单元测试；
- 应用服务：使用假仓库或内存实现测试协作；
- 基础设施：针对数据库、网络的集成测试；
- 入口：少量端到端测试验证组装。

不要为了测试去调用大量内部私有函数。若某段逻辑必须被大量独立测试，它可能值得成为独立公开概念或独立模块。

## 15. 从单文件逐步重构

假设原程序包含输入、校验、计算、保存和输出，可以按以下顺序重构：

1. 先用函数分离纯计算；
2. 为数据定义明确结构；
3. 把文件或数据库访问提取为仓库；
4. 把交互入口与应用服务分开；
5. 当职责稳定后再移动到不同模块；
6. 为公开行为补充测试；
7. 检查依赖是否单向；
8. 删除只转发一次、没有边界价值的多余层。

不要一次性把小脚本改造成复杂架构。模块化应解决真实变化和维护问题。

## 16. 常见反模式

### 16.1 万能工具模块

`utils.py`、`helpers.py` 不断吸收无关函数。解决方法是根据具体职责命名，例如 `date_parser.py`、`price_formatter.py`。

### 16.2 一个文件一个函数

文件数量很多，但每个文件没有独立职责，阅读时需要频繁跳转。相关小函数应聚合在同一高内聚模块。

### 16.3 巨型模块

一个模块承担模型、存储、网络、业务规则和入口。应按变化原因逐步拆分。

### 16.4 重新导出一切

顶层 `__init__.py` 导出所有内部对象，导致公共 API 失控、导入变重和循环依赖。

### 16.5 隐式注册副作用

仅靠“导入某模块”来修改全局注册表，容易受导入顺序影响。优先使用显式注册或清晰的插件加载阶段。

### 16.6 过度抽象

只有一个实现、没有替换需求的简单函数被包装成多层接口、工厂和适配器。抽象应该降低变化成本，而不是展示设计模式。

## 17. 模块设计检查清单

- 能否用一句话说明模块职责？
- 文件中的对象是否因相近原因变化？
- 公开接口是否少而明确？
- 调用者是否依赖内部名称或全局状态？
- 导入是否产生网络、数据库或输出副作用？
- 依赖方向是否稳定且无环？
- 外部系统是否可通过参数替换？
- 核心逻辑是否能在无 I/O 情况下测试？
- 包层级是否过深？
- 当前抽象是否解决真实问题？

## 18. 本节小结

1. 模块化的本质是建立职责和依赖边界，不是追求更多文件。
2. 高内聚让相关代码一起变化，低耦合让模块只依赖稳定接口。
3. 输入输出、业务规则和基础设施应适当分离，使核心逻辑可独立测试。
4. 依赖注入可以把具体数据库、网络和邮件实现从业务逻辑中移出。
5. 循环导入、万能工具模块和大量全局状态通常是边界不清的信号。
6. 架构复杂度应随真实需求增长，既要避免巨型模块，也要避免过度设计。
