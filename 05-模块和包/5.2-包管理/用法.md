# 5.2 包管理

本节中的“包”主要指用于组织 Python 模块的导入包（import package），不是后面将介绍的可发布发行包。包通过目录层级建立模块命名空间，使大型项目可以按业务领域和职责拆分代码。

## 1. 模块、导入包与发行包

这三个概念容易混淆：

| 概念 | 含义 | 示例 |
|---|---|---|
| 模块（module） | 可被导入的代码单元，常见形式是一个 `.py` 文件 | `shop/models.py` |
| 导入包（import package） | 可以包含子模块和子包的模块 | `shop/` |
| 发行包（distribution package） | 由安装工具安装和管理的项目产物 | PyPI 上的 `requests` |

发行包名称与导入名称不一定相同。例如安装时使用的名称可能包含连字符，而代码中使用下划线或完全不同的导入名。

## 2. 普通包结构

一个典型普通包：

```text
project/
├── main.py
└── shop/
    ├── __init__.py
    ├── models.py
    ├── services.py
    └── utils/
        ├── __init__.py
        └── validators.py
```

导入方式：

```python
import shop.models
from shop import services
from shop.utils.validators import validate_email
```

完整模块名反映目录层级：

- `shop`
- `shop.models`
- `shop.utils`
- `shop.utils.validators`

普通包通常包含 `__init__.py`。它可以是空文件，也可以执行轻量初始化、声明版本或组织公开 API。

## 3. `__init__.py` 的作用

### 3.1 标记普通包

包含 `__init__.py` 的目录会被当作普通包。虽然现代 Python 也支持没有该文件的命名空间包，但学习和大多数普通项目中，显式保留它通常更直观。

### 3.2 包初始化

第一次导入包时会执行 `__init__.py`：

```python
# shop/__init__.py
print("initializing shop package")
```

与模块顶层代码一样，不应在这里执行耗时或不稳定的外部操作。

### 3.3 组织公开接口

```python
# shop/__init__.py
from .models import Product
from .services import create_order

__all__ = ["Product", "create_order"]
```

调用者可以写：

```python
from shop import Product, create_order
```

这种“重新导出”可以提供简洁稳定的入口，但要权衡以下问题：

- `__init__.py` 过重会增加导入时间；
- 大量重新导出会隐藏对象真实位置；
- 不谨慎的交叉导入容易形成循环依赖；
- 公共 API 一旦发布，就需要考虑兼容性。

### 3.4 包元数据

小型内部项目有时在 `__init__.py` 中设置版本：

```python
__version__ = "1.0.0"
```

已安装发行包的版本通常更适合通过 `importlib.metadata.version()` 查询，避免在多个文件重复维护版本号。

## 4. 绝对导入

绝对导入从顶层包开始写完整路径：

```python
# shop/services.py
from shop.models import Product
from shop.utils.validators import validate_email
```

优点：

- 来源清晰，阅读单个文件时容易定位；
- 移动到包内其他层级时含义通常更稳定；
- 不容易误导入同名模块；
- 大多数情况下推荐优先使用。

缺点是大型深层包中的路径可能较长，包整体重命名时改动较多。

## 5. 相对导入

相对导入使用点号表示当前包层级：

```python
# shop/services.py
from .models import Product
from .utils.validators import validate_email
```

点号含义：

- `.`：当前包；
- `..`：上一级包；
- `...`：上两级包。

例如：

```text
company/
└── shop/
    ├── models.py
    └── services/
        └── order.py
```

```python
# company/shop/services/order.py
from ..models import Product
```

相对导入只能在明确的包上下文中工作。下面这种直接运行经常失败：

```bash
python company/shop/services/order.py
```

因为该文件作为脚本运行时不再拥有预期的父包上下文。应从项目根目录使用模块方式运行：

```bash
python -m company.shop.services.order
```

## 6. `python -m` 与模块执行

`python -m package.module` 会先按模块导入规则定位目标，再把它作为入口执行。这比直接传入深层文件路径更能保留正确的包语义。

```text
project/
└── app/
    ├── __init__.py
    ├── __main__.py
    └── cli.py
```

如果定义：

```python
# app/__main__.py
from .cli import main

main()
```

就可以执行：

```bash
python -m app
```

`__main__.py` 是包作为程序运行时的入口。可复用逻辑仍应放在普通模块中，`__main__.py` 只负责调用入口函数。

## 7. 导入子模块时的绑定

执行：

```python
import shop.models
```

通常会先初始化 `shop`，再加载 `shop.models`，并把子模块作为属性绑定到包对象上。因此可以使用：

```python
shop.models.Product
```

但仅执行：

```python
import shop
```

并不保证所有子模块自动加载。只有 `shop/__init__.py` 主动导入的成员，或已经被其他导入语句加载的子模块，才会相应可用。不要假设“导入包”等于“递归导入包内所有文件”。

## 8. `__package__`、`__path__` 与 `__spec__`

理解以下属性有助于排查导入问题：

```python
import shop

print(shop.__name__)
print(shop.__package__)
print(shop.__path__)
print(shop.__spec__)
```

- `__package__`：相对导入使用的包上下文；
- `__path__`：包搜索子模块的位置集合，普通模块通常没有该属性；
- `__spec__`：模块的导入规范，包含加载器、来源、是否为包等信息。

日常业务代码通常不需要直接修改这些属性。

## 9. 命名空间包

命名空间包可以让同一个逻辑包分布在多个目录中，通常没有 `__init__.py`：

```text
plugins-a/
└── company_plugins/
    └── export/
        └── csv_plugin.py

plugins-b/
└── company_plugins/
    └── importers/
        └── json_plugin.py
```

当两个父目录都位于模块搜索路径中时，`company_plugins` 可以组合来自不同位置的子包。

命名空间包适合大型插件生态、多个发行项目共享顶层命名空间等场景。普通单仓库项目若没有明确需求，使用带 `__init__.py` 的普通包更易理解和管理。

## 10. 包内资源文件

包中除了 Python 代码，还可能包含模板、默认配置、证书或静态数据：

```text
weather_app/
├── __init__.py
├── service.py
└── data/
    └── city_codes.json
```

不要假设当前工作目录就是包目录，也不要简单拼接相对文件路径。应使用 `importlib.resources`：

```python
from importlib.resources import files

data_file = files("weather_app").joinpath("data/city_codes.json")
text = data_file.read_text(encoding="utf-8")
```

这样更适合已安装包、压缩资源和不同运行目录。发布发行包时，还必须确保构建配置把资源文件包含进产物。

## 11. 推荐的项目布局

### 11.1 简单布局

```text
project/
├── pyproject.toml
├── README.md
├── myapp/
│   ├── __init__.py
│   ├── cli.py
│   └── services.py
└── tests/
    └── test_services.py
```

适合学习和简单应用，但从项目根目录运行时，源码目录天然位于搜索路径中，可能掩盖“项目未正确安装”的问题。

### 11.2 `src` 布局

```text
project/
├── pyproject.toml
├── README.md
├── src/
│   └── myapp/
│       ├── __init__.py
│       ├── cli.py
│       └── services.py
└── tests/
    └── test_services.py
```

`src` 布局可以减少从仓库目录意外导入未安装源码的情况，促使开发和测试更接近用户安装后的行为。它需要正确配置构建工具，并通常以可编辑模式安装后开发。

## 12. 包命名与目录设计

- 包名通常使用简短的小写名称，下划线应谨慎使用；
- 不要使用连字符作为导入包目录名；
- 顶层包名应避免与标准库、常见第三方库冲突；
- 目录层级表达稳定的领域边界，而不是机械地按“控制器、工具、其他”无限拆分；
- 避免层级过深，过深的相对导入通常意味着结构难以理解；
- `utils.py` 容易变成无边界杂物箱，最好使用更具体的名称；
- 子包之间尽量形成单向依赖，不要相互随意导入内部实现。

## 13. 包的公开与内部接口

Python 主要通过命名约定表达内部实现：

```text
shop/
├── __init__.py
├── api.py
├── _pricing.py
└── _internal/
    └── cache.py
```

前导下划线表示“不建议外部依赖”，但不会阻止访问。真正保持可维护性的关键是：

- 文档只承诺公开入口；
- 测试重点覆盖公开行为；
- 外部代码不越过边界依赖内部模块；
- 重构时保持公开 API 兼容，内部实现可以调整。

## 14. 常见导入错误

### 14.1 `ModuleNotFoundError`

目标包不在当前解释器的搜索范围内。检查运行目录、解释器、虚拟环境、安装状态和拼写。

### 14.2 `ImportError: attempted relative import with no known parent package`

通常是直接运行了包内深层文件。回到项目根目录使用 `python -m 完整模块名`。

### 14.3 `cannot import name ... from partially initialized module`

通常与循环导入有关。检查模块依赖图并调整职责，不要只交换导入语句顺序。

### 14.4 同名包导入错误

使用 `module.__file__`、`module.__spec__` 和 `sys.path` 确认真正加载的位置。

## 15. 本节小结

1. 包通过目录和点分模块名组织大型代码，普通包通常包含 `__init__.py`。
2. `__init__.py` 可以组织公开接口，但应保持轻量并避免复杂副作用。
3. 绝对导入来源清晰；相对导入适合表达包内关系，但依赖正确的包上下文。
4. 包内模块应优先通过 `python -m package.module` 运行，而不是直接执行深层文件。
5. `src` 布局有助于让测试使用真正安装后的包，适合规范化项目。
6. 包结构应体现职责边界和单向依赖，避免循环导入、过深层级和万能 `utils`。
