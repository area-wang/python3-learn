# 6.4 自定义异常

内置异常通用的语义无法表达业务错误时，就需要自定义异常。通过定义自己的异常类，可以让错误信息更精确、更结构化，也便于调用方按业务语义分别捕获和处理。本节讲解自定义异常的设计、继承关系、属性携带，以及在分层架构中的使用。

## 1. 为什么需要自定义异常

内置异常类别有限，业务错误往往需要更细分的语义：

```python
class InsufficientBalanceError(Exception):  # 余额不足
    pass

class UserNotFoundError(LookupError):     # 用户不存在
    pass

class ValidationError(ValueError):        # 数据校验失败
    pass
```

相比之下，`raise Exception("余额不足")` 只有字符串描述，调用方既无法针对“余额不足”专门处理，也无法从中读取结构化信息。

自定义异常的好处：

- **按业务语义捕获**：上层只捕获自己关心的类型；
- **结构化信息**：可以附带字段、错误码等；
- **分层清晰**：领域层抛领域异常，避免泄漏底层细节；
- **可扩展**：通过继承表达异常分类。

## 2. 最简单：继承现有异常

最简单的自定义异常只需继承一个合适的父类，并保持空体：

```python
class MyError(Exception):
    pass

raise MyError("something wrong")
```

选择合适的父类很重要，常用做法：

| 想表达的语义 | 推荐父类 |
|---|---|
| 通用领域错误 | `Exception` |
| 输入格式/内容不对 | `ValueError` |
| 类型不支持的操作 | `TypeError` |
| 查找类错误 | `LookupError`（或 `KeyError`） |
| 运行期意外 | `RuntimeError` |

继承内置异常的好处：调用方如果不关心具体子类，仍能按父类捕获：

```python
try:
    raise MyError("...")
except Exception as e:   # 仍可捕获
    print(e)
```

## 3. 选择继承哪个父类

继承关系直接决定了“是否容易捕获”和“语义归属”。

```python
class AgeInvalid(ValueError):
    pass

class OrderNotFount(LookupError):
    pass
```

选择依据：

1. **功能最贴近的内置基类**：让父类本身就能表达“这类错误”的大致含义；
2. **领域异常的根类**：项目可定义一个 `AppError(Exception)` 作为根，所有业务异常都从它派生，便于在最外层统一捕获并转换为对外的响应；
3. **避免过深继承**：层级过深会让分类难以理解，通常 2-3 层足够。

```python
class AppError(Exception):
    """本应用所有业务异常的根类。"""

class PaymentError(AppError):
    """支付相关错误。"""

class InsufficientBalanceError(PaymentError):
    """余额不足。"""
```

调用方可以分别按需捕获：

```python
try:
    pay(...)
except InsufficientBalanceError as e:
    refund(...)
except PaymentError as e:
    notify_admin(e)
except AppError as e:
    show_user_error(e)
```

## 4. 构造器与属性携带

让自定义异常接受和服务化字段，调用方能直接读取结构化信息：

```python
class InvalidAge(ValueError):
    def __init__(self, age, reason):
        super().__init__(f"年龄非法: {age}, 原因: {reason}")
        self.age = age
        self.reason = reason
```

使用：

```python
try:
    raise InvalidAge(-1, "不能为负")
except InvalidAge as e:
    print(e.age)     # -1
    print(e.reason)  # 不能为负
    print(str(e))    # 年龄非法: -1, 原因: 不能为负
```

约定要点：

- 调用 `super().__init__(...)` 把可读消息传给父类，使 `str(e)` 友好；
- 自定义字段赋给实例属性；
- 如希望 `args` 也能保留，可传入字段元组：`super().__init__(age, reason)`。

```python
class InvalidAge(ValueError):
    def __init__(self, age, reason):
        super().__init__(age, reason)
        self.age = age
        self.reason = reason

try:
    raise InvalidAge(-1, "不能为负")
except InvalidAge as e:
    print(e.args)    # (-1, '不能为负')
    print(e.age)     # -1
```

`args` 在异常复制、序列化、打印时有用，但结构化访问应使用具名属性。

## 5. 错误码模式

有些项目用整数或字符串错误码区分错误，便于日志和前端处理：

```python
class ApiError(Exception):
    def __init__(self, code, message, payload=None):
        super().__init__(message)
        self.code = code
        self.message = message
        self.payload = payload

raise ApiError(40401, "用户不存在", {"user_id": 42})
```

调用方：

```python
try:
    ...
except ApiError as e:
    if e.code == 40401:
        show_not_found(e.payload["user_id"])
    else:
        show_error(e.message)
```

错误码的好处：跨语言稳定，不受异常类名变化影响；缺点：分散的码表需要额外文档维护。

## 6. 异常分层与翻译

分层架构中，让下层异常自动上抛往往会泄漏实现细节。常见做法是在层边界“翻译”异常：

```python
# repository.py
class RepositoryError(Exception):
    pass

def get_user(user_id):
    try:
        return db.query(user_id)
    except db.NotFoundError as e:
        raise UserNotFoundError(user_id) from e
    except db.ConnectionError as e:
        raise RepositoryError("数据库不可用") from e

# service.py
def login(user_id, password):
    user = get_user(user_id)   # 抛 UserNotFoundError / RepositoryError
    if not verify(password, user.password_hash):
        raise AuthenticationError(user_id)
    return user
```

要点：

- 下层捕获自己的实现异常，翻译为领域异常，并用 `from e` 保留根因；
- 上层只关心领域异常，不知道用的是哪种数据库；
- 最外层（控制器、入口）根据领域异常生成对外响应。

```python
# api.py
def handle_login(request):
    try:
        user = login(...)
    except UserNotFoundError:
        return {"ok": False, "error": "USER_NOT_FOUND"}
    except AuthenticationError:
        return {"ok": False, "error": "AUTH_FAILED"}
    except AppError as e:
        return {"ok": False, "error": "INTERNAL", "message": str(e)}
```

## 7. __str__ 与 __repr__

若构造器已把消息传给父类，`str(e)` 通常够用。若需要自定义展示，可重写 `__str__`：

```python
class FieldError(ValueError):
    def __init__(self, field, value, reason):
        super().__init__(f"{field}={value!r}: {reason}")
        self.field = field
        self.value = value
        self.reason = reason

    def __str__(self):
        return f"[{self.field}] 值 {self.value!r} 非法: {self.reason}"
```

`__repr__` 在调试时显示，可以重写为更紧凑的形式，通常默认实现已可接受。

## 8. 多个异常一起捕获

利用继承关系，一条 `except` 即可 grouped 捕获：

```python
class PaymentError(AppError): pass
class PaymentTimeout(PaymentError): pass
class PaymentRejected(PaymentError): pass

try:
    pay()
except PaymentTimeout:
    retry()
except PaymentError:    # 捕获所有其他支付错误（含 PaymentRejected 等）
    notify_support()
except AppError:
    show_generic_error()
```

注意分支顺序：子类写在前面，父类写在后面。

## 9. 异常类放在哪里

- 简单项目：把异常类定义在使用它的模块顶部；
- 较大项目：统一放在 `exceptions.py` 或按子领域分文件；
- 跨模块复用的异常定义在被依赖的基础模块里，避免循环导入。

```text
project/
├── exceptions.py     # 通用 AppError 及领域根异常
├── payment/
│   └── errors.py      # 支付相关异常
└── ...
```

## 10. 设计建议

- 异常类名以 `Error` 结尾，符合 Python 内置习惯（`KeyError`、`ValueError`）；
- 类名要表达“发生了什么”，如 `InsufficientBalanceError`，而非 `BalanceException`；
- 携带结构化字段，但不要塞入难以序列化或循环引用的对象；
- 通过继承表达分类与可捕获性；
- 在层边界翻译异常，保留根因（`from e`）；
- 不要为每个错误都定义新异常类，颗粒度过细反而难维护；合理借助错误码区分差异；
- 文档化每个领域异常的含义、字段与何时抛出。

## 11. 完整示例：账户服务

```python
# account_error.py
class AccountError(Exception):
    """账户相关错误根类。"""

class InsufficientBalanceError(AccountError):
    def __init__(self, account_id, balance, amount):
        super().__init__(f"账户 {account_id} 余额 {balance} 不足以支付 {amount}")
        self.account_id = account_id
        self.balance = balance
        self.amount = amount

class AccountInactiveError(AccountError):
    def __init__(self, account_id):
        super().__init__(f"账户 {account_id} 已停用")
        self.account_id = account_id


# account_service.py
def withdraw(account, amount):
    if amount <= 0:
        raise ValueError("amount 必须大于零")
    if not account.active:
        raise AccountInactiveError(account.id)
    if account.balance < amount:
        raise InsufficientBalanceError(account.id, account.balance, amount)
    account.balance -= amount
    return account.balance


# api.py
def handle_withdraw(account, amount):
    try:
        balance = withdraw(account, amount)
    except InsufficientBalanceError as e:
        return {"ok": False, "error": "INSUFFICIENT_BALANCE",
                "balance": e.balance, "amount": e.amount}
    except AccountInactiveError as e:
        return {"ok": False, "error": "ACCOUNT_INACTIVE",
                "account_id": e.account_id}
    except AccountError as e:
        return {"ok": False, "error": "ACCOUNT_ERROR", "message": str(e)}
    return {"ok": True, "balance": balance}
```

外层控制器只看到领域异常和结构化字段，不必了解账户类内部细节。

## 12. 本节小结

1. 自定义异常让业务错误表达更精确、更结构化。
2. 继承合适的目标父类（通常 `Exception` 或更具体的内置异常），既贴合语义又便于捕获。
3. 通过继承表达异常分类：领域根异常 → 子领域异常 → 具体异常，注意 `except` 中子类在前。
4. 自定义构造器携带属性字段，同时把可读消息传给父类，使 `str(e)` 友好。
5. 在架构层边界翻译异常，用 `from e` 保留根因，避免泄漏实现细节。
6. 异常命名遵循 `XxxError` 惯例，颗粒度合理，文档化含义与字段。
