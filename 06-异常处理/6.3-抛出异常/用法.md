# 6.3 抛出异常

抛出异常（raise）是主动向调用方报告错误信息的方式。当一个函数无法完成自己的职责时，它通常不返回特殊值，而是抛出一个语义明确的异常，让调用方决定如何处理。本节讲解 `raise` 的基本用法、异常链机制，以及如何与 `assert`、`traceback` 等配合。

## 1. raise 的基本形式

```python
raise 异常类("消息")
```

```python
def divide(a, b):
    if b == 0:
        raise ZeroDivisionError("除数不能为零")
    return a / b
```

也可以先构造异常对象再抛：

```python
error = ValueError("非法输入")
raise error
```

两种写法等价，但通常直接 `raise ValueError("非法输入")` 更简洁。

## 2. raise 的使用场景

### 2.1 参数合法性检查

```python
def set_age(age):
    if age < 0:
        raise ValueError(f"年龄不能为负数: {age}")
    if age > 150:
        raise ValueError(f"年龄不合理: {age}")
    return age
```

### 2.2 前置条件不满足

```python
def transfer(account_from, account_to, amount):
    if amount <= 0:
        raise ValueError("转账金额必须大于零")
    if account_from.balance < amount:
        raise RuntimeError("余额不足")
    ...
```

### 2.3 不支持的操作

```python
def fetch_user(user_id):
    if user_id is None:
        raise TypeError("user_id 不能为 None")
    ...
```

### 2.4 转换异常类型

底层异常对外语义不友好时，可以翻译为上层异常（异常链见后文）：

```python
def get_user(user_id):
    try:
        row = db.query(user_id)
    except db.NotFoundError as e:
        raise ValueError(f"用户不存在: {user_id}") from e
    return row
```

## 3. 不带参数的 raise

在 `except` 块中，`raise` 不带参数表示“重新抛出当前捕获的异常”：

```python
def process(data):
    try:
        return int(data)
    except ValueError:
        log("解析失败")
        raise      # 重新抛出
```

它和 `raise e` 的区别在于 traceback：

```python
# 不推荐：会改变 traceback 的起点
raise e

# 推荐：保留原始异常的完整调用栈
raise
```

## 4. 异常链：raise ... from ...

异常链用于在抛出新异常时，保留“原始异常”作为上下文，便于排查根因。语法是 `raise ... from ...`：

```python
def load_user(user_id):
    try:
        data = open(f"{user_id}.json").read()   # 可能 FileNotFoundError
    except FileNotFoundError as e:
        raise ValueError(f"无法加载用户 {user_id}") from e
```

抛出后看到的 traceback 类似：

```text
FileNotFoundError: [Errno 2] No such file or directory: '42.json'

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  ...
ValueError: 无法加载用户 42
```

### 4.1 __cause__ 与 __context__

- `from e` 会把 `e` 设置为新异常的 `__cause__`，表示“直接原因”；
- 没有显式 `from` 时，如果异常是在处理另一个异常的过程中抛出的，原异常会自动成为 `__context__`。

```python
def f():
    try:
        1 / 0
    except ZeroDivisionError:
        raise ValueError("处理失败")   # __context__ 会被设置

def g():
    try:
        open("none.txt")
    except FileNotFoundError as e:
        raise ValueError("处理失败") from e   # __cause__ 被设置
```

打印 `__cause__` 和 `__context__` 的区别：

```python
try:
    g()
except ValueError as e:
    print("cause:", e.__cause__)
    print("context:", e.__context__)
```

| 属性 | 设置时机 | 含义 |
|---|---|---|
| `__cause__` | 显式 `raise ... from ...` | 主动声明的直接原因 |
| `__context__` | 在处理一个异常时又抛出另一个 | 隐式上下文 |

显式 `from` 表达更清晰的因果关系，是翻译异常时的推荐写法。

### 4.2 抑制上下文：from None

如果不希望新异常携带原始上下文（例如把实现细节隐藏起来），可以使用 `raise ... from None`：

```python
def get_user(user_id):
    try:
        internal_lookup(user_id)
    except InternalError:
        raise UserNotFoundError(user_id) from None   # 不暴露内部异常
```

这样打印 traceback 时不会出现“上述异常导致以下异常”信息。但主要用于确实需要隐藏实现细节的场景，不要轻易丢弃上下文。

## 5. raise 在循环和函数中的传播

`raise` 一旦执行，当前函数立即停止返回，异常沿调用链上抛：

```python
def validate(age):
    if age < 0:
        raise ValueError("年龄非法")
    return age

def create_user(name, age):
    age = validate(age)        # 这里抛出 ValueError
    return {"name": name, "age": age}   # 不会执行

create_user("alice", -1)      # 最终在调用处暴露
```

`create_user` 不需要处理异常，它会自动透传到调用者。是否处理异常是设计选择，而不是义务。

## 6. 先检查再抛出 vs EAFP

Python 风格通常偏 EAFP（Easier to Ask Forgiveness than Permission，先做再说）：直接尝试并在异常发生时捕获，而不是事先做大量检查。但有些前置条件用 LBYL（Look Before You Leap，先看再跳）更清晰：

```python
# EAFP：直接做，捕获异常
try:
    value = int(text)
except ValueError:
    value = None

# LBYL：先判断再执行
if text.lstrip("-").isdigit():
    value = int(text)
else:
    value = None
```

要点：

- 不确定来源（用户输入、第三方数据）的解析，EAFP 通常更简洁自然；
- 边界清晰、判断成本低的前置条件，LBYL 同样可读；
- 不论哪种风格，错误都应通过**抛出语义化异常**报告，而不是返回容易忽视的魔法值。

## 7. assert：调试断言

`assert` 用于在代码中声明“此处必须为真”的条件，常用于开发期自检和不可达分支提示：

```python
def sqrt(x):
    assert x >= 0, f"参数必须为非负数: {x}"
    return x ** 0.5
```

`assert cond, msg` 在 `cond` 为 `False` 时抛出 `AssertionError(msg)`，等价于：

```python
if not cond:
    raise AssertionError(msg)
```

### 7.1 assert 的局限

- **可以被全局关闭**：用 `python -O` 运行时，所有 `assert` 语句会被跳过；因此**不要用 assert 做生产环境的参数校验或业务逻辑判断**；
- 适合做开发期不变式检查、单元测试、防御性自我检查；
- 对外接口的参数校验应使用显式 `if + raise`，而不是 `assert`。

```python
# 不推荐：被优化后失效
def withdraw(balance, amount):
    assert amount > 0, "金额必须大于零"
    ...

# 推荐：稳定有效
def withdraw(balance, amount):
    if amount <= 0:
        raise ValueError("金额必须大于零")
    ...
```

### 7.2 AssertionError

`AssertionError` 是普通异常，可以被捕获：

```python
try:
    assert False, "条件不成立"
except AssertionError as e:
    print("断言失败:", e)
```

虽然可捕获，但通常不应在业务中专门处理 `AssertionError`，而应让它在开发期暴露问题。

## 8. 抛出时携带更多信息

异常对象可以通过构造参数和自定义属性携带信息（自定义异常见 6.4 节）。即使是内置异常，也可以多参数化：

```python
raise ValueError("非法值", "field=age", "value=-1")

try:
    raise ValueError("非法值", "field=age", "value=-1")
except ValueError as e:
    print(e.args)   # ('非法值', 'field=age', 'value=-1')
```

`e.args` 会保留所有构造参数，便于上层解析。但更结构化的做法仍是自定义异常类。

## 9. 抛出异常的成本

抛出异常本身有一定开销（构造异常、收集 traceback），因此：

- 不要用异常做热点循环的正常控制流；
- 不要把“预期会发生”的情况当成异常频繁抛出；
- 对于“可能失败且失败很常见”的查询（例如查字典键），优先用 `get`、`in` 等返回值方式。

但是对于真正的错误情况，抛出异常才是清晰的契约表达，不应为了“性能”而改用魔法值掩盖错误。

## 10. 实用模式

### 10.1 翻译并保留原因

```python
def load_users():
    try:
        with open("users.json") as f:
            return json.load(f)
    except FileNotFoundError as e:
        raise RuntimeError("用户数据文件缺失") from e
    except json.JSONDecodeError as e:
        raise RuntimeError("用户数据损坏") from e
```

### 10.2 不可达分支

```python
def handle(command):
    if command == "start":
        return start()
    elif command == "stop":
        return stop()
    else:
        raise ValueError(f"未知命令: {command!r}")
```

### 10.3 带上下文的再抛出

```python
def task():
    try:
        do_work()
    except Exception:
        log("任务失败")
        raise RuntimeError("task 执行失败") from sys.exc_info()[1]
```

更常见的是直接 `raise ... from e`，`sys.exc_info()[1]` 等价效用于手动构造场景。

## 11. 常见误区

- **抛出过宽的异常类型**：`raise Exception("出错了")` 信息模糊，应使用具体类型；
- **抛错后还试图返回**：`raise` 后函数已停止，写在其后的代码不会执行；
- **用 assert 做参数校验**：被 `-O` 关闭后失效；
- **吞掉异常又不抛**：捕获后既不处理也不 `raise`，等于掩盖；
- **丢失上下文**：`raise NewError()` 不带 `from`，原异常信息进入 `__context__` 间接展示，不如显式 `from e` 清楚；
- **过度翻译**：把所有底层异常都翻译成 `RuntimeError`，丢失语义，翻译应保留有意义的类型。

## 12. 本节小结

1. `raise 异常类("消息")` 主动报告错误，是函数表达“无法履行职责”的标准方式。
2. `except` 中不带参数的 `raise` 重新抛出当前异常并保留原始 traceback。
3. `raise ... from cause` 建立异常链，把 `cause` 记录到新异常的 `__cause__`；`from None` 抑制上下文。
4. `__context__` 在“处理异常过程中又抛异常”时自动设置，`__cause__` 由 `from` 显式设置。
5. `assert` 用于开发期不变式检查，可被 `-O` 关闭，不能用作生产参数校验。
6. 异常应清晰、具体、带原因，避免过宽类型和丢失上下文。
