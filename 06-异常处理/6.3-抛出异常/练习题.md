# 6.3 抛出异常练习题

## 一、概念题

1. `raise ValueError("...")` 和 `error = ValueError("..."); raise error` 在效果上是否等价？为什么通常使用前者？
2. `except` 块中不带参数的 `raise` 与 `raise e` 有什么区别？哪种更推荐？为什么？
3. `raise ... from cause` 的作用是什么？它会把原始异常记录到新异常的哪个属性上？
4. `__cause__` 和 `__context__` 的区别是什么？分别由什么机制设置？
5. `raise NewError() from None` 起什么作用？什么时候适合用它？
6. 为什么不应该用 `assert` 做对外接口的参数校验？什么样的运行选项会影响 `assert` 的行为？
7. `assert cond, msg` 在 `cond` 为假时抛出什么异常？它和 `if not cond: raise ...` 在语义上有何区别？
8. EAFP 和 LBYL 各指什么风格？为什么 Python 通常偏好 EAFP？
9. 抛出异常时携带多个参数（如 `raise ValueError("非法", "age", -1)`），这些参数可以在哪里取回？
10. 为什么不应把所有底层异常都翻译成 `RuntimeError`？翻译异常时应保留什么？

## 二、判断代码输出

### 1. 抛出后停止

```python
def make(age):
    if age < 0:
        raise ValueError("age < 0")
    print("已通过校验")
    return age

try:
    make(-1)
except ValueError:
    print("捕获到异常")
```

写出输出，并说明“已通过校验”是否会被打印、为什么。

### 2. 异常链

```python
def f():
    try:
        1 / 0
    except ZeroDivisionError as e:
        raise ValueError("上层错误") from e

try:
    f()
except ValueError as e:
    print("cause:", type(e.__cause__).__name__)
    print("context:", type(e.__context__).__name__)
```

写出输出，并说明 `__cause__` 与 `__context__` 的来源。

### 3. 隐式上下文

```python
def g():
    try:
        open("no_such_file_xyz.txt")
    except FileNotFoundError:
        raise RuntimeError("处理失败")

try:
    g()
except RuntimeError as e:
    print("cause:", e.__cause__)
    print("context:", type(e.__context__).__name__)
```

写出输出，说明 `__cause__` 为什么是 `None`、`__context__` 为什么不是。

### 4. from None

```python
def h():
    try:
        {}["x"]
    except KeyError:
        raise ValueError("上层") from None

try:
    h()
except ValueError as e:
    print("cause:", e.__cause__)
    print("context:", e.__context__)
```

写出输出，说明 `from None` 抑制了什么。

### 5. assert 行为

```python
def check(x):
    assert x > 0, "x 必须为正"
    return x

try:
    check(0)
except AssertionError as e:
    print("断言:", e)
```

写出输出，并指出 `assert` 触发的具体异常类型。

### 6. 重新抛出保留栈

```python
def inner():
    raise ValueError("inner")

def middle():
    try:
        inner()
    except ValueError:
        raise

try:
    middle()
except ValueError as e:
    print("捕获:", e)
```

写出输出，并说明 `middle` 中 `raise`（不带参数）保持了什么信息。

### 7. 断言能否被捕获

```python
try:
    assert 1 == 2, "数学崩坏"
except AssertionError as e:
    print("抓到了:", e)
```

写出输出，说明 `AssertionError` 是否可被普通 `except` 捕获。

## 三、改错题

### 1. 抛出过宽

```python
def set_score(score):
    assert score >= 0
    if score > 100:
        raise Exception("分数过高")
    return score
```

指出两个问题：

1. 为什么不该用 `assert` 做参数校验？会被什么运行选项关闭？
2. 为什么 `raise Exception(...)` 过于宽泛？应改用什么具体类型？并改写。

### 2. 丢失上下文

```python
def load_item(item_id):
    try:
        with open(f"{item_id}.txt") as f:
            return f.read()
    except FileNotFoundError:
        raise RuntimeError(f"无法加载 {item_id}")
```

说明 `RuntimeError` 时缺少了什么信息，并用 `from` 改写使其保留原因。

### 3. 抛错后多余的 return

```python
def get_balance(user):
    if user is None:
        raise ValueError("user 不能为空")
        return 0
    return user.balance
```

指出无意义的代码行并解释原因，去掉它。

### 4. 翻译不当

```python
def parse_list(text):
    try:
        return json.loads(text)
    except Exception:
        raise RuntimeError("解析失败")
```

指出问题：

1. 捕获 `Exception` 过宽；
2. 翻译成 `RuntimeError` 丢失语义；
3. 未保留原始原因。

改写为精确捕获 `json.JSONDecodeError`、用更贴切的语义化异常（可使用本章后续会学的自定义异常，或先用 `ValueError`），并用 `from` 保留原异常。

## 四、编程题

### 1. 入参校验函数

实现 `def create_user(name, age, email):`，要求：

- `name` 必须是非空字符串，否则抛 `ValueError` 并说明原因；
- `age` 必须是 int 且在 0 到 120 之间，否则抛 `ValueError`；
- `email` 必须包含 `@`，否则抛 `ValueError`；
- 任一错误信息都要包含“哪个字段、什么问题”；
- 写出 3 个合法、3 个非法的调用，并展示捕获后的异常消息。

### 2. 翻译并保留原因

实现 `def load_users():`：

- 读取 `users.json`；
- 文件不存在时抛 `RuntimeError("用户数据文件缺失")`，保留 `FileNotFoundError` 原因；
- JSON 损坏时抛 `RuntimeError("用户数据损坏")`，保留 `json.JSONDecodeError` 原因；
- 在调用处分别捕获两种 `RuntimeError`，并打印 `e.__cause__` 的类型名。

用伪造的损坏文件和不存在的文件各测试一次。

### 3. 不可达分支

实现 `def handle_command(cmd):`，支持 `"add"`、`"remove"`、`"list"` 三种命令，其他命令抛 `ValueError`，信息中包含未知命令的字符串形式，并使用 `!r` 体现原始形态（如空字符串、带空格的命令）。

### 4. 调试断言与正式校验对比

实现 `def clamp(value, low, high):`，要求把值限制在 `[low, high]` 范围内。分别用两种方式校验 `low <= high`：

- 方式 A：使用 `assert low <= high, "..."`；
- 方式 B：使用 `if low > high: raise ValueError(...)`。

并回答：

1. 用 `python -O` 运行后，方式 A 还能阻止非法入参吗？
2. 哪种方式适合对外公开 API 的入参校验？

### 5. 重新抛出与栈保留

实现三层函数 `process -> parse -> scan`：

- `scan` 内部抛出 `RuntimeError("扫描异常")`；
- `parse` 捕获并 `raise`（不带参数）；
- `process` 捕获并 `raise RuntimeError("处理失败") from <原异常>`；
- 最外层捕获最终的 `RuntimeError`，打印 `e.__cause__` 链一路追溯到根因的类型名（提示：循环读取 `__cause__` 直到为 `None`）。

### 6. from None 的取舍

实现两个版本的 `def get_secret():`：

- 版本 A：内部捕获 `KeyError`，`raise PermissionError("无权访问") from None`；
- 版本 B：内部捕获 `KeyError`，`raise PermissionError("无权访问") from e`。

分别在外层捕获 `PermissionError`，打印 `__cause__`。说明两种写法的取舍：何时隐藏实现细节更好、何时保留原因更好？

### 7. 多参数异常

实现 `def validate_order(order):`，参数非法时抛出 `ValueError("order_invalid", field, value)`，含 3 个参数。外部捕获时分别解析出 `field` 和 `value`，按要求打印 `{field}={value}` 的诊断信息。要求至少覆盖 `amount <= 0`、`quantity <= 0` 两种情况。

## 五、综合实践：可诊断的函数调用器

实现 `def call(func, *args):`：

1. 调用 `func(*args)`；
2. 失败时把原异常翻译成自定义 `CallFailed`（本章可先用 `RuntimeError` 代替，下一节用自定义异常替换），并在异常构造时用 `from` 保留原异常；
3. 异常消息中包含 `func.__name__` 与失败参数的 `repr`；
4. 在外层捕获并打印：异常类型、消息、`__cause__` 的类型名、`__cause__` 的消息。

要求对以下三个调用都测试一次：

```python
call(int, "abc")
call(lambda x: x[10], [1, 2])
call(lambda: 1 / 0)
```

最后回答：

- 为什么“加一层翻译异常”比直接让原异常上抛更有用？
- `from` 让我们对根因的可观测性增加了什么？
